# 調用第三方服務的可用性設計

## 📝 課程概述
在微服務架構中，系統難免需要與第三方平台打交道（如支付、短信、身份認證等）。然而第三方接口往往不在你的控制範圍內，當對方不穩定或性能不佳時，如何確保自身系統的高可用性？本單元將從架構設計的角度，探討如何構建一個具備容錯能力的第三方服務調用模塊。

## 核心觀念與實作解析

### 為什麼需要專門的第三方服務模塊？

幾乎所有系統都需要與第三方平台交互：
- **登錄註冊**：微信開放平台掃碼登錄
- **金融結算**：銀行接口調用
- **短信驗證**：短信服務商
- **身份認證**：人臉識別供應商

大多數開發者在實現這些功能時，僅關注「功能實現」，卻忽略了「可用性」與「容錯」設計。這正是面試中展現系統設計能力的關鍵切入點。

### 第三方服務模塊的四大核心目標

#### 一、一致性抽象

**問題背景**：不同第三方平台的 API 差異巨大——不同的通信協議、加密算法、請求/響應格式、認證機制、回調機制等。

**解決方案**：提供統一的接口抽象層，業務方只需調用你的接口，傳入基本信息（如金額、支付方式），完全不需要關心底層細節。

**帶來的價值**：
1. **研發效率大幅提高**：業務方接入新第三方變得簡單，無需了解平台細節
2. **高可擴展性**：接入新第三方時，已有業務方完全不受影響

**實際案例**：重構前，某團隊接入接口需一週；重構後，另一團隊僅用兩天完成接入，且穩定性更高、Bug 更少。

#### 二、客戶端治理

不同於服務端或網關的治理，這裡需要在**客戶端**主動實施治理措施。

**限流策略**：
- 大多數第三方平台有調用頻率限制（如銀行接口可能限制每秒 10 個請求）
- 在發起調用前就開啟客戶端限流，避免發出必然失敗的請求

**重試機制**：
- 當第三方接口超時時，提供對業務方透明的重試機制
- **關鍵前提**：只有在第三方接口是**冪等**的情況下才能重試
- 避免業務方自行處理超時邏輯

#### 三、可觀測性支持

由於第三方接口不在控制範圍內，必須做好完善的監控體系：

**監控工具**：接入 Prometheus、SkyWalking 等工具

**告警機制**（分兩類）：
1. **維護團隊告警**：通知功能維護者出現問題
2. **業務方告警**：通知業務方第三方平台不穩定，以便啟動容錯措施

**改進效果**：
- 重構前：等用戶投訴或業務方報告才知問題
- 重構後：第三方接口問題能在短時間內被發現，快速啟動容錯預案

#### 四、測試支持

核心是提供 **Mock 服務**，讓業務方能夠充分測試：

**測試環境行為**：
- 生產環境：真實調用第三方 API
- 測試環境：返回 Mock 響應

**Mock 服務的價值**：
- **節省成本**：避免測試環境真的發送付費短信
- **降低依賴**：某些第三方認證機制複雜，測試環境難以真實調用
- **靈活控制**：可返回成功、失敗、甚至模擬超時等各種響應

### 進階容錯策略

#### 策略一：同步轉異步

**適用場景**：對時效性要求不高的業務（如數據上報）

**實現方式**：
- 當第三方崩潰時，將業務方請求臨時存儲
- 第三方恢復後，再逐步處理積壓的請求

**進階架構**：使用消息隊列徹底解耦
- 業務方將消息投遞到隊列
- 消費者服務不斷消費消息、調用第三方處理
- 處理完成後通過隊列通知業務方

**設計原則**：但凡能異步解耦的，絕不搞同步調用。

#### 策略二：自動替換第三方

**前提條件**：公司有多個可替換的服務供應商（如 A、B、C 三個短信供應商）

**實現邏輯**：
- 發現第三方 A 持續失敗或響應時間過長
- 自動切換到供應商 B

**健康判斷依據**：響應時間、錯誤率、超時率（可引導到熔斷、降級、限流話題）

**極端情況**：所有供應商都崩潰時，只能告警並接受現實（多供應商同時故障是小概率事件）

#### 策略三：壓測支持

**核心問題**：第三方不可能配合你的壓測

**解決方案**：通過 Mock 提供壓測支持

**三大要點**：
1. **模擬響應時間**：在代碼中睡眠「平均響應時間 + 隨機偏移量」
2. **觸發容錯機制**：在高並發下驗證同步轉異步、自動切換等機制確實生效
3. **流量分發**：全鏈路壓測時，根據鏈路元數據將壓測流量轉發到 Mock，真實業務請求正常調用第三方

### 面試話術設計

**主動出擊策略**：在自我介紹或項目介紹時，強調系統是高可用的微服務架構，並特別提到「需要和很多第三方平台打交道，所以特別關注第三方調用的可用性」。

**前後對比框架**：
1. 接手時的問題：可擴展性、可用性、可觀測性、可測試性都很差
2. 重構措施：一致性抽象、客戶端治理、可觀測性平台、測試工具
3. 改進效果：研發效率提升、穩定性提高、快速響應故障

**量化技巧**：研發效率難以直接量化，改用具體案例說明（如接入時間從一週縮短到兩天）。

## 💡 重點摘要

- 第三方服務模塊的四大核心目標：一致性抽象、客戶端治理、可觀測性支持、測試支持
- 客戶端治理的關鍵措施是限流和重試，重試必須確保接口冪等性
- 可觀測性支持需要為維護團隊和業務方分別設置告警機制
- 三大進階容錯策略：同步轉異步、自動替換第三方、壓測支持
- 面試時使用「前後對比」框架，用具體案例量化研發效率的提升
