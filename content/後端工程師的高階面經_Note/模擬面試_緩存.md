# Redis 緩存面試精華整理

## 📝 課程概述
本章節針對後端工程師面試中常見的緩存問題進行系統性整理，涵蓋 Redis 過期策略、緩存淘汰機制、緩存模式、一致性問題、穿透擊穿雪崩等核心議題。透過這些面試題目，幫助你檢驗對緩存知識的掌握程度，並建立完整的知識體系。

## 核心觀念與實作解析

### 一、Redis 過期數據刪除策略

Redis 採用「惰性刪除 + 定期刪除」的混合策略，而非立即刪除過期數據，原因在於：

- **為什麼不立即刪除？** 立即刪除需要為每個 key 設置定時器，當 key 數量龐大時，會消耗大量 CPU 資源，影響性能。
- **惰性刪除（Lazy Expiration）**：當訪問某個 key 時，檢查是否過期，若過期則刪除。缺點是過期數據可能長期占用內存。
- **定期刪除（Periodic Expiration）**：每隔一段時間隨機抽取部分 key 進行檢查並刪除過期項。為什麼不一次性刪除所有過期 key？因為會阻塞主線程，影響正常請求處理。
- **RDB 與 AOF 處理**：生成 RDB 時過期 key 不會被持久化；重寫 AOF 時會主動刪除過期 key。

**延伸思考**：設計本地緩存時，如何實現過期刪除？需考慮過期時間設定（過長占用內存，過短頻繁回源）。

### 二、緩存淘汰策略

當內存不足時，Redis 需要決定淘汰哪些數據：

- **LFU（Least Frequently Used）**：淘汰訪問頻率最低的數據，適合熱點數據穩定的場景。
- **LRU（Least Recently Used）**：淘汰最近最少使用的數據，適合時間局部性強的場景。
- **Redis 支持的淘汰策略**：
  - `noeviction`：不淘汰，內存滿時返回錯誤
  - `allkeys-lru` / `volatile-lru`：LRU 淘汰所有 key / 僅淘汰設置過期時間的 key
  - `allkeys-lfu` / `volatile-lfu`：LFU 淘汰
  - `allkeys-random` / `volatile-random`：隨機淘汰

**實務問題**：
1. 如何提高緩存命中率？需分析業務訪問模式、調整 key 過期時間、優化緩存預熱策略。
2. 多業務共用 Redis 時，如何控制單一業務的內存使用？可通過獨立 Redis 實例或監控告警實現。
3. 如何優先淘汰普通用戶數據、保留 VIP 用戶數據？可通過 key 命名區分或使用不同數據庫索引。

### 三、緩存模式

緩存模式主要解決緩存與數據庫之間的協作問題，但**無法完全解決一致性問題**：

| 模式 | 特點 | 一致性 |
|------|------|--------|
| Cache Aside | 先查緩存，未命中再查數據庫並回填 | 弱一致 |
| Read Through | 緩存層統一處理讀取邏輯 | 弱一致 |
| Write Through | 寫入時同步更新緩存與數據庫 | 較強一致 |
| Write Back | 先寫緩存，異步寫入數據庫 | 有數據丟失風險 |
| Refresh Ahead | 主動刷新即將過期的數據 | 弱一致 |

**Singleflight 模式**：防止緩存擊穿，將併發請求合併為單次數據庫查詢。

**延遲雙刪**：刪除緩存 → 更新數據庫 → 延遲後再次刪除緩存，降低不一致窗口期，但仍無法完全解決一致性問題。

### 四、緩存一致性問題

數據不一致的根本原因在於緩存與數據庫是兩個獨立存儲，更新無法原子化完成：

**常見解決方案**：
1. **設置過期時間**：作為兜底，最終一致性。
2. **延遲雙刪**：降低不一致窗口。
3. **分布式鎖**：強一致性，但性能開銷大。
4. **訂閱 Binlog**：異步更新緩存，解耦更新邏輯。
5. **本地緩存 + Redis**：需考慮多級緩存一致性，通常通過消息隊列通知更新。

**關鍵問題**：
- 更新數據庫和更新緩存能否同時成功？需要考慮事務補償機制。
- 併發更新如何保證一致性？可通過樂觀鎖、版本號或分布式鎖實現。

### 五、緩存穿透、擊穿、雪崩

| 問題 | 定義 | 解決方案 |
|------|------|----------|
| 穿透 | 查詢不存在的數據，緩存無法命中，壓力直接打到數據庫 | 布隆過濾器、空值緩存、參數校驗 |
| 擊穿 | 熱點 key 過期瞬間，大量請求穿透到數據庫 | 互斥鎖、Singleflight、熱點數據永不過期 |
| 雪崩 | 大量緩存同時過期或 Redis 崩潰 | 過期時間隨機化、多級緩存、熔斷降級、緩存預熱 |

**Redis 崩潰保護策略**：
- 熔斷機制：快速失敗，避免拖垮數據庫
- 降級策略：返回默認值或緩存副本
- 多級緩存：本地緩存作為備援

### 六、Redis 單線程模型

**為什麼 Redis 用單線程？**
1. 內存操作極快，瓶頸在網絡 IO 而非 CPU
2. 避免多線程上下文切換開銷
3. 無鎖設計，邏輯簡單高效

**Redis 真的是單線程嗎？**
- 核心命令執行是單線程
- 後期引入多線程處理網絡 IO（讀寫 socket），提升吞吐量

**為什麼 Memcached 用多線程？**
- Memcached 早期設計，當時網絡 IO 是瓶頸
- Redis 使用 epoll + Reactor 模式，IO 多路復用效率更高

**epoll 優勢**：
- 相比 select/poll，epoll 只返回活躍的 fd，避免線性掃描
- 採用事件驅動，適合高併發連接場景

### 七、分布式鎖

**基本實現**：SET key value NX PX milliseconds

**關鍵問題**：
1. **過期時間如何確定？** 需大於業務執行時間，但過長會導致鎖釋放延遲。
2. **業務未執行完鎖過期？** 需要鎖續約（Watchdog），續約失敗需處理補償邏輯。
3. **加鎖超時怎麼辦？** 區分網絡超時和鎖被持有，後者需重試或快速失敗。
4. **減少競爭？** 分段鎖、樂觀鎖、隊列削峰。

**Redlock**：跨多個 Redis 實現的分布式鎖，解決單點故障問題，但爭議較多（時鐘漂移問題）。

### 八、緩存綜合應用

**性能優化策略**：
1. 緩存預熱：系統啟動時加載熱點數據
2. 結果緩存：服務調用結果本地緩存，注意失效同步問題
3. 多級緩存：本地緩存 → Redis → 數據庫
4. 緩存崩潰容錯：熔斷降級、快速失敗

**監控指標**：
- 緩存命中率
- 內存使用量
- QPS / 延遲
- 過期 key 數量

## 💡 重點摘要

- Redis 採用「惰性刪除 + 定期刪除」混合策略，平衡性能與內存回收
- LRU 適合時間局部性強的場景，LFU 適合熱點穩定的場景，需根據業務選擇淘汰策略
- 緩存模式無法完全解決一致性問題，需配合過期時間、延遲雙刪、分布式鎖等手段
- 穿透用布隆過濾器、擊穿用 Singleflight、雪崩用隨機過期時間和熔斷降級
- Redis 單線程模型基於 epoll + Reactor 模式，後期引入多線程處理網絡 IO
- 分布式鎖需考慮過期時間、續約、超時處理、競爭優化等問題
- 緩存設計需考慮崩潰容錯、多級緩存、預熱策略、監控告警
