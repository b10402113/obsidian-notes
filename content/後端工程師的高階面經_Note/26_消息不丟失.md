# 消息不丟失：生產者收到寫入成功響應後消息一定不會丟失嗎？

## 📝 課程概述

本單元深入探討 Kafka 消息隊列中消息丟失的各種場景與防範措施。從生產者發送、消息隊列存儲到消費者消費三個環節，系統性地建立確保消息不丟失的完整方案，並提供在 Kafka 上實現消息回查機制的亮點設計。

## 核心觀念與實作解析

### Kafka 主從同步與 ISR

在 Kafka 中，消息存儲於分區中，每個分區採用主從架構以避免單點故障。主分區與從分區分布在不同 broker 上，盡量做到一個 broker 只承載一個主分區，但可承載其他主分區的從分區，形成隔離保護。

**寫入語意與 acks 參數**

Kafka 通過 `acks` 參數讓生產者決定寫入語意，有三個取值：

- **acks = 0**：「fire and forget」模式，發送後即認為成功，不關心 broker 是否收到、持久化或完成主從同步。
- **acks = 1**：主分區寫入成功即返回成功響應。
- **acks = all**：主分區寫入成功且同步給所有 ISR 成員後才返回成功。

**ISR（In-Sync Replicas）**

ISR 指與主分區保持同步的所有從分區集合。若某從分區因網絡問題無法同步，會被移出 ISR。通過 `min.insync.replicas` 參數可配置 ISR 最少成員數量，當分區數不足時，`acks = all` 的發送會失敗。

### 消息丟失的各種場景

理解消息丟失需從生產者到消費者的完整鏈路分析：

**1. 生產者發送階段**

- `acks = 0` 時，生產者收到客戶端成功響應，但 broker 可能根本沒收到或處理出錯。
- 啟用批量發送且批次較大時，Kafka 客戶端可能連請求都未發送就崩潰。

**2. 主從同步階段**

- `acks = 1` 時，主分區寫入成功後立即崩潰，新選舉的主分區（來自從分區）缺少該消息。
- 允許 unclean 選舉時，若 ISR 為空，會選擇非 ISR 中的從分區作為主分區，該分區可能缺少部分數據。

**3. 刷盤階段**

消息寫入成功後可能仍在操作系統的 page cache 中，尚未刷入磁盤。Kafka 提供三個刷盤參數：

- `log.flush.interval.messages`：定量刷，達到指定消息數量強制刷盤。
- `log.flush.interval.ms`：定時刷，間隔指定毫秒刷盤。
- `log.flush.scheduler.interval.ms`：調度器檢查間隔。

記憶口訣：Kafka 要麼**定量刷**，要麼**定時刷**。

**4. 消費者提交階段**

異步消費場景下，消費者線程拿到消息就提交偏移量，但工作線程尚未處理或處理中宕機，導致消息「被提交但未消費」的丟失。

### 確保消息不丟失的完整方案

**發送方保證：本地消息表方案**

將分布式事務轉化為本地事務 + 補償機制：

1. 業務操作過程中，在本地消息表記錄待發消息，形成本地數據庫事務。
2. 嘗試立刻發送消息，成功則刪除消息或標記已發送。
3. 異步補發機制掃描本地消息表，找出超時未發送成功的消息補發。

關鍵設計要點：
- 事務提交後宕機，異步補發機制會找出消息補發。
- 消息發送成功但狀態未更新，會重複發送，需消費者冪等處理。
- 本地消息表增加重試間隔、重試次數控制字段。
- 最終補發失敗則告警，人工介入。

**消息隊列保證**

- 設置 `acks = all` 確保主從同步完成。
- 禁用 unclean 選舉，避免非 ISR 分區成為主分區。
- 根據業務需求調整刷盤參數（需權衡性能與可靠性）。

**消費者保證**

大多數情況無需額外處理，但異步消費需特別注意。可採用批量消費、批量提交確保異步消費不丟失消息。

### 亮點方案：在 Kafka 上支持消息回查機制

消息回查機制是兩階段提交的應用：先發準備請求，業務完成後發確認請求，消息中間件才將消息轉交消費者。若未收到確認請求，中間件回查業務方決定是否提交。

**整體流程設計**

1. 應用發送準備消息到 `look_back_msg` topic，包含業務 topic、消息體、業務類型、業務 ID、準備狀態、回查接口。
2. 回查中間件消費並存儲消息到數據庫。
3. 業務操作完成後發送提交消息（或回滾消息）。
4. 回查中間件查詢消息內容，轉發到業務 topic。

**亮點一：回查實現**

關鍵是回查中間件需知道如何回查應用代碼，設計支持 HTTP 和 RPC 兩種方式：

- **HTTP 回查**：業務方提供回查 URL，中間件發送 `POST` 請求帶 `biz_type` 和 `biz_id`，業務方返回提交或回滾狀態。
- **RPC 回查**：業務方實現回查接口，提供服務名，中間件利用 RPC 泛化調用發起調用。

**亮點二：數據存儲**

使用分區表、交替表或分庫分表存儲回查消息，保證高性能與高可靠。可按時間分區，歷史分區快速歸檔。

**亮點三：有序消息**

準備消息必須先於提交消息到達。解決方案：按業務 ID 計算哈希值，除以分區數量的餘數作為目標分區，確保同一業務的消息有序。

## 💡 重點摘要

- **消息丟失環節**：生產者發送、主從同步、刷盤、消費者提交四個環節都可能丟失消息，需針對性防範。
- **acks 參數選擇**：關鍵業務使用 `acks = all` 確保主從同步完成，禁用 unclean 選舉。
- **本地消息表**：將分布式事務轉化為本地事務 + 補償機制，確保發送方一定發出消息。
- **消息回查機制**：借鑒兩階段提交，在 Kafka 上實現支持 HTTP/RPC 回查的可靠消息方案。
- **消費者冪等**：重試機制必然導致重複消費，消費者必須設計為冪等。
