# 微服務高可用治理方案

## 📝 課程概述
本單元探討如何為微服務應用設計全面的高可用方案。從 SLA 指標出發，深入解析容錯設計、故障隔離、監控告警與變更規範四大核心策略，並提供完整的面試話術與實踐案例，幫助工程師在面試中展現系統性思維與解決問題的能力。

## 核心觀念與實作解析

### 高可用的衡量標準：SLA

可用性通常以 **SLA (Service Level Agreement)** 來衡量，常以「幾個九」表示。三個九代表系統在一年內正常服務時間超過 99.9%，約當全年不可用時間不超過 8.76 小時。四個九則將不可用時間壓縮至約 53 分鐘內。

高可用的門檻一般認定為三個九，部分場景要求四個九。與高併發、大數據經驗相比，高可用是所有工程師都能在自己維護的系統中實踐的核心能力，無需依賴大廠核心部門的特殊場景。

### 實現高可用的四大核心策略

#### 1. 容錯 (Design for Failure)

容錯的核心思維是「湊合用」—即便部分組件故障，系統仍能提供服務。潛在故障點包括：
- **服務本身**：透過限流、熔斷、降級等機制保護
- **依賴的服務**：設計容錯機制，避免連鎖故障
- **軟體基礎設施**：使用高可用方案（如 Redis Cluster 取代單機 Redis）
- **硬體基礎設施**：依賴雲廠商或運維團隊保障

關鍵在於當 Redis 等中間件崩潰時，透過限流保護資料庫，確保系統整體仍能運作。

#### 2. 限制故障影響範圍

隔離是最佳策略。將複雜系統拆分為獨立服務，服務內部再細分模組、核心與非核心服務，降低相互影響。

實務上面臨兩大難點：
- **服務互相依賴**：部分源自業務複雜度，部分源自設計不合理。可透過改進設計降低依賴，但無法完全消除
- **共享基礎設施**：理論上可為每個服務提供獨立基礎設施，但成本考量下多數公司仍選擇共享，導致單一組件故障牽連多個服務

#### 3. 快速發現與快速修復

**快速發現**依賴完備的觀測與告警系統：
- 觀測範圍涵蓋服務本身、基礎設施、第三方依賴
- 核心鏈路上的依賴需全方位監控
- 告警設置需合理，「沒有告警的觀測是沒有靈魂的」

**快速修復**本質是組織建設問題：
- 需安排 24 小時值班機制
- 值班人員需了解專案細節
- 依賴自動化故障處理機制，而非個人自覺

#### 4. 規範變更流程

變更是線上故障的主要來源。規範流程包括：
- 任何變更需經過 Review
- 做好回退準備
- 禁止未測試直接發布

這點與快速修復一樣，屬於組織問題而非純技術問題。

### 面試準備策略

面試前需準備「從前端到後端全方位的高可用方案」，重點思考：
1. 面向前端用戶的介面是否有防禦措施（如限流）
2. 第三方組件（Redis、MySQL、Kafka）是否啟用高可用方案
3. 第三方組件崩潰時的容錯機制
4. 服務的負載均衡算法、熔斷、降級、限流、超時控制
5. 上線流程、配置變更流程等規範

### 面試敘事框架

完整的面試敘事可拆解為五個步驟：

#### Step 1：發現問題

> 某某業務是公司核心業務，需保證高可用。入職初期系統可用性較低，首月即遭遇嚴重線上故障：其他業務組上線功能帶來大量 Redis 大物件操作，導致 Redis 響應緩慢，核心服務超時。
>
> 經調研歸納三大原因：缺乏監控告警、缺乏服務治理、缺乏合理的變更流程。

#### Step 2：計劃方案

展示有計畫的解決方案：
1. 引入全方位監控與告警
2. 引入服務治理措施
3. 為第三方依賴引入高可用方案
4. 拆分核心與非核心業務的共同依賴
5. 規範變更流程

若公司基礎設施完善，可加入全鏈路壓測、混沌工程、故障演練等進階方案。

#### Step 3：落地實施

補充細節並適度揭露困難：
- 監控需逐一鏈路排查，業務與第三方依賴皆需覆蓋
- 服務治理涵蓋限流、熔斷等多種方案
- 高可用方案需資金投入（如 Redis Cluster 需更多實例）
- 核心業務逐步啟用獨立集群，老服務維持現狀
- 變更流程以「建議」方式推動

適度揭露困難能增強說服力，展現實務經驗。

#### Step 4：取得效果

量化成果：
> 經改進後，服務可用性從不足兩個九提升至三個九。

補充說明超出影響力範圍的部分：
> 依賴同事提供的服務可用性仍較差，需推動整體提升。整個系統要做到四個九需全公司技術人員共同努力。

#### Step 5：後續改進

針對既有方案缺點提出改進：
> 老服務仍共享部分基礎設施，需進一步解耦。例如讓全部服務使用自組的資料庫實例，避免受其他團隊影響。

### 亮點方案

#### 異步與解耦

核心原則：「能異步執行的絕對異步執行，能解耦的必須解耦」。

**設計思維**：多做多錯，少做少錯，不做不錯。

實踐方式：
- 將核心業務邏輯拆分為同步執行的關鍵步驟與可異步執行的非關鍵步驟
- 同步步驟成功後發送訊息至訊息佇列
- 異步步驟透過重試機制確保最終一致性

範例場景：創建訂單時，訂單創建與支付需同步執行，但發送通知郵件、增加積分可異步處理。

#### 自動故障處理

達成三個九後，進一步提升需降低事故發生率或提高反應速度。人員無法 24 小時緊繃待命，自動化機制至關重要。

**範例：微服務集群自動擴容**

設計方案：
- 允許不同業務方設置不同擴容條件
- 例如 CPU 使用率超過 90% 並持續一段時間，觸發自動擴容
- 強調「集群所有節點」都超過指標才擴容，避免單一節點高負載誤判

其他常見方案：
- **自動修復數據**：定時任務比對業務數據，發現不一致時告警並觸發修復
- **自動補發訊息**：比對業務數據，發現訊息未發送時告警並觸發補發

## 💡 重點摘要

- 高可用是所有工程師都能實踐的核心能力，以 SLA 三個九為基本門檻，四大策略為容錯、限制故障範圍、快速發現修復、規範變更流程
- 容錯設計的核心是「湊合用」思維，確保部分組件故障時系統整體仍能運作，關鍵在於對第三方依賴設計容錯機制
- 面試敘事採用「發現問題 → 計劃方案 → 落地實施 → 取得效果 → 後續改進」框架，展現系統性思維與解決問題能力
- 異步與解耦是提升可用性的重要手段，核心原則是「能異步就異步，能解耦就解耦」
- 自動故障處理機制是從三個九邁向四個九的關鍵，包括自動擴容、自動修復數據、自動補發訊息等
