# Kafka 性能優化實戰指南

## 📝 課程概述
本單元探討如何在實際業務中保證 Kafka 高性能，從生產者、Broker 到消費者三個維度進行優化。掌握消息從生產到消費完整生命週期的性能調優方法，是後端工程師面對高併發場景的必備技能。

## 核心觀念與實作解析

### 壓縮算法選擇原則

選擇壓縮算法需在 **壓縮比** 與 **壓縮速率** 之間權衡：

- **壓縮比高**：節省網絡帶寬與磁盤存儲空間
- **壓縮速率高**：提升吞吐量

一般而言，壓縮比越高，壓縮速率越低，兩者呈反比關係。實際選擇應根據業務場景偏向哪一邊，並以性能測試結果為準，而非僅依賴理論分析。

---

### 操作系統交換區（Swap）基礎

現代操作系統支持交換區（Swap），當物理內存不足時，會將部分內存頁淘汰到磁盤上。

**關鍵觀念**：
- Swap 可視為「虛擬內存」
- 觸發交換會導致性能顯著下降
- Linux 參數 `vm.swappiness` 控制使用交換區的積極性（默認值 60）
- **追求性能調小 `vm.swappiness`** 是中間件優化的核心原則

---

### 生產者優化策略

#### 1. 優化 acks 參數

根據業務需求調整 acks 值：

| 需求 | acks 值 | 說明 |
|------|---------|------|
| 追求性能 | 0 | 不等待確認，性能最佳 |
| 平衡選擇 | 1 | 等待 leader 確認 |
| 追求不丟消息 | all | 等待所有副本確認 |

**實戰案例**：某高併發接口原使用 `acks=all`，但業務對消息可靠性要求不高，調整為 `acks=0` 後，響應時間顯著下降，客戶端超時問題大幅減少。

#### 2. 優化批次（Batch）

**批次優化的好處**：
- 生產者發送速率更快
- Broker 處理同樣數量消息時，批次越大性能越好

**相關參數**：
- `linger.ms`：湊夠一個批次的最大等待時間
- `batch.size`：一個批次最大字節數

**調優方向**：調大批次

**注意事項**：
- 批次過大可能增加數據丟失風險
- 當瓶頸轉為 Broker 處理能力時，再調大批次無效
- 最佳策略是通過壓測確定合適的批次大小

**發送者阻塞的診斷邏輯**：
- 若是發送速率問題 → 調大批次（調大緩衝區只是治標）
- 若是緩衝池太小 → 調大緩衝池
- 難以區分時 → 先調大批次測試，再調整緩衝池

#### 3. 啟用壓縮

Kafka 默認不啟用壓縮。啟用壓縮可進一步提升吞吐量。

**推薦算法**：LZ4（經實測吞吐量表現最佳）

### Broker 優化策略

#### 1. 優化 Swap

**調整 `vm.swappiness`**：
- 調整為 10：充分利用內存
- 調整為 1：某些 Linux 版本表示進行最少交換，但不禁用

**為何不完全禁用 Swap？**
物理內存有限，直接禁用容易遇到內存不足問題。優化內存使用而非完全禁用，即使物理內存不夠，使用交換區也比系統不可用好。

#### 2. 優化網絡讀寫緩衝區

Kafka 是網絡 IO 頻繁的應用，調整以下參數可提升性能：

| 參數 | 說明 | 建議值 |
|------|------|--------|
| `net.core.rmem_default` / `net.core.wmem_default` | Socket 默認讀寫緩衝區 | 128KB |
| `net.core.rmem_max` / `net.core.wmem_max` | Socket 最大讀寫緩衝區 | 2MB |
| `net.ipv4.tcp_wmem` / `net.ipv4.tcp_rmem` | TCP 讀寫緩衝區（最小/默認/最大） | 4KB / 64KB / 2MB |

**核心原則**：調大讀寫緩衝區，實際數值需根據 Broker 硬件資源確定。

#### 3. 優化磁盤 IO

**兩個優化方向**：

1. **使用 XFS 文件系統**
   - 相比 EXT4，XFS 性能更好
   - 同等條件下性能提升約 5%

2. **禁用 atime**
   - atime 記錄文件最後訪問時間
   - Kafka 用不上此功能，禁用可減少磁盤 IO

#### 4. 優化主從同步

**相關參數**：

| 參數 | 說明 | 優化方向 |
|------|------|----------|
| `num.replica.fetchers` | 從分區拉取數據的線程數 | 調大（如設為 3） |
| `replica.fetch.min.bytes` | 同步數據最小字節 | 調大，避免小批量同步 |
| `replica.fetch.max.bytes` | 同步數據最大字節 | 調大（如 5MB），不小於 `message.max.byte` |
| `replica.fetch.wait.max.ms` | 從分區最大等待時間 | 配合 `replica.fetch.max.bytes` 調大 |

**核心原則**：都調大，讓從分區一批次同步盡可能多的數據。

**限制**：調大到一定程度後，瓶頸會轉為從分區處理能力，或超過消息併發量則無意義。

**延伸應用**：此為典型的「批量拉數據模型」，可應用於業務層面的批量拉數據場景。

#### 5. 優化 JVM

Kafka 運行在 JVM 上，優化 Java 性能的措施同樣有效。

**Full GC 的影響**：
1. 發送者若設置 `acks=1` 或 `all`，會被阻塞，吞吐量下降
2. Full GC 時間過長可能導致：
   - 主分區被認為崩潰，觸發主從選舉
   - 從分區被移出 ISR，影響 `acks=all` 的發送者

**優化方向**：
- 調大 JVM 堆內存
- 堆內存很大時，啟用 G1 垃圾回收器

**實戰案例**：某 Kafka 集群堆內存 8G 但使用 CMS 垃圾回收器，Full GC 停頓時間長。切換到 G1 回收器後，垃圾回收頻率和停頓時間都下降了。

---

### 中間件優化通用思路

1. **操作系統層面**：調整 swap、TCP、IO 相關參數
2. **中間件本體**：調整刷盤參數、主從同步、JVM 垃圾回收
3. **客戶端參數**：調整生產者、消費者的相關配置

此套路適用於絕大多數中間件優化。

---

## 💡 重點摘要

- 選擇壓縮算法需在壓縮比與壓縮速率之間權衡，實際選擇應以性能測試為準
- 生產者優化三大措施：調整 acks 參數、調大批次大小、啟用壓縮（推薦 LZ4）
- Broker 優化需從操作系統層面入手：調整 swap 參數、網絡緩衝區、磁盤 IO、主從同步、JVM 配置
- 追求性能的應用應調小 `vm.swappiness`，充分利用物理內存，避免頻繁觸發交換
- 中間件優化通用套路：操作系統參數 → 中間件本體配置 → 客戶端參數
