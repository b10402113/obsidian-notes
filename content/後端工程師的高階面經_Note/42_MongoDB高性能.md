# MongoDB 高性能查詢優化

## 📝 課程概述

本單元探討 MongoDB 查詢性能優化的核心方法，從查詢執行過程、索引設計原則到六大優化方案，幫助開發者在面試與實戰中掌握高性能數據庫調優的關鍵技巧。理解這些優化手段需要對 MongoDB 底層原理有透徹認識。

## 核心觀念與實作解析

### MongoDB 查詢過程

MongoDB 在分片架構下，查詢需要準確定位數據所在位置。這與分庫分表的查詢邏輯相似：最重要的步驟是計算目標數據可能在哪個分片上。

**mongos 的關鍵角色**：
- mongos 實例負責路由查詢到目標分片
- 合併各分片返回的結果集
- 處理分頁查詢時的排序與篩選

當無法精確計算目標位置時，MongoDB 會考慮廣播查詢，這會帶來性能開銷。

### ESR 索引設計規則

ESR 代表索引設計的三個核心要素順序：

| 順序 | 含義 | 說明 |
|------|------|------|
| **E** (Equality) | 等值查詢 | 精確匹配條件 |
| **S** (Sort) | 排序操作 | ORDER BY 字段 |
| **R** (Range) | 範圍查詢 | >, <, BETWEEN 等 |

**設計原則**：索引字段應按 E → S → R 順序排列。

**範例**：若查詢用 A 等值查找、B 排序、C 範圍查詢，索引應設計為 `ABC`。若設計成 `BAC` 則違背 ESR 規則。

**允許的變形**：
- EESR：兩個等值列
- ESSR：兩個排序列
- ERR：多個範圍列

關鍵在於保持相對順序不變。

### 優化方案一：覆蓋索引

覆蓋索引指查詢所需的所有字段都包含在索引中，無需回表讀取完整文檔。

**實作方式**：
- 使用 `projection` 指定查詢字段
- 確保投影字段均為索引字段

**實戰案例**：早期業務查詢直接加載整個文檔，後續發現大部分調用者只需少數字段。新增只返回必要字段的查詢接口後，性能提升至少 30%。

**延伸思考**：不僅查詢，更新操作也應只更新必要字段，避免前端傳遞整個文檔造成不必要的開銷。

### 優化方案二：排序優化

**問題核心**：若無法利用索引排序，MongoDB 必須在內存中排序，疊加分頁查詢時性能急劇下降。

**最壞情況**：`skip(100000).limit(100)` 可能需要將所有文檔加載到內存排序，再定位目標數據。

**兩種優化思路**：

1. **利用索引排序**
   - 新建適當索引
   - 修改查詢條件匹配索引

2. **禁止跨頁查詢**（借鑒分庫分表方案）
   - 每次查詢攜帶上一頁的排序字段極值
   - 例如：依 `create_time` 倒序，查詢條件帶入 `WHERE create_time <= $last_min_create_time`

**面試延伸**：MongoDB 分頁問題與關係型數據庫、分庫分表場景相似，可橫向對比討論。

### 優化方案三：增加 mongos 數量

**為什麼 mongos 是瓶頸**：
- 分片查詢需經 mongos 路由與結果合併
- 分頁查詢時，mongos 需收集各分片結果再排序
- 可能面臨 CPU、內存或網絡帶寬瓶頸

**優化策略**：
- 監控查詢性能，排查 mongos 瓶頸
- 增加 mongos 實例數量
- **獨立部署**：讓 mongos 獨享 CPU 和內存資源
- **業務隔離**：核心服務使用獨立 mongos 實例或獨立 MongoDB 集群

### 優化方案四：拆分大文檔

大文檔（字段多、特定字段特別大）會嚴重影響 MongoDB 性能。

**拆分策略**：

| 策略 | 說明 |
|------|------|
| 按訪問頻率拆分 | 頻繁訪問字段與不頻繁字段分離 |
| 按字段大小拆分 | 小字段與大字段分離 |

**實戰拆分三步驟**：
1. 訪問頻繁的小字段 → 一個文檔
2. 訪問不頻繁的大字段 → 另一個文檔
3. 剩餘字段 → 第三個文檔

**權衡**：
- 優點：大部分查詢只需第一個文檔
- 缺點：需要完整文檔時需查詢三次再合併

**最佳實踐**：一開始就約束文檔大小，拆分終究是下策。

### 優化方案五：嵌入文檔

當兩個文檔 A、B 有緊密關聯關係時，可將 B 文檔嵌入 A 文檔，減少查詢次數。

**適用場景**：
- A 與 B 一對一映射
- 業務查詢經常需要同時獲取 A 和 B

**懶惰更新策略**：
1. 查詢 A 文檔
2. 若 A 尚未嵌入 B，則查詢 B 並嵌入 A
3. 更新 A 時使用樂觀鎖（條件中加入「A 不包含 B 文檔」）

**常見應用：冗餘字段**：
- 在其他文檔中冗餘用戶暱稱、頭像等字段
- 避免二次查詢用戶文檔
- 需容忍數據一致性问题

### 優化方案六：操作系統層面優化

**內存優化**：
- 保證足夠物理內存放全部索引
- 索引命中性能預估基於索引常駐內存

**Swap 優化**：
- 避免 MongoDB 觸發交換
- 調小 `vm.swappiness` 參數

**面試準備建議**：
- 收集公司內 MongoDB 慢查詢案例
- 準備索引優化實戰經驗
- 了解 MongoDB 參數調整
- 掌握平均查詢時間、99 線、999 線數據

**橫向對比話術**：
- MySQL 索引優化 → 提起 MongoDB 索引
- 分庫分表分頁 → 提起 mongos
- Elasticsearch 分片 → 提起 MongoDB 分片

## 💡 重點摘要

- ESR 規則是索引設計的核心原則，字段順序應遵循等值 → 排序 → 範圍
- 覆蓋索引可避免回表，使用 projection 指定字段是基本優化手段
- 排序優化分兩路：利用索引排序、或改用游標式分頁避免大偏移量
- mongos 是分片架構的查詢瓶頸，可通過增加實例數量與業務隔離優化
- 大文檔拆分與嵌入文檔是兩種相反策略，需根據業務場景選擇
- 操作系統層面重點在內存與 Swap 優化，確保索引常駐內存
