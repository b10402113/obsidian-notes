# 緩存一致性問題：高並發服務的解決方案

## 📝 課程概述
本單元深入探討緩存一致性問題的根源與解決方案。從操作部分失敗與並發操作兩個維度分析數據不一致的成因，並提供消息隊列、版本號、分布式鎖等實務解決方案，幫助你在面試中展現對緩存一致性的深度理解。

## 核心觀念與實作解析

### Double-Check 模式基礎

Double-check 是並發編程中兼顧安全性與性能的經典模式，核心思路為「檢查、加鎖、檢查」。基本流程：先加讀鎖檢測數據是否存在，若存在則直接返回；否則釋放讀鎖、加寫鎖、再次檢查後執行操作。

**常見變種：**
- 第一次檢查不加鎖（適用於分布式鎖場景）
- 用原子操作取代讀鎖（前提是原子操作能完成檢查）

這是性能優化的重要手段，可納入整體並發優化方案中。

### 數據不一致的兩大根源

#### 根源一：操作部分失敗

這是最難解決的問題。以最簡單的模型為例，更新數據庫和更新緩存必須「要麼都成功，要麼都失敗」，這本質上是分布式事務問題。

**關鍵認知：**
- 緩存中間件（如 Redis）不支持分布式事務
- 在徹底解決操作部分失敗問題之前，只能盡可能避免不一致並儘快達成一致
- 可採取的措施：重試失敗操作、數據自動校驗與修復

#### 根源二：並發操作

多個線程同時更新數據庫和緩存時，可能出現「先更新數據庫的線程後更新緩存」的情況，導致數據不一致。

**解決方向：** 確保同一時刻只有一個線程在更新數據庫和緩存。在分布式環境下，即便有數百個實例，也只能有一個實例上的一個線程在更新數據。

### 解決方案詳解

#### 方案一：消息隊列

將更新請求發送到消息隊列排隊，確保針對同一業務的更新請求保持有序。消費者依次取出消息後更新數據庫和緩存。

**要點：**
- 同一業務的消息必須有序，否則更新會出錯
- 消費者更新失敗後可多次重試，對業務影響小
- 這是追求最終一致性的方案，強一致性場景不適用

**變種：** 先更新數據庫，再發送消息讓消費者更新緩存。但消費者若依賴消息中的數據更新緩存，仍會有並發問題。建議將消息當作觸發器，查詢數據庫數據來執行更新。

#### 方案二：版本號

每次更新版本號加一，低版本數據不能覆蓋高版本數據。

**實施方式：**
- 在數據庫中增加版本字段
- 更新 Redis 時使用 Lua 腳本，先檢測緩存版本號再執行更新
- 可用更新時間替代版本號

這個方案能有效解決 Cache Aside 等模式中的數據不一致問題，缺點是版本號本身需要維護。

#### 方案三：多級緩存更新順序

當架構為本地緩存 + Redis + 數據庫時，需考慮更新順序。

**建議順序：** 數據庫 → 本地緩存 → Redis

**先更新本地緩存的理由：**
1. 更新本地緩存幾乎不會失敗
2. 查詢時先查本地緩存，先更新可確保用戶拿到最新數據
3. 即便後續 Redis 更新失敗，也不會查到不一致數據

但需注意：引入多級緩存後，數據不一致的概率會更大。

### 亮點方案：一致性哈希與緩存結合

通過一致性哈希負載均衡算法，確保某個 key 只有一個服務端節點處理。

**關鍵細節：**
- 更新緩存時需使用 singleflight 模式
- 可做到同一 key 落在同一節點，且該節點最多只有一個線程更新數據
- 多個更新請求會輪流更新數據庫和緩存

**節點上下線處理：**
- 節點下線：新請求自動打到其他節點，只有一個節點處理某 key
- 節點上線（擴容）：短期內會有兩個節點處理寫請求，可能不一致
- 解決方案：新節點上線的頭幾秒不讀寫緩存，等待老節點請求自然返回

### 亮點方案：分布式鎖應用

#### 思路一：先本地事務，後分布式鎖

**寫請求流程：** 執行本地事務 → 事務提交後加分布式鎖 → 刪除緩存 → 釋放分布式鎖

**讀請求流程：** 讀緩存 → 未命中則加分布式鎖 → 從數據庫加載數據回寫緩存 → 釋放鎖

**優化：** 應用 double-check 機制，讀請求加上分布式鎖後再次讀緩存，檢查是否有其他線程已加載數據。

**特點：** 解決並發更新問題，但無法解決操作部分失敗問題。

#### 思路二：先刪除緩存，再提交事務

**流程：** 開啟本地事務 → 執行事務操作 → 獲取分布式鎖 → 刪除緩存 → 提交事務 → 釋放分布式鎖

**讀請求：** 緩存未命中回查時，仍需先加分布式鎖。

**失敗場景分析：**
- 刪除失敗：事務不提交，數據一致
- 刪除成功、事務提交失敗：數據一致，只是多刪一次緩存

**強一致性的條件：**
1. 分布式鎖本身必須可靠（一個線程拿鎖，其他線程絕對拿不到同一把鎖）
2. 刪除緩存超時時持續重試直到確認刪除成功

**缺點：** 本地事務容易超時（分布式鎖被搶占、網絡不穩定導致無法刪除緩存）

**緩解方案：** 先加分布式鎖 → 開啟本地事務 → 刪除緩存 → 提交事務 → 釋放分布式鎖。代價是分布式鎖持有時間變長。

## 💡 重點摘要

- 數據不一致有兩大根源：操作部分失敗（難以解決，本質是分布式事務問題）與並發操作（可通過多種方案解決）
- Double-check 模式是並發優化的重要手段，核心是「檢查、加鎖、檢查」三步驟
- 消息隊列方案將更新請求排隊，追求最終一致性，適合可異步更新場景
- 版本號方案通過版本比較防止低版本覆蓋高版本，有效解決並發更新問題
- 分布式鎖的「先刪除緩存再提交事務」思路可無限接近強一致性，但依賴鎖的可靠性且存在事務超時風險
