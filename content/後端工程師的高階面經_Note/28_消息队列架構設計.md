# 消息佇列架構設計

## 📝 課程概述
本單元探討面試中高難度的系統設計題目：如何從零設計一個消息佇列。課程以 MySQL 為基礎實作案例，深入解析 Topic、Partition、Broker、消費者組等核心概念的設計原理與權衡，幫助你建立完整的消息佇列架構思維。

## 核心觀念與實作解析

### 為什麼需要 Topic 與分區設計？

消息佇列的基本形態是發布-訂閱模式。現代消息佇列（如 Kafka）都有四個核心概念：生產者、消費者、Broker 和 Topic。

**Topic 的必要性**：Topic 代表不同的業務，是天然的业务隔離边界。若所有 Topic 共用一張表，難以應付大數據與高併發場景，且不同業務會相互影響。

**分區的必要性**：若 Topic 內部不劃分分區，所有生產者需競爭同一把鎖才能寫入，消費者也要競爭同一把鎖才能讀取，效能極差。引入分區設計可解決併發競爭問題。

以 MySQL 實作為例：
- 一個 Topic 對應一個邏輯表
- 分區對應分庫分表後的物理表
- 例如 `create_order` Topic 有 3 個分區，則對應 `create_order_0`、`create_order_1`、`create_order_2` 三張物理表
- 每張表使用自增主鍵，對應 Kafka 中的偏移量（offset）

### Broker 與消息存儲設計

**分散式存儲原則**：同一 Topic 的不同分區應盡量分散在不同 Broker 上存儲。這樣即便某個 Broker 崩潰，該 Topic 也最多只有一個分區受影響。

以 MySQL 實作：
- 分區不僅要分表，還要分庫（分數據源）
- 不同分區存放在不同的主從集群上
- 主從集群本身就達成類似 Kafka 的副本效果，但沒有 ISR 概念
- 使用 MySQL 的主從機制可免去管理主從選舉的問題，大幅降低落地難度

### 生產者設計：推模型

**推 vs 拉模型**：生產者應採用推模型，主動推送消息到 Broker。因為消息產生速率完全與 Broker 無關，讓 Broker 主動拉取不好控制拉的頻率和數量。

**效能優化策略**：

1. **批量發送**：生產者可湊夠一個批次後再發送，批次大小由生產者控制。需設置兜底措施，避免消息長時間停留在生產者記憶體中造成丟失。Kafka 的 `linger.ms` 參數即控制最終等待時間。

2. **直接插入消息**：追求極致效能時，可讓生產者直接連接資料庫，省略一次網路通信。生產者引入本地依賴，根據 Topic、分區找到對應資料庫配置，執行 INSERT 語句插入消息。

### 消費者設計：拉模型

**消費者組概念**：不同業務方可能消費同一 Topic 的消息，需引入消費者組概念。一個業務方是一個消費者組，組內可有多個消費者。

**拉模型優勢**：消費者才知道自己的消費速率，使用拉模型可按需拉取。例如每 1 秒從消息佇列拉取 50 條消息。

**分區與消費者對應關係**：每個分區對於一個消費者組來說，只能有一個消費者讀取消息。但一個消費者可消費多個分區。

### 偏移量記錄機制

以 MySQL 實作，需要額外的表記錄消費進度：
- 表名如 `create_order_consumers`
- 三個關鍵欄位：消費者組名稱、分區、已消費偏移量

**指定偏移量消費**：消費者可從指定偏移量重新消費。例如已消費到偏移量 1000，因業務問題需從偏移量 100 重試，只需更新 `committed_offset` 為 100。

```sql
UPDATE create_order_consumers SET committed_offset=100
WHERE partition = 2 AND consumer_group = 'test'
```

**效能優化**：使用 Redis 記錄消費偏移量，異步刷新到資料庫。需注意 Redis 宕機可能導致偏移量未同步，消費者需做到冪等處理。

### 延遲消息實現

在消息表增加 `send_time` 欄位記錄預期發送時間：

```sql
SELECT * FROM some_topic
WHERE send_time <= now()
AND send_time > $last_batch_send_max_time
```

**同時發送問題**：若使用 LIMIT，可能跳過或重複消費相同時間戳的消息。解決方案：不依賴資料庫計算 LIMIT，在應用層處理。讀取時檢查第 50 條之後的資料，若 `send_time` 相同則加入當前批次。

### 適用場景

基於 MySQL 實現消息佇列的場景：ToB 業務中，客戶要求本地部署但不具備維護專業消息佇列的技術能力。典型例子如私有化部署的即時通訊工具。

## 💡 重點摘要
- Topic 與分區設計解決業務隔離與併發競爭問題，一個 Topic 對應一個邏輯表，一個分區對應一個物理表
- 同一 Topic 的不同分區應分散在不同主從集群上，提高可用性
- 生產者使用推模型，可透過批量發送、直連資料庫優化效能
- 消費者使用拉模型，按需消費，需記錄消費偏移量
- 延遲消息可透過 `send_time` 欄位實現，需注意同時發送問題
