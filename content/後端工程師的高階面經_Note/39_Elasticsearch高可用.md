# Elasticsearch 高可用架构設計

## 📝 課程概述
本單元探討如何保障 Elasticsearch 的高可用性,從基礎架構認識到進階實踐方案。透過理解節點角色、寫入機制與分片設計,結合限流、消息隊列削峰、協調節點保護與雙集群等策略,建立完整的容錯思維,為面試與實戰做好準備。

## 核心觀念與實作解析

### Elasticsearch 節點角色

Elasticsearch 的節點可以扮演多種角色,主要分為三類:

- **候選主節點 (Master-eligible Node)**: 可被選舉為主節點,負責集群管理(如創建索引)。另有一種變體為僅投票節點 (Voting-only Node),只參與選舉但不會被選為主節點。
- **協調節點 (Coordinating Node)**: 負責協調請求處理流程。接收查詢請求後確定數據節點位置,讓數據節點執行查詢,最後合併結果返回。大多數節點都會兼任此角色。
- **數據節點 (Data Node)**: 存儲實際數據,執行查詢並返回結果。可進一步區分為熱數據節點 (Hot)、暖數據節點 (Warm)、冷數據節點 (Cold),根據數據熱度分層存儲。

**節點角色設置原則**: 資源充足時專款專用(單一角色),資源有限時可兼任。兼任可能引發性能問題,追求高性能高可用時建議節點只扮演單一角色。

### Elasticsearch 寫入數據流程

寫入過程分為三個階段:

1. **Buffer 寫入**: 文档首先寫入 Elasticsearch 自身的 Buffer
2. **Refresh 到 Page Cache**: 定時刷新(默認 1 秒),此時產生段 (Segment),文檔至此才可被搜索,因此 Elasticsearch 是近實時系統
3. **Flush 到磁盤**: 刷新到磁盤並同步記錄 Commit Point

**段合併機制**: 持續寫入會產生大量段,每個段消耗 CPU、內存和文件句柄。合併過程需確保不影響已有查詢:
- 已有段保持不動
- 創建新段,將有效數據寫入(標記刪除的文檔不寫入)
- 透過新的 Commit Point 告知查詢使用新段
- 待舊查詢結束後刪除舊段

**Translog 機制**: 類似 MySQL 的 redo log,用於宕機恢復。Translog 固定間隔刷新到磁盤(默認 5 秒),採用順序寫(只追加)保證高效率。最差情況下可能丟失 5 秒數據。

### Elasticsearch 索引與分片架構

**概念對照**:
- 索引 = 邏輯表
- 分片 = 分庫分表
- 分片主從結構 = 分庫分表的主從架構

每個分片都有主從結構,Elasticsearch 會盡量將分片分散在不同節點上(類似 Kafka 將分區分散在不同 broker),以最小化節點崩潰的影響範圍。主分片崩潰後,由主節點選擇新的主分片,機制類似 Redis Sentinel。

### 提高可用性的實踐方案

#### 方案一:限流保護節點

**實施途徑**:
1. **Elasticsearch 插件機制**: 開發自定義限流插件,結合內存使用率和 CPU 使用率設計限流策略
2. **網關/代理**: 在 Elasticsearch 前部署網關(如極限網關)進行熔斷、限流、降級
3. **客戶端限流**: 各業務方限制查詢頻率,最易落地

**核心觀點**: 限流只是治標,經常觸發限流或有性能問題時應考慮擴容。

#### 方案二:消息隊列削峰

在業務方與 Elasticsearch 間加入消息隊列:
- 業務方只寫數據庫後立即返回
- 監聽 binlog 生成消息到 Kafka
- Elasticsearch 根據自身負載調整消費速率

**進階:降級策略**: 區分核心數據消費者與非核心數據消費者,當 Elasticsearch 性能下降時停止非核心消費者。極端情況下(大促/秒殺)可完全停掉數據同步,僅支持查詢。

#### 方案三:保護協調節點

協調節點類似分庫分表代理,負責分發請求和處理結果集。大請求(如命中十個分片且每個返回數萬條數據)可能導致 CPU 100% 或 OOM。

**保護策略**:
1. **部署純粹協調節點**: 專門部署只扮演協調節點角色的節點
2. **隔離策略**: 客戶端判斷請求大小,大請求發送到純粹協調節點,普通請求發送到兼任節點
3. **單一角色原則**: 資源充足時所有節點只扮演單一角色,提升可用性與性能

#### 方案四:雙集群

**付費方案**: 使用 CCR (Cross-Cluster Replication) 跨集群複製

**自建方案**:
- A、B 兩個集群
- 寫入消息隊列後由兩個消費者分別寫入兩個集群
- 查詢優先使用 A 集群,故障時切換到 B 集群

**切換機制**:
- **客戶端切換**: 封裝 Elasticsearch 客戶端,監控響應時間和超時,自動切換
- **DNS 切換**: 正常情況 DNS 解析返回集群 A 的 IP,容災切換時返回集群 B 的地址

### 面試準備要點

**面試前需收集的信息**:
- 公司是否使用 Elasticsearch?解決什麼問題?
- 性能表現:讀寫流量、存儲數據量
- 索引規模:分片數量、確定分片數量的依據
- 可用性保障措施:是否使用 Elasticsearch 網關?
- 故障經歷:問題類型與解決方案

**常見面試題**:
- 為什麼說 Elasticsearch 是近實時的?
- Elasticsearch 的 flush 和 refresh 分別是什麼?
- Elasticsearch 的寫入過程是怎樣的?

**答題思路**:
1. 從分片主從結構切入(基本可用性保障)
2. 補充 Translog 機制(數據持久性)
3. 引導至高可用優化方案(展示實戰經驗)

## 💡 重點摘要

- Elasticsearch 高可用的核心是分片主從結構,主分片崩潰後由主節點選出新主分片
- 寫入流程透過 Buffer → Page Cache → 磁盤的三階段,配合 Translog 機制降低數據丟失風險(最差 5 秒)
- 段合併透過 Commit Point 機制確保查詢不受影響,類似數據遷移的平滑切換
- 限流保護、消息隊列削峰、協調節點隔離、雙集群是四個遞進的可用性優化方案
- 節點角色專款專用、單一角色原則是追求高性能高可用的最佳實踐
