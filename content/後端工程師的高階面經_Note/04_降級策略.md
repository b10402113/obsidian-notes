# 降級策略：高可用架構的資源調配藝術

## 📝 課程概述

本單元探討微服務架構中的降級機制，說明如何在系統資源不足時，透過暫停次要服務或提供有損服務來保障核心業務。降級與熔斷、限流並列為三大可用性保障措施，是構建高可用系統的必備技能。

## 核心觀念與實作解析

### 什麼是降級？

降級的核心概念可以用一句話概括：「湊合過唄，還能離咋的。」當系統資源不足以支撐所有服務時，選擇性地暫停或簡化部分服務，將資源留給更重要的業務。

典型的應用場景是電商大促期間，平台會關閉退款服務。這樣做有兩個好處：
1. 騰出服務器資源給訂單、支付等核心服務
2. 減少對公共組件的壓力（如數據庫寫入壓力）

### 降級與熔斷的關係

降級與熔斷非常相似，都需要考慮兩個關鍵問題：
- 如何判定服務健康（降級中則是判定是否需要降級）
- 降級/熔斷後如何恢復（需考慮抖動問題）

**兩者的選擇原則**：
- 優先考慮降級（提供有損服務）
- 寫服務通常無法降級，只能熔斷
- 若希望系統負載快速降低，熔斷優於降級

### 降級的分類與實踐方式

#### 一、跨服務降級

核心邏輯是「犧牲次要服務，保障核心服務」。常見做法有三種：

1. **整個服務停掉**
   - 例：大促期間停掉退款服務

2. **停掉服務的部分節點**
   - 例：十個節點停掉五個，挪作他用

3. **停止訪問某些資源**
   - 例：日誌中心壓力大時，通知非核心服務停止上傳日誌，僅本地保存

#### 二、本服務提供有損服務

針對單一服務的降級策略：

1. **返回默認值** - 最簡單的方式
2. **禁用可觀測性組件** - 降低採樣率或停用埋點
3. **同步轉異步** - 返回「已接收」響應，後續異步處理
4. **簡化流程** - 跳過非關鍵步驟或改為異步執行

### 面試亮點方案

#### 方案一：讀寫服務降級寫服務

**適用場景**：同一服務同時提供讀寫接口，讀服務比寫服務更重要。

**實例**：
- B 端商家錄入門店資訊
- C 端用戶查詢門店資訊

**降級策略**：
當讀服務響應時間超過閾值時，暫停 B 端寫服務，將資源騰給 C 端讀服務。

**優點分析**：
- 寫服務 QPS 雖低，但對數據庫壓力遠大於讀請求
- 暫停寫服務能有效降低數據庫負載

**通用原則**：
- B/C 端合併部署 → 降級 B 端
- 付費/非付費服務 → 降級非付費服務
- 根據業務價值分級，從不重要的服務開始降級

**業務價值判斷**：
最簡單的方法是詢問產品經理，或根據公司主要營收來源確定。唯一的例外是合規相關服務（如內容審核），即便不賺錢也絕對不能降級。

#### 方案二：快慢路徑降級慢路徑

**適用場景**：服務邏輯可分為快路徑（如查緩存）和慢路徑（如查數據庫、發起服務調用、複雜計算）。

**降級策略**：
觸發降級後，只允許走快路徑，不走慢路徑。若快路徑無結果，直接返回錯誤。

**實例**：
- 正常：查緩存 → 缓存未命中 → 查數據庫
- 降級：查緩存 → 缓存未命中 → 直接返回錯誤

**原理**：
少數緩存未命中的請求會佔據大量系統資源。降級慢路徑能確保快路徑請求得到正常處理，大幅提高系統吞吐量。

### 跨節點降級的限制

目前大多數降級方案局限於同一節點上的不同服務。若服務分散在不同節點，通常需要人工介入（如大促關閉退款服務）。

**理論上可行的方案**：
網關可支援跨節點降級 —— 當重要服務資源不足時，停掉次要服務的部分節點，並在其上部署重要服務。但遺憾的是，大多數網關和微服務框架都未提供此功能。

## 💡 重點摘要

- 降級是高可用架構的重要手段，與熔斷、限流並列為三大可用性保障措施
- 降級分為跨服務降級和本服務有損服務兩大類，核心是識別服務重要性分級
- 讀寫服務降級寫服務：B/C 端合併部署時優先保障 C 端讀服務
- 快慢路徑降級慢路徑：犧牲慢路徑請求，保障快路徑吞吐量
- 降級決策需考慮抖動問題，避免頻繁切換造成系統不穩定
- 任何故障處理都應考慮恢復策略是否會引起抖動
