# Redis 緩存過期策略解析

## 📝 課程概述

本單元探討 Redis 如何處理過期 key 的刪除機制，深入解析為什麼 Redis 不會立刻刪除過期資料。課程涵蓋四種過期機制的設計思路、Redis 的懶惰刪除與定期刪除策略、主從架構下的過期處理，以及 RDB/AOF 持久化時對過期 key 的處理方式。

## 核心觀念與實作解析

### 緩存命中率

緩存命中率是衡量緩存效果的關鍵指標，計算公式為：

```
緩存命中率 = 緩存命中次數 / 查詢總次數
```

實務上應努力將命中率提升至 90% 以上。但需注意，命中率受業務模式影響——若場景是缓存計算時間很長的結果，但大部分請求都是小請求（不會命中缓存），命中率可能連一半都不到。不過這些小請求計算快速，走即時計算的響應時間仍可接受。

### 四種過期機制的設計思路

從系統設計角度，過期機制可考慮四種實現思路：

| 策略 | 說明 |
|------|------|
| **定時刪除** | 針對每個需刪除的對象啟動計時器，到期後直接刪除 |
| **延遲隊列** | 將對象放入延遲隊列，取出時即表示已過期 |
| **懶惰刪除** | 使用對象時檢查是否過期，過期則刪除 |
| **定期刪除** | 每隔一段時間遍歷對象，刪除已過期者 |

**優缺點分析**：
- 定時刪除：精確但開銷大（每個 key 一個計時器）
- 延遲隊列：開銷大，修改過期時間需調整隊列順序
- 懶惰刪除：簡單高效，但過期 key 可能長期佔用記憶體
- 定期刪除：折衷方案，需控制執行開銷

大多數缓存框架（如 Redis）採用 **懶惰刪除 + 定期刪除** 結合的策略。

### 為什麼不立刻刪除過期 key？

**核心原因：效能代價太高**

#### 方案一：定時器
- key 數量龐大，一個 key 一個計時器，Redis 無法承受
- 修改過期時間需重置計時器，額外開銷

#### 方案二：延遲隊列
- 延遲隊列本身開銷大（尤其 key 很多時）
- 修改過期時間需調整隊列中各 key 順序
- 需額外線程配合，增加並發控制複雜度

**結論**：定期刪除與懶惰刪除雖然看似浪費記憶體，但浪費極少且對響應時間影響有限。

### Redis 定期刪除的開銷控制

Redis 不會遍歷所有 key，而是採用以下策略：

1. 每個定期刪除循環遍歷 DB
2. 若當次循環未遍歷完全部 DB，下次從當次最後遍歷的 DB 繼續
3. 針對每個 DB 的處理步驟：
   - 若 DB 中無設置過期時間的 key，跳過該 DB
   - 從設置過期時間的 key 中抽一批（默認 25 個）
   - 逐個檢查，過期則刪除
   - 每遍歷 16 個 key 檢測執行時間，超過閾值則中斷
   - 若這批 key 過期比例超過閾值，繼續抽下一批

**為什麼隨機抽樣？**
確保每個 key 都有機會被檢查到。若按順序遍歷，每次遍歷到中間就沒時間，後面的 key 可能永遠無法被遍歷。

**控制開銷的套路**：控制時間或控制個數。

### 定期刪除頻率控制

透過 `hz` 參數控制所有後台任務的執行頻率：

- 若 `hz = N`，每 `1/N` 秒執行一次後台任務
- 例如 `hz = 10`，每 100ms 執行一次
- 正常情況下不建議超過 100，值越大 CPU 使用率越高

**`dynamic-hz` 選項**：開啟後，`hz` 作為基數，實際值由 Redis 動態計算。

### 主從架構下的過期 key 處理

**Redis 3.2 之前的 Bug**：查詢從庫時，即使 key 已過期，仍可能返回資料。

**Redis 3.2 之後的行為**：
- 從庫查詢已過期的 key 會返回 NULL
- **但從庫不會主動刪除**，會等待主庫的刪除命令

```
主庫：發現 key 過期 → 執行刪除操作
從庫：發現 key 過期 → 返回 NULL，但不刪除，等主庫命令
```

### 持久化處理過期 key

#### RDB（快照文件）

**原則：主庫不讀不寫，從庫原封不動**

| 場景 | 行為 |
|------|------|
| 生成 RDB（主庫） | 忽略已過期的 key |
| 加載 RDB（主庫） | 忽略 RDB 中已過期的 key |
| 加載 RDB（從庫） | 原封不動載入，因為很快會收到主庫刪除指令 |

#### AOF（Append Only File）

- 無論定期刪除或懶惰刪除，都會記錄一條 `DEL` 命令
- AOF 重寫時，會忽略已過期的 key

### 如何確定過期時間？

**核心三角關係**：緩存容量、過期時間、命中率

```
過期時間 ↑ → 命中率 ↑ → 所需容量 ↑
```

**實務做法**：
1. 根據業務場景預估（如用戶 30 分鐘內大概率會再次使用）
2. 模擬線上流量測試，逐步延長過期時間直到滿足命中率
3. 若資源不足，只能縮短過期時間，代價是命中率下降

**命中率如何確定？**
根據用戶體驗需求反推。例如：
- 要求 90% 用戶直接命中緩存（響應時間 < 100ms）
- 根據命中/未命中緩存的響應時間推算

```
假設：命中緩存 100ms，未命中 1000ms，要求平均響應時間 300ms
則命中率 p 需滿足：100 × p + 1000 × (1-p) = 300
```

### 過期時間設計案例

#### 案例一：高併發冪等方案中的 Redis

**場景**：布隆過濾器-Redis-唯一索引的高併發冪等方案

**設計思路**：
- 過期時間與重試機制相關
- 若重試基本在 10 分鐘內完成，過期時間設為 10 分鐘
- 過短 → 命中率低，請求落到資料庫撐不住高併發
- 過長 → 浪費記憶體

#### 案例二：熱點數據過期時間

**原則**：越熱的數據，過期時間越長

- 榜單數據：每小時計算一次 → 過期時間 1 小時
- 大 V 新作品：預期粉絲數小時內看完 → 過期時間數小時
- 舊作品：觀看人少 → 過期時間較短

#### 案例三：預加載與超短過期時間

**場景**：用戶行為可預測（如列表頁 → 詳情頁）

**設計思路**：
- 用戶搜索後大概率點擊列表前幾項
- 返回列表頁時，異步預加載第一頁詳情到緩存
- 過期時間設很短（如 1 分鐘），因為：
  - 用戶不一定會訪問
  - 就算訪問也只訪問一兩次
  - 這個緩存只對該用戶有意義

**本質**：用記憶體換響應時間

## 💡 重點摘要

- Redis 採用 **懶惰刪除 + 定期刪除** 結合策略，單獨使用任一策略都有缺陷
- 不立刻刪除過期 key 的原因：定時器和延遲隊列的效能代價太高，不值得
- Redis 透過 **控制執行時間** 來控制定期刪除開銷，在服務正常請求和清理過期 key 間取得平衡
- 從庫查詢過期 key 返回 NULL，但不主動刪除，等待主庫命令
- RDB 處理原則：主庫不讀不寫過期 key，從庫原封不動；AOF 處理：追加 DEL 命令，重寫時忽略過期 key
- 過期時間需根據緩存容量、命中率和業務場景綜合考量
