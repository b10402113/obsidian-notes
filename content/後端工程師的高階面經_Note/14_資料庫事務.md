# 資料庫事務：事務提交後，資料真的安全了嗎？

## 📝 課程概述
本單元深入探討資料庫事務的實現機制，特別是 undo log、redo log 與 binlog 的運作原理。透過理解這些底層機制，你將能回答「事務提交了，資料就一定不會丟嗎？」這個關鍵問題，並在面試中展現扎實的 MySQL 基礎。

## 核心觀念與實作解析

### Undo Log：回滾的「後悔藥」

Undo log 是回滾日誌，記錄事務執行過程中被修改的資料，讓事務可以回滾到原本的狀態。不同操作對應不同的 undo log 形態：

**INSERT 操作**
- Undo log 記錄該行的主鍵
- 回滾時根據主鍵刪除對應記錄

**DELETE 操作**
- Undo log 記錄該行的主鍵
- DELETE 實際上只是將刪除標記位設為 true
- 回滾時將刪除標記位設回 false

**UPDATE 操作（未更新主鍵）**
- Undo log 記錄主鍵與被修改欄位的原值
- 回滾時將資料恢復為原值

**UPDATE 操作（更新主鍵）**
- 視為 DELETE 舊行 + INSERT 新行
- Undo log 包含兩部分：DELETE 的 undo log + INSERT 的 undo log

Undo log 同時也是 MVCC 版本鏈的載體，讓不同事務能看到對應版本的資料。

### Redo Log：確保持久性的關鍵

**為什麼需要 redo log？**

InnoDB 並非直接操作磁碟，而是透過 buffer pool（記憶體）進行讀寫，後續再將修改過的資料刷新到磁碟。這會產生一個問題：如果 buffer pool 已修改，但尚未刷新到磁碟時資料庫崩潰，資料就會丟失。

**Redo log 的解決方案**

1. 先更新 buffer pool
2. 寫入 redo log
3. 事務結束後再將 buffer pool 刷新到磁碟
4. 若崩潰可透過 redo log 恢復

**關鍵優勢：順序寫取代隨機寫**

Redo log 採用順序寫（WAL, Write-Ahead Log），效能遠優於隨機寫。即便在 SSD 上，順序寫速度仍比隨機寫快上一個數量級。

**寫入流程**

```
redo log buffer → page cache（OS） → 磁碟
```

**innodb_flush_log_at_trx_commit 參數控制刷盤時機**

| 值 | 行為 | 風險 |
|---|---|---|
| 0 | 每秒刷新 redo log buffer 到磁碟 | 可能丟失 1 秒內的資料 |
| 1 | 每次提交都刷新到磁碟（預設值，最安全） | 無風險 |
| 2 | 每次提交刷新到 page cache | 若 OS 崩潰會丟失 |

**例外情況**

- Redo log buffer 超過一半滿時，會主動觸發刷盤
- 某事務提交觸發刷盤時，會一併刷新 buffer 中所有事務的 redo log

### 事務執行過程（以 UPDATE 為例）

假設執行 `UPDATE tab SET a = 5 WHERE id = 1`，原值 a = 3：

1. **事務開始**：找到目標行，加鎖，讀入 buffer pool
2. **寫入 undo log**：記錄 a = 3
3. **更新 buffer pool**：將 a 改為 5
4. **寫入 redo log**：記錄更新操作
5. **提交事務**：根據 `innodb_flush_log_at_trx_commit` 決定是否刷盤
6. **刷新 buffer pool**：將髒頁寫回磁碟

**異常處理**

- Redo log 已刷盤但 buffer pool 丟失 → MySQL 重啟後重放 redo log
- 事務回滾 → 使用 undo log 恢復 buffer pool 與磁碟資料

### Binlog 與兩階段提交

**Binlog 特性**

- MySQL Server 層級的日誌（所有引擎通用）
- 用途：資料恢復、主從同步

**兩階段提交確保一致性**

```
第一階段：redo log Prepare
第二階段：redo log Commit
```

判斷標準：**binlog 是否寫成功**

- Binlog 寫成功 → 視為事務已提交
- Binlog 寫失敗 → 視為事務提交失敗

**sync_binlog 參數控制 binlog 刷盤**

| 值 | 行為 |
|---|---|
| 0（預設） | 由 OS 決定，寫入 page cache 即成功 |
| N | 每 N 次提交刷盤一次；N = 1 最安全 |

### ACID 特性

| 特性 | 說明 |
|---|---|
| 原子性（Atomicity） | 事務不可分割，要麼全成功，要麼全失敗 |
| 一致性（Consistency） | 執行結果滿足資料約束，無矛盾 |
| 隔離性（Isolation） | 事務間互不干擾 |
| 持久性（Durability） | 提交後永久保存，故障也不丟失 |

**亮點提示**：可從隔離性引出隔離級別話題，MySQL InnoDB 的可重複讀解決了幻讀問題。

## 💡 重點摘要

1. **Undo log 用於回滾**，記錄資料的原值；**redo log 用於重做**，採用順序寫提升效能
2. **事務安全性取決於刷盤策略**：`innodb_flush_log_at_trx_commit = 1` 與 `sync_binlog = 1` 最安全
3. **兩階段提交確保 redo log 與 binlog 一致性**，以 binlog 寫入成功為判斷標準
4. **崩潰恢復口訣**：redo log 未刷盤 → 回滾；redo log 已刷盤 → 重放
5. **面試亮點**：可延伸至寫入語義（單機刷盤時機、分布式主從同步）及調整參數策略
