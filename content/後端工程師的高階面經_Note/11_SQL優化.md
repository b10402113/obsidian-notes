# SQL 優化：如何發現 SQL 中的問題？

## 📝 課程概述

本單元深入探討 SQL 優化的核心方法論，從 EXPLAIN 命令的使用到多種實務優化案例，協助後端工程師建立完整的效能調優能力。課程特別強調面試準備策略，讓學習者能將技術知識轉化為面試亮點。

## 核心觀念與實作解析

### SQL 優化的定位與目標

SQL 優化是「資料庫優化」體系中的一環。完整的資料庫優化包含四個層次：

1. **硬體資源優化**：升級機器規格
2. **作業系統優化**：調整系統參數
3. **伺服器/引擎優化**：調整資料庫軟體設定，如事務隔離級別、InnoDB 日誌刷盤時機
4. **SQL 優化**：針對 SQL 語句本身的調整

從資料庫角度，SQL 優化有兩個核心目標：
- **減少磁碟 IO**：避免全表掃描、善用索引與覆蓋索引
- **減少記憶體 CPU 消耗**：降低排序、分組、去重等操作

### EXPLAIN 命令：效能診斷的關鍵工具

EXPLAIN 是每個後端工程師必須掌握的工具。使用方式為 `EXPLAIN your_sql`，資料庫會返回執行計畫。

關鍵欄位解析：

| 欄位 | 說明 |
|------|------|
| **type** | 查詢方式，從優到劣：system > const > eq_ref > ref > range > index > ALL |
| **possible_keys** | 候選索引 |
| **key** | 實際使用的索引 |
| **rows** | 掃描行數 |
| **filtered** | 所需資料占 rows 的比例 |

type 類型說明：
- **system / const**：資料庫只返回一行資料，查詢時間固定
- **eq_ref / ref**：根據索引值查找
- **range**：索引範圍掃描
- **index**：索引全表掃描
- **ALL**：全表掃描，觸發磁碟 IO

優化流程：**EXPLAIN 查看執行計畫 → 嘗試優化 → 循環反覆直到效能達標**

### 索引列的選擇原則

設計索引時，列的選擇至關重要：

1. **外鍵**：常用於關聯、過濾資料
2. **頻繁出現在 WHERE 的列**：避免全表掃描
3. **頻繁出現在 ORDER BY 的列**：避免查詢後再次排序
4. **頻繁出現在關聯條件的列**（一般不建議使用關聯查詢）
5. **區分度高的列**：每行資料都不同的列，組合索引時應放左側

### 大表表結構變更的挑戰

修改索引或表結構時，資料庫會加表鎖直到修改完成。大表可能鎖住數分鐘到數小時。

三種解決方案：

| 方案 | 優點 | 缺點 |
|------|------|------|
| **停機變更** | 操作簡單 | 影響業務 |
| **業務低谷變更** | 影響較小 | 可能跨入高峰期 |
| **建立新表** | 不停機、不影響業務 | 需要資料遷移 |

## 優化案例實戰

### 案例 1：覆蓋索引優化

**情境**：高頻 SQL 查詢 `SELECT *` 但業務只用 A、B、C 三列，WHERE 條件也是這三列。

**解法**：建立 `<A, B, C>` 組合索引，將 SQL 改為 `SELECT A, B, C`。

**效果**：完全避免回表，查詢時間降至 1ms 以內。

**核心原理**：覆蓋索引讓查詢只需掃描索引，不需要回到主表取得資料。

### 案例 2：優化 ORDER BY

**情境**：`SELECT * FROM xxx WHERE uid = 123 ORDER BY update_time`，用戶資料多時執行緩慢。

**解法**：建立 `<uid, update_time>` 組合索引。

**原理**：索引本身有序。uid 確定後，update_time 在索引中已排序，資料庫可直接按順序返回，省去排序過程。

**效果**：查詢時間從秒級降到數十毫秒。

**延伸應用**：DISTINCT 等操作也可用類似思路優化。

### 案例 3：優化 COUNT

**問題**：MySQL InnoDB 引擎未存儲資料總數，`SELECT COUNT(*)` 執行緩慢。

**方案一：預估值取代精確值**
```sql
EXPLAIN SELECT * FROM xxx WHERE uid = 123
```
使用 EXPLAIN 返回的預估行數。

**方案二：Redis 記錄總數**
使用 Redis 或額外表格記錄總數。

**注意事項**：使用 Redis 維持總數會有資料一致性問題，解法：
- 業務可接受短暫不一致：異步刷新 Redis
- 使用 Canal 監聽 MySQL binlog 刷新 Redis

### 案例 4：索引提示優化

**情境**：資料庫執行計畫異常，不用索引或使用錯誤索引。

**解法**：使用 FORCE INDEX、USE INDEX、IGNORE INDEX 糾正資料庫行為。

**注意**：這不是好的實踐，不到迫不得已不要使用。

### 案例 5：用 WHERE 替換 HAVING

**原理**：資料庫先執行 WHERE 找候選列，再執行 HAVING 二次過濾。

**優化**：將 HAVING 中非聚合函數的條件提前到 WHERE。

**效果**：某案例查詢時間降低 40%。

**經驗法則**：除非使用聚合函數作為過濾條件，否則優先寫在 WHERE。

### 案例 6：優化分頁偏移量

**問題**：`LIMIT 5000, 50` 需讀取 5050 行，丟棄前 5000 行，頁碼越大越慢。

**解法**：使用小偏移量
```sql
WHERE id > max_id LIMIT 50
```
max_id 為上一批的最大 ID，確保偏移量永遠為 0。

**效果**：查詢速度穩定在毫秒級。

## 面試準備策略

### 資料收集清單

- 維護業務的所有表結構定義（含索引）
- 每張表執行最頻繁的三個 SQL 是否用到索引
- 公司慢 SQL 的發現、分析、優化過程
- 優化前後的執行時間對比

### 面試切入點

當面試官問到以下問題時，可引導到 SQL 優化：
- 是否做過效能優化？
- 接口響應時間？有無優化空間？
- 是否了解索引？是否用過索引？

### 回答框架

1. 描述系統需求：「某系統是核心系統，對效能/可用性有高要求」
2. 說明優化目標：「響應時間降到 100ms 以內，可用性達三個九」
3. 闡述方法：「使用 EXPLAIN 查看執行計畫，確認索引使用與操作消耗」
4. 展示結果：「優化後查詢時間從秒級降到毫秒級」

### 面試節奏控制

SQL 優化手段繁多，**不需要全部掌握**。面試關鍵在於：
- 掌控主動權
- 引導面試官問你熟悉的內容
- 精心設計面試節奏與案例

## 💡 重點摘要

- SQL 優化目標：減少磁碟 IO 與 CPU/記憶體消耗
- EXPLAIN 是診斷 SQL 效能的核心工具，關注 type、key、rows、filtered
- 索引設計：優先選擇外鍵、WHERE 列、ORDER BY 列、高區分度列
- 覆蓋索引可避免回表，是高頻 SQL 的首選優化手段
- 排序欄位加入索引可利用索引有序性，避免額外排序
- 大偏移量分頁使用 `WHERE id > max_id` 維持效能穩定
