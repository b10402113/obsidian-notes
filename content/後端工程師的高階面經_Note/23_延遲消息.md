# 在 Kafka 上實現延遲消息的方案

## 📝 課程概述

延遲消息是消息隊列面試中的熱門話題，特別是 Kafka 並不原生支持延遲消息，但許多業務場景（如訂單超時取消）卻需要此功能。本單元將深入探討在 Kafka 上實現延遲消息的多種方案，從基礎到進階，並結合分庫分表等技術提供高級解決方案。

## 核心觀念與實作解析

### 延遲消息的本質

延遲消息是指消息不會被立即消費，而是經過一段時間後才會被消費。在到達指定時間前，消息會持續存儲在消息隊列服務器上。典型的應用場景包括訂單超時取消、延遲通知等。

### 其他消息隊列的實現方式

#### RabbitMQ 的兩種方案

**插件方案**：使用 `rabbitmq_delayed_message_exchange` 插件
- 原理：實現一個 exchange 控制消息何時真正投遞到隊列
- 存儲：消息暫存在 Mnesia（基於文件的數據庫）
- 缺點：消息在投遞前存於服務端本地，節點不可用會導致消息丟失；不支援高併發大數據量

**TTL + 死信隊列方案**：
- 原理：創建 `delay_queue` 設置過期時間，無消費者；將業務隊列 `biz_queue` 綁定為其死信隊列
- 流程：消息發送到 `delay_queue` → 過期後轉發到 `biz_queue` → 消費者接收
- 缺點：TTL 在隊列級別設定，無法做到隨機延遲時間，需創建多個不同 TTL 的隊列

### 基礎方案：定時任務調度

最簡單的方案是利用分布式定時任務平台，業務發送者註冊一個在指定時間後發送消息的任務。此方案易於實現，但無法支撐高併發場景。

### 基礎方案：分區設置不同延遲時間

#### 架構設計

創建 `delay_topic`，將分區設定為不同的延遲時間（如 1min、3min、10min），延遲消費者消費對應分區，等待指定時間後轉發到 `biz_topic`。

```
delay_topic (p0: 1min, p1: 3min, p2: 10min)
    ↓
延遲消費者 (每分區一個消費者，等待後轉發)
    ↓
biz_topic (業務消費者無感)
```

#### 關鍵問題：Rebalance

消費者在睡眠期間不會消費消息，Kafka 會判定消費者崩潰而觸發 rebalance。解決方案是利用 Kafka 的 Pause/Resume 功能：

1. 拉取消息（offset = N），查看剩餘延遲時間 t
2. 暫停消費，睡眠時間 t
3. 睡眠結束後，恢復消費，從 offset = N 繼續

> **重要**：Kafka 的暫停仍會發起 Poll 調用，只是不拉取數據，確保 Kafka 認為消費者仍在運行。

#### 關鍵問題：一致性

轉發到 `biz_topic` 和提交 offset 的順序至關重要：

- **先提交再轉發**：提交後宕機會導致消息丟失
- **先轉發再提交**（推薦）：提交前宕機會重複轉發，需消費者確保冪等性

#### 優缺點分析

**優點**：實現簡單，對業務方影響小，只需根據延遲時間選擇正確分區。

**缺點**：
1. 延遲時間必須預先設定，不支援隨機延遲
2. 分區間負載不均，可能導致消息積壓

### 進階方案：基於 MySQL 的隨機延遲方案

#### 架構設計

```
業務發送者 → delay_topic → 延遲消費者 → MySQL
                                    ↓
                              延遲發送者 → biz_topic → 業務消費者
```

延遲消費者將消息轉儲到數據庫，延遲發送者輪詢數據庫轉發已到期的消息。

#### 性能優化策略

**1. 分區表**

根據發送時間分區，歷史分區可及時清理：
- 低併發：按週分區
- 高併發：按天分區

**2. 表交替**

準備兩個表（`tab_0`、`tab_1`）交替使用：
- 今天用 `tab_0`，明天用 `tab_1`
- 切換時可 TRUNCATE 之前的表
- 限制：延遲時間不能超過一天

**3. 分庫分表**

按 `biz_topic` 名稱分庫分表，可疊加分區表和表交替方案。

**負載均衡問題**：不同 topic 併發度不同，會造成壓力差異。

**解決方案**：
- 不考慮有序性：輪詢插入各表（延遲消息查找時只按發送時間）
- 保持有序性：同一 `biz_topic` 的消息落入同一張表，且發送到 `delay_topic` 時按 `biz_topic` 名稱選擇分區

**4. 批量操作**

延遲消費者批量消費、批量插入、批量提交；延遲發送者批量發送、批量更新狀態。雖會加劇一致性問題，但消費者冪等性可解決。

## 💡 重點摘要

- 延遲消息是 Kafka 面試熱點，因 Kafka 不原生支援但業務需求強烈
- RabbitMQ 可透過插件或 TTL + 死信隊列實現，但各有局限
- 基礎方案包括定時任務調度與分區設置不同延遲時間，後者需處理 rebalance 和一致性問題
- 進階方案使用 MySQL 存儲延遲消息，透過分區表、表交替、分庫分表、批量操作支撐高併發
- 分庫分表時需考慮負載均衡與消息有序性，可透過輪詢或按 topic 分表解決
- 消費者冪等性是解決一致性問題的關鍵
