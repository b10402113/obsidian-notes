# 資料庫索引：為什麼 MySQL 用 B+ 樹而不用 B 樹？

## 📝 課程概述
資料庫索引是面試中的高頻考點，也是影響系統性能的關鍵因素。本單元從 B+ 樹的原理出發，深入解析 MySQL 索引的運作機制、分類方式與最左匹配原則，幫助你建立扎實的索引知識體系。

## 核心觀念與實作解析

### B+ 樹的定義與特徵

B+ 樹是一種多叉樹，其核心特徵有二：

1. **葉子節點存放資料**：非葉子節點只存放索引關鍵字
2. **葉子節點以鏈表串聯**：支援範圍查詢

可以用一個比喻來理解：B+ 樹就像一個部門，管理層（非葉子節點）只負責傳達指令，具體事務由基層員工（葉子節點）執行。基層員工之間私底下有聯繫，對應到 B+ 樹就是葉子節點被鏈表串聯。

B+ 樹用於資料庫索引有三大優勢：
- **查詢性能更好**：樹的高度比二元樹更低，代表更少的磁碟 IO
- **適合範圍查詢**：葉子節點以鏈表串聯，可快速遍歷
- **適合放入記憶體**：非葉子節點不存放資料，空間佔用小

第三點常被忽略，但至關重要。使用索引提升查詢效能的前提，就是索引本身能全部載入記憶體，只有真實資料行放在磁碟上。

### 索引分類

MySQL 索引從不同角度看有不同分類：

- **聚簇索引 vs 非聚簇索引**：依葉子節點是否存放資料行劃分
- **覆蓋索引**：索引包含某查詢的所有欄位，可避免回表
- **唯一索引**：索引值必須唯一
- **前綴索引**：只取欄位值的前一部分作為索引
- **組合索引**：由多個欄位組成的索引
- **全文索引**：支援文本模糊查詢
- **哈希索引**：MySQL InnoDB 引擎不支援

一個索引可以同時具備多種屬性，關鍵在於從哪個角度理解。

### 聚簇索引與非聚簇索引

資料表本身可以看作一棵用主鍵搭建的 B+ 樹，葉子節點存放所有資料行，這就是聚簇索引。其他索引也是 B+ 樹，但葉子節點存放的是主鍵。

**回表**是指：透過非聚簇索引找到主鍵後，再回到聚簇索引查找資料行的過程。回表會觸發磁碟 IO，效能較差，實務上應盡量避免。

### 覆蓋索引

如果查詢的欄位全部都在某個索引中，資料庫可以直接從索引取得資料，不必回表。

例如：在 `user_tab` 的 `(id, name)` 上建立組合索引，查詢 `SELECT id, name FROM user_tab WHERE id = 123` 就能直接使用索引資料。

覆蓋索引不是獨立的索引類型，而是某個索引相對於某個查詢的特性。這衍生出兩個 SQL 優化原則：
1. 只查詢需要的欄位
2. 針對最頻繁的查詢設計覆蓋索引

本質都是為了避免回表。

### 最左匹配原則

組合索引的使用遵循最左匹配原則。以索引 `<A, B, C>` 為例：
- A 絕對有序
- A 確定時，B 有序
- A、B 都確定時，C 有序

**反過來說**：
- 若 A 不確定，B、C 都無序
- 若 A 確定但 B 不確定，C 無序

口訣：**AND 用 OR 不用，正用反不用，範圍則中斷**。

實務上，是否使用索引要以 `EXPLAIN` 命令輸出為準。

### 索引的代價

索引並非免費，會消耗系統資源：
1. **磁碟空間**：索引本身需要儲存
2. **記憶體空間**：運行時索引會載入記憶體
3. **維護成本**：增刪改時需同步維護索引

面試時若被問「索引有什麼壞處」，可從這三點切入。

## 💡 重點摘要

- B+ 樹的三個核心優勢：查詢快、範圍查詢友好、適合放入記憶體
- 聚簇索引的葉子節點存放資料行，非聚簇索引存放主鍵
- 回表會觸發磁碟 IO，應透過覆蓋索引避免
- 最左匹配原則決定組合索引的使用方式
- 索引有儲存、記憶體與維護成本
