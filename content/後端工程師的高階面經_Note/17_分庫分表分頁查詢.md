# 分庫分表分頁查詢優化策略

## 📝 課程概述

本單元探討分庫分表架構下分頁查詢的效能問題與解決方案。從全局查詢法的效能瓶頸出發，逐步介紹平均分頁、禁用跨頁查詢、二次查詢法及中間表方案，幫助你在面試中系統性回答分頁查詢優化問題，拉開與其他候選人的差距。

## 核心觀念與實作解析

### 分庫分表的基本做法

分庫分表一般使用三種算法：

1. **哈希分庫分表**：根據分庫分表鍵計算哈希值後取餘選擇目標資料庫。例如訂單表按買家 ID 除以 8 的餘數進行分表。
2. **範圍分庫分表**：按數據範圍分段，最常見的是按日期分表（如每月一張表）。
3. **中間表**：引入額外表格記錄主鍵到目標表的映射關係。

這三者可以組合使用，例如哈希分表搭配中間表。

### 分庫分表中間件的形態

分庫分表中間件有三種部署形態：

1. **SDK 形態**：以依賴形式引入代碼（如 ShardingSphere Java 依賴），性能最佳但與語言強耦合。
2. **Proxy 形態**：獨立部署的中間件，對業務方偽裝成普通資料庫。優點是跨語言通用、遷移成本低；缺點是性能較差、存在單點故障風險。
3. **Sidecar 形態**：理論上的形態，目前尚無成熟產品。架構上性能介於 SDK 與 Proxy 之間，無單體故障問題。

### 全局查詢法及其效能問題

**為什麼分頁查詢在分庫分表後變得困難？** 因為要做到「全局有序」非常困難。

假設執行 `SELECT * FROM order_tab ORDER BY id LIMIT 4 OFFSET 2`，中間件需要考慮數據可能分布在任意表中的各種情況。因此，中間件會將查詢改寫為：

```sql
LIMIT x OFFSET y  =>  LIMIT x+y OFFSET 0
```

改寫後發送給所有目標表，在記憶體中排序後取出符合條件的數據。

**效能瓶頸分析**：

- **網路傳輸**：原本只需傳輸 10 條數據，分庫分表後若命中 N 個表，需傳輸 `(1000+10) × N` 條數據（假設 LIMIT 10 OFFSET 1000）。
- **記憶體**：中間件需在記憶體中維持排序結果，Proxy 形態容易 OOM。
- **CPU**：排序是 CPU 密集操作，高併發下容易 CPU 100%。

**優化手段：歸併排序**

每個目標表返回的結果已經有序，可使用歸併排序逐條讀取，取夠數據即返回，無需一次性載入全部數據。

### 平均分頁方案

**基本思路**：在每個表上平均執行分頁查詢，合併結果作為近似答案。

```sql
-- 原查詢
SELECT * FROM order_tab ORDER BY id LIMIT 4 OFFSET 2

-- 改寫為
SELECT * FROM order_tab_0 ORDER BY id LIMIT 2 OFFSET 1
SELECT * FROM order_tab_1 ORDER BY id LIMIT 2 OFFSET 1
```

**精度問題**：此方案返回的數據不一定是全局最精確的結果。例如預期取 3、4、5、6，實際可能取到 2、4、5、9。

**適用場景**：對順序、精度要求不嚴格的場景（如瀏覽頁面）。

**進階版本**：根據數據分佈決定各表取多少數據。若某表佔 70% 數據，則從該表取 70% 的分頁數據。

### 禁用跨頁查詢（實務最常用）

**核心思路**：要求用戶只能從第 0 頁開始逐頁往後翻，不允許跨頁。透過攜帶上一頁的極值將 OFFSET 控制為 0。

**實作方式**：

```sql
-- 升序排序
SELECT * FROM order_tab WHERE id > max_id ORDER BY id LIMIT 50 OFFSET 0

-- 降序排序
SELECT * FROM order_tab WHERE id < min_id ORDER BY id DESC LIMIT 50 OFFSET 0
```

**極值選擇原則**：升序用最大值，降序用最小值。若 ORDER BY 包含多列，則依各列的升序/降序決定。

**優勢**：查詢時間非常穩定，OFFSET 永遠為 0。手機 App 下拉刷新場景天然適用。

### 換用其他中間件

若分庫分表處理分頁太困難，可考慮：

1. **NoSQL 方案**：使用 Elasticsearch、ClickHouse 等處理排序。
2. **分佈式關係型資料庫**：將分頁難題交給這些資料庫處理。

### 二次查詢法（亮點方案）

**核心理念**：先獲得某個數據的全局偏移量，再根據此偏移量計算剩餘數據的偏移量。

**執行步驟**（假設查詢 `LIMIT 4 OFFSET 4`，共 2 個表）：

1. **首次查詢**：發送 `LIMIT 4 OFFSET 2` 到所有表（平均分配 OFFSET）。
2. **確認最小值**：找出所有返回結果中的最小值（升序情況下）。
3. **二次查詢**：構造 `BETWEEN min AND max` 查詢，max 為各表首次查詢的最大值。
4. **計算全局偏移量**：根據二次查詢比首次查詢多出的數據量推算 min 的全局偏移量。
5. **取最終結果**：在二次查詢結果中，從 min 之後補足到目標偏移量，再取所需數據。

**簡化版記憶**：
1. 首次查詢，拿到最小值。
2. 二次查詢，確認最小值的全局偏移量。
3. 在二次查詢結果中根據偏移量取數據。

**特點**：結果精確，但實作複雜度高。

### 引入中間表方案

**核心思路**：額外存儲一份數據專門用於排序，在中間表加上排序相關的列。

```sql
-- 先在中間表查詢目標數據
SELECT id FROM index_tab ORDER BY update_time LIMIT 10 OFFSET 100

-- 再去目標表查詢完整數據
SELECT * FROM order_tab WHERE id IN (...)
```

**缺陷**：
1. WHERE 條件只能使用中間表上的列。
2. 維護中間表會引入數據一致性問題。

**一致性解決方案**：
- **業務雙寫**：同時寫入目標表和中間表。
- **Canal 監聽 binlog**：異步更新中間表，業務無感知。建議引入重試機制降低失敗機率。

**注意**：此方案依賴最終一致性，不適合強一致性場景。

## 💡 重點摘要

- 全局查詢法將 `LIMIT x OFFSET y` 改寫為 `LIMIT x+y OFFSET 0`，存在網路、記憶體、CPU 三大效能瓶頸，可用歸併排序緩解。
- 平均分頁在各表平均執行分頁查詢，適合精度要求不高的場景，可根據數據分佈優化。
- 禁用跨頁查詢是實務最常用方案，透過攜帶上一頁極值將 OFFSET 控制為 0，查詢時間穩定。
- 二次查詢法可精確取得結果但實作複雜，需兩次查詢並計算全局偏移量。
- 中間表方案需維護數據一致性，可透過 Canal 監聽 binlog 異步更新，適合最終一致性場景。
