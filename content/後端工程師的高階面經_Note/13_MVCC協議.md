# MVCC 協議：MySQL 的多版本並發控制機制

## 📝 課程概述

本單元深入探討 MySQL InnoDB 引擎的 MVCC（Multi-Version Concurrency Control）機制，解決「為什麼在修改資料時仍能讀取該資料」的核心問題。理解 MVCC 不僅是面試必考題，更能串聯事務與隔離級別兩大重點，讓你在面試中進退自如。

## 核心觀念與實作解析

### 為什麼需要 MVCC？

鎖機制雖然能控制並發，但效能太差。即便使用讀寫鎖，讀和寫之間仍然是互斥的。然而資料庫作為效能關鍵的中間件，如果某個執行緒修改資料時就阻塞所有 SELECT 語句，這種效能損耗是無法接受的。

**關鍵洞察**：資料庫即便在讀取時，也不能被寫操作阻塞。因此 InnoDB 引入 MVCC，目的在於避免讀寫阻塞。

### 四大隔離級別

隔離級別代表一個事務是否了解其他事務，以及了解程度如何。MySQL 有四個隔離級別：

1. **讀未提交（Read Uncommitted）**：事務可以看到其他事務尚未提交的修改
2. **讀已提交（Read Committed, RC）**：事務只能看到已提交事務的修改。若執行過程中有其他事務提交，仍能看到最新修改
3. **可重複讀（Repeatable Read, RR）**：事務內多次讀取同一資料，結果相同。即使執行過程中有其他事務提交，也看不到其修改。這是 MySQL 的預設隔離級別
4. **串行化（Serializable）**：事務對資料的讀寫都是序列化的

**重要補充**：從上到下隔離性變強但效能變差。特別注意，理論上可重複讀未解決幻讀，但 MySQL 因使用臨鍵鎖（Next-Key Lock），其可重複讀隔離級別已解決幻讀問題。

### 三種讀異常

- **髒讀（Dirty Read）**：讀到其他事務尚未提交的資料
- **不可重複讀（Non-repeatable Read）**：事務執行過程中，對同一行資料讀到的結果不同
- **幻讀（Phantom Read）**：事務執行過程中，其他事務插入新資料並提交，後續步驟讀到該新資料

| 隔離級別 | 髒讀 | 不可重複讀 | 幻讀 |
|---------|-----|-----------|------|
| 讀未提交 | 可能 | 可能 | 可能 |
| 讀已提交 | 不可能 | 可能 | 可能 |
| 可重複讀 | 不可能 | 不可能 | 可能（MySQL 已解決） |
| 串行化 | 不可能 | 不可能 | 不可能 |

### 版本鏈的實現

InnoDB 為每一行增加兩個額外欄位：

- **trx_id**：事務 ID（事務版本號）。每個事務開始時獲得一個 ID，該事務操作的所有資料行的 trx_id 都會被修改為此 ID
- **roll_ptr**：回滾指標。透過 roll_ptr 將每一行的歷史版本串聯在一起

這條版本鏈存儲在 undolog 中。當新事務要讀取資料時，問題變成：應該讀取哪個 trx_id 的資料？這就涉及到 Read View。

### Read View 機制

Read View 是一種可見性規則，用於控制事務應該讀取哪個版本的資料。核心欄位為 **m_ids**，代表當前已開始但尚未結束的事務 ID（活躍事務 ID）。

Read View 僅用於已提交讀和可重複讀兩個隔離級別，差異在於 **何時生成 Read View**：

**已提交讀（RC）**：
- 每次查詢都重新創建新的 Read View
- 像「渣男」朋友，每次見面都換新對象
- 若其他事務提交，下次查詢能看到最新修改

**可重複讀（RR）**：
- 事務開始時創建 Read View，整個事務過程中保持不變
- 像「痴情」男，每次看到的都是最初認定的對象
- 即使其他事務提交，也看不到其修改

Read View 相關概念：
- **m_up_limit_id**：m_ids 中的最小值
- **m_low_limit_id**：下一個將分配的事務 ID
- **m_creator_trx_id**：當前事務 ID

### 面試核心思路

回答「為什麼有了鎖還需要 MVCC」時，關鍵詞是 **避免讀寫阻塞**：

> 單純使用鎖時，並發效能較差。即便在讀寫鎖機制下，讀和寫仍是互斥的。資料庫作為效能關鍵的中間件，若某執行緒修改資料就讓其他執行緒無法讀取，這種效能損耗無法接受。因此 InnoDB 引入 MVCC，減少讀寫阻塞。

回答 MVCC 原理時，按 **基本定義 → 實現機制 → 隔離級別** 的邏輯順序，提及關鍵詞：版本鏈、trx_id、roll_ptr、undolog、Read View、隔離級別。

### 亮點方案：調整隔離級別

**為什麼改為已提交讀**：
1. 業務場景很少利用可重複讀特性（大多數事務內對同一資料只讀一次）
2. 可重複讀更容易引起死鎖（如臨鍵鎖引發的死鎖問題）
3. 已提交讀效能更好

**若需可重複讀特性怎麼辦**：
- **改造業務**：第一次查詢後快取結果，避免第二次查詢
- **幻讀問題**：業務層面通常不是問題，因為難以區分是否為幻讀，且事務提交往往代表業務已結束
- **指定隔離級別**：在 Session 或事務維度指定隔離級別

### 推進策略（軟技能）

1. **準備充分**：充分調研實際情況，提出針對性方案
2. **公開決議**：先與關鍵人物溝通取得支持，再在公開會議拋出議題
3. **小步推進**：先改造不重要業務的資料庫，或只在新建資料庫應用
4. **全面鋪開**：制定操作規範，讓業務負責人選擇合適時機切換

## 💡 重點摘要

- MVCC 的核心目的是避免讀寫阻塞，提升並發效能
- 版本鏈透過 trx_id 和 roll_ptr 串聯歷史版本，存儲於 undolog
- Read View 的生成時機決定了 RC 與 RR 的差異：RC 每次查詢重新生成，RR 只在事務開始時生成
- MySQL 的 RR 隔離級別透過臨鍵鎖解決了幻讀問題
- 面試亮點：推動降低隔離級別為已提交讀，並準備好應對「若需可重複讀怎麼辦」的追問
