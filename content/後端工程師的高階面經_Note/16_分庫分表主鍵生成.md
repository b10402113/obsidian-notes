# 分庫分表主鍵生成策略設計

## 📝 課程概述

本單元探討在分庫分表架構下,傳統自增主鍵失效的原因,並深入分析 UUID、資料庫步長自增、雪花算法三種主流方案的原理與缺陷。在此基礎上,提出「主鍵內嵌分庫分表鍵」的創新設計思路,以及發號器的高並發優化策略。

## 核心觀念與實作解析

### 為什麼分庫分表後自增主鍵失效

分庫分表架構通常包含三層:主從集群 → 庫 → 表,例如 8×4×32 表示 8 個主從集群,每集群 4 個庫,每庫 32 張表。

問題核心在於:若多張表各自依賴資料庫自增主鍵,會產生 ID 衝突。例如按 buyer_id 取模分表後,order_tab_0 和 order_tab_1 的第一筆資料 ID 都是 1,無法滿足全域唯一需求。

此外,主鍵生成還需考量:
- **插入效能**:自增主鍵可避免頻繁頁分裂
- **高並發支援**:大數據量場景下的併發壓力

### 方案一:UUID

最簡單直接,但有兩大缺陷:
1. **過長**:實務上通常不計較長度
2. **非遞增**:這是面試亮點所在

#### 為何遞增主鍵效能更好——頁分裂視角

MySQL InnoDB 使用 B+ 樹組織資料,每個頁按主鍵排序存放。若插入非遞增 ID,會導致:
- 資料往頁中間插入
- 引發頻繁頁分裂
- 嚴重時分裂從葉節點一路連鎖到根節點

**對比**:自增主鍵迫使 B+ 樹朝單一方向增長,插入效能最佳。

#### 為何遞增主鍵效能更好——順序讀視角

遞增主鍵資料在磁碟上位置相近,範圍查詢時可充分利用順序讀特性,提升 I/O 效率。

### 方案二:資料庫步長自增

設定步長讓各表生成不同序列。例如 10 張表:
- 表 0:1、11、21、31...
- 表 1:2、12、22、32...

**特點**:
- 實作簡單,只需建表時指定步長
- 全域不保證遞增,但單表內遞增
- 效能受限於資料庫效能

### 方案三:雪花算法 (Snowflake)

64 位 ID 分三段:
- 1 bit 保留
- 41 bits 時間戳
- 10 bits 機器 ID
- 12 bits 序列號

**唯一性保證**:
- 時間戳不同 → 不同時刻 ID 不同
- 機器 ID 不同 → 同一時刻不同機器 ID 不同
- 序列號控制 → 同一時刻同一機器內不衝突

#### 亮點一:靈活調整分段

各段含義與長度可自定義:
- 時間戳 41 bits 可縮減至 39 bits,十幾年也夠用
- 機器 ID 可代表算法實例(進程/執行緒/協程)
- 可引入業務含義

**核心思想**:雪花算法是一種設計範式,透過時間戳與分段切割,賦予 ID 各段不同意義。

#### 亮點二:序列號耗盡處理

高並發時序列號可能不夠用,解法:
1. 加長序列號(從時間戳挪 bits)
2. 改用 96/128 位 ID
3. **兜底方案**:讓業務方等待下一毫秒(變相限流)

#### 亮點三:低頻場景資料堆積問題

若按 ID 取模分表,低頻場景可能導致資料全落同一張表。解法:
- 序列號從隨機數開始計數
- 從上一時刻序列號終點開始計數

### 創新方案:主鍵內嵌分庫分表鍵

**痛點**:分庫分表鍵(如 buyer_id)與主鍵(如 order_id)往往不同,查詢時需額外維護映射。

**設計思路**:參考雪花算法,將分庫分表鍵嵌入主鍵結構:
- 第一段:時間戳
- 第二段:買家 ID 後四位(分庫分表鍵)
- 第三段:隨機數

**優勢**:透過訂單 ID 即可反推資料所在庫表,無需額外索引。

#### 全域遞增問題

無法嚴格保證,但可達到「大體遞增」:
- 同一時刻不同用戶建立訂單,ID 大小取決於用戶 ID
- 同一用戶同時刻兩筆訂單,隨機數部分決定大小

**結論**:效能不如嚴格遞增,但優於完全隨機。

#### 唯一性問題

衝突概率極低,需滿足三個條件:
- 同一用戶
- 同一時刻
- 隨機數碰撞(假設範圍 0-100000,概率 1/100000)

**容錯措施**:插入時若主鍵衝突錯誤,重新生成 ID 再試。

**時鐘回撥問題**:相比正統雪花算法,有隨機數段稀釋風險,影響較輕。

### 發號器優化策略

#### 批量取

業務方每次取一批 ID(如 100 個),內部慢慢消耗。

**優點**:發號器併發壓力降至原本的 1%。
**缺點**:可能破壞遞增順序(B 先取先插,A 後取後插)。

#### 提前取

預先取得 ID,結合批量取。快用完時再取下一批,需設計兜底等待機制。

#### Singleflight 模式

多執行緒需 ID 時,派一個代表去取,分發給其他執行緒。降低發號器併發負載。

#### 區域性分發

執行緒取 ID 時多拿一些(如 20 個)存入 TLB(Thread-Local Buffer),後續從 TLB 取,避開全域競爭。

## 💡 重點摘要

- 分庫分表後自增主鍵會產生全域衝突,需設計新的主鍵生成策略
- UUID 簡單但非遞增,會引發頻繁頁分裂,影響插入與查詢效能
- 雪花算法透過時間戳+分段設計保證唯一性,各段含義可靈活自定義
- 主鍵內嵌分庫分表鍵是實務亮點方案,可簡化路由邏輯但需處理遞增與唯一性權衡
- 發號器可透過批量取、提前取、singleflight、區域性分發優化高並發場景
