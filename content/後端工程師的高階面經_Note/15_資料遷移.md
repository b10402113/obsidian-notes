# 不停機資料遷移的完整方案設計

## 📝 課程概述
本單元深入探討如何在不停機的情況下完成資料庫遷移，這是後端工程師必須掌握的高難度技術。透過系統化的八步驟方案，結合雙寫機制、增量校驗與資料修復，確保遷移過程中的資料一致性，同時保持業務持續運行。

## 核心觀念與實作解析

### 為什麼不停機遷移如此重要？

資料遷移場景在實務中非常常見，包括：
- 重構老系統，使用新的表結構
- 單庫拆分為分庫分表，或分庫分表擴容
- 大表修改表結構定義

許多人在面試時只能回答「停機遷移」，但這無法展現技術深度。不停機遷移方案能綜合體現候選人設計複雜方案解決棘手問題的能力，是區分技術水平的關鍵點。

### 前置知識：備份工具與關鍵參數

#### MySQL 常用備份工具

**mysqldump** 是邏輯備份工具，導出的是一條條 SQL 語句，優點是使用簡單，缺點是導入導出速度較慢。

**XtraBackup** 是物理備份工具，直接複製 InnoDB 底層存儲文件，支援增量備份和恢復。

#### 加速 mysqldump 的關鍵技巧

對於導出速度，可開啟 `extended-insert` 選項，將多行合併為一個 INSERT 語句。

對於導入速度，可採取三項優化：
1. 關閉唯一性檢查和外鍵檢查（源表已保證這兩項）
2. 關閉 binlog（導入資料不需要 binlog）
3. 調整 redo log 刷盤時機，將 `innodb_flush_log_at_trx_commit` 設為 0

#### innodb_autoinc_lock_mode 參數

此參數控制自增主鍵生成策略，有三個取值：
- **0**：使用表自增鎖，INSERT 語句結束後釋放
- **1**：普通 INSERT INTO VALUES 語句申請主鍵後即釋放鎖；INSERT SELECT 等語句執行完畢才釋放
- **2**：所有語句申請主鍵後立刻釋放

重要特性：執行 INSERT INTO VALUES 時，無論插入多少行都只申請一次主鍵，這些主鍵**必然是連續的**，可從返回的最後一個 ID 推測全部 ID。此特性在雙寫場景中至關重要。

### 八步驟不停機遷移方案

完整的遷移流程如下：

1. **創建目標表**
2. **用源表資料初始化目標表**
3. **執行校驗並修復資料**（以源表為準）
4. **業務代碼開啟雙寫**（讀源表，先寫源表，以源表為準）
5. **開啟增量校驗與資料修復**（保持一段時間）
6. **切換雙寫順序**（讀目標表，先寫目標表，以目標表為準）
7. **繼續保持增量校驗與資料修復**
8. **切換為目標表單寫**（讀寫都只操作目標表）

核心記憶點：右側四步都要考慮校驗和修復資料的問題，確保資料一致性。

### 步驟詳解與亮點分析

#### 步驟二：初始化目標表資料

兩種來源：
- 使用源表的歷史備份（但會落後生產資料）
- 使用 mysqldump 從源表導出資料（導出期間可能有資料變化）

此步驟後必須立即進行校驗與修復，因為備份或導出過程中源表資料可能已發生變化。

#### 步驟三：第一次校驗與修復

若公司有明確資料庫規範（如所有表都有 `update_time` 欄位），可採用增量方案：只校驗 `update_time` 晚於導出時間點的記錄，修復時**直接用源表資料覆蓋目標表資料**。

#### 步驟四：業務開啟雙寫

**雙寫實現方式**分為侵入式與非侵入式：

侵入式方案直接修改業務代碼，要求業務代碼在寫源表後再寫目標表，但工作量大且容易出錯。

非侵入式方案利用 ORM 框架：
- **AOP 方案**：透過 interceptor、middleware、hook、handler、filter 等機制，捕捉增刪改調用並篡改為雙寫模式
- **資料庫操作抽象**：透過 Session、Connection、Connection Pool、Executor 等，將源表操作修改為雙寫模式

關鍵要求：雙寫狀態必須能在運行期隨時切換（單寫源表、先寫源表、先寫目標表、單寫目標表），通常透過配置中心的標記位控制。

以 GORM 為例，可使用 ConnPool 接口，用裝飾器模式封裝兩個資料源，根據標記位執行雙寫邏輯。

**資料一致性問題**：若寫入源表成功但目標表失敗，可暫時不管，因為後續有校驗與修復機制處理。曾考慮過發送消息到消息佇列修復，但難點在於無法確定受影響的行（如 UPDATE 語句失敗時無法推斷哪些行被影響）。

**自增主鍵問題**：雙寫時必須在源表插入時拿到自增主鍵值，再將此值作為目標表插入的主鍵，否則並發場景下兩表的主鍵可能不一致。批量插入時更需注意：INSERT INTO VALUES 語法生成的主鍵是連續的，但多個 INSERT INTO VALUE 或 INSERT SELECT 語句可能生成不連續主鍵，需提前改造此類業務。

#### 步驟五：增量校驗與資料修復

**方案一：利用更新時間戳**

定時查詢每張表，根據 `update_time` 判斷資料是否變化：

```sql
-- 查詢最近更新的記錄
SELECT * FROM xx WHERE update_time >= last_time
```

比對源表與目標表的對應記錄，若不一致則用源表資料修復目標表。

此方案有兩個前提：
1. 所有表都有更新時間戳
2. 刪除必須是軟刪除（若為硬刪除，源表刪除後目標表未刪，匹配邏輯會找不到）

硬刪除場景的補救措施：**反向全量校驗**，從目標表查全量資料，再去源表找對應資料，若源表沒有則說明已刪除，可刪除目標表資料。

**主從延遲問題**：若校驗時讀從庫，可能遇到兩種異常（源表或目標表的主從延遲）。解決方案：

簡單粗暴：全部讀主庫，但對主庫壓力大。

**進階方案：雙重校驗**
- 第一次校驗讀從庫
- 若發現不一致，再讀主庫校驗一次
- 修復時以主庫資料為準

此方案基於「主從延遲和資料不一致是小概率事件」的前提。

**方案二：利用 binlog**（更進階）

使用基於行的 binlog 模式，有三種形態：

**形態一：binlog 作為觸發器**
監聽 binlog，收到後用主鍵查詢源表與目標表，比較兩者資料，不一致則用源表修復目標表。

**形態二：binlog 資料作為源表資料**
用 binlog 中的主鍵查詢目標表，比較 binlog 內容與目標表資料。若不一致，再用主鍵查源表，用查到的資料覆蓋目標表（防止 binlog 是舊資料而目標表是新資料的情況）。

**形態三：比較源表與目標表的 binlog**（理論可行但不建議）
直接比較兩表的 binlog，但存在兩個棘手問題：
1. 收到兩端 binlog 的時間差，需要緩存一端等待另一端
2. 順序問題，多次雙寫同一行時 binlog 順序可能錯亂

此方案過於複雜，得不償失。

#### 步驟六：切換雙寫順序

這是一個關鍵亮點。許多人會直接從雙寫（源表為準）切換到目標表單寫，但風險太大，無法回滾。

正確做法：引入過渡階段，先寫目標表再寫源表，業務讀目標表。若發現問題還能回滾為先寫源表再寫目標表，確保有「後悔藥」可吃。

#### 步驟七：保持增量校驗與修復

切換雙寫順序後，繼續增量校驗與修復，但此時**以目標表為準**。

### 核心要點總結

- 無論先後順序或並發問題，修復時永遠用主表的最新資料
- 若源表或目標表本身是分庫分表，查詢與修復時使用對應的分庫分表規則即可
- 方案在第八步之前都可回滾，一旦切換到第八步則無法回滾

### 面試策略

即便實際使用停機遷移，面試時也應回答不停機遷移方案。可在回答停機遷移後，提起了解或曾實施過不停機遷移方案。

強調高端方案才能拉開與其他候選人的差距。

## 💡 重點摘要

- 不停機資料遷移透過八步驟方案確保資料一致性，核心是雙寫機制配合增量校驗與修復
- mysqldump 導入優化三手段：關閉唯一性/外鍵檢查、關閉 binlog、調整 redo log 刷盤時機
- 雙寫實現採用非侵入式方案，透過 ORM 框架的 AOP 或資料庫操作抽象層實現
- 自增主鍵處理關鍵：源表插入時獲取主鍵值，再設為目標表主鍵，確保兩表一致
- 切換雙寫順序是關鍵過渡階段，提供回滾能力，降低遷移風險
