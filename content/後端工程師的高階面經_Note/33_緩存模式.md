# 緩存模式：能否解決緩存一致性問題？

## 📝 課程概述

本單元深入探討各種緩存模式（Cache Pattern）的運作原理、優缺點，以及在數據一致性方面的表現。緩存模式是面試高頻問題，但多數人回答不夠完整或深入，特別是當面試官追問「如何用緩存模式解決一致性問題」時容易掉入陷阱。

## 核心觀念與實作解析

### 緩存模式總覽

主要的緩存模式包括：
- **Cache Aside**：最基本的模式，由業務代碼控制緩存與數據庫的讀寫順序
- **Read Through**：讀穿透，緩存未命中時由緩存層自動從數據庫加載數據
- **Write Through**：寫穿透，業務方只需寫入緩存，緩存層負責更新數據庫
- **Write Back**：寫回模式，數據只寫入緩存，緩存過期時才刷新到數據庫
- **Refresh Ahead**：利用 CDC 異步刷新緩存
- **Singleflight**：控制併發量，避免緩存擊穿

此外，刪除緩存與延遲雙刪雖然不嚴格算作緩存模式，但在實務中非常常見。

### Cache Aside 模式

**核心概念**：將緩存視為獨立數據源，由業務代碼控制讀寫順序。

**寫入流程**：優先寫入數據庫。原因是大多數業務場景以數據庫為準，即使緩存寫入失敗，緩存過期後重新加載即可恢復一致性。

**關鍵結論**：無論先寫數據庫還是先寫緩存，Cache Aside 都**無法解決數據一致性問題**。

當併發讀寫發生時，可能出現「後啟動的線程先完成」的情況，導致緩存與數據庫不一致。

### Read Through 模式

**核心概念**：讀操作時，若緩存未命中，由緩存層代替業務代碼從數據庫加載數據並緩存。寫操作與 Cache Aside 相同。

**一致性問題**：由於寫操作未受控，Read Through 同樣存在緩存一致性問題。

#### 亮點：異步變種方案

1. **異步寫回緩存**：從數據庫加載數據後立即返回，另開線程異步更新緩存。適用於緩存操作較慢的場景（如大對象序列化）。

2. **完全異步加載**：緩存未命中時直接返回錯誤或默認值，異步加載並回寫緩存。適用於對響應時間極度敏感的場景，代價是當次調用無法獲取正確數據。

### Write Through 模式

**核心概念**：寫入時只需寫入緩存，緩存層負責更新數據庫。讀操作與 Cache Aside 相同。

**設計考量**：
- 未規定先寫數據庫還是先寫緩存，但一般優先寫數據庫
- 若緩存中無數據，是否刷新緩存取決於該數據是否會被頻繁讀取

#### 亮點：異步變種方案

1. **異步寫入數據庫與刷新緩存**：寫入緩存後立即返回成功，異步執行後續操作。**風險**：若緩存崩潰，數據可能丟失。

2. **同步寫數據庫，異步刷新緩存**：適用於緩存寫入代價高昂的場景（如大對象序列化）。

### Write Back 模式

**核心概念**：寫入時只更新緩存，緩存過期時才刷新到數據庫。需有組件監聽過期 key 進行數據同步。

**致命缺陷**：若緩存突然宕機，未刷新的數據將丟失，這限制了其在現實中的應用。但若緩存能做到高可用，仍可考慮使用。

#### 亮點：數據一致性表現

**本地緩存 vs Redis**：
- 使用本地緩存：數據分散在多節點，仍有一致性問題
- 使用 Redis（假設不考慮數據丟失）：**可實現數據一致性**

**一致性分析**：
- 寫操作：業務方只更新緩存，對業務方而言數據必然一致
- 讀操作：緩存未命中時從數據庫加載，可能產生不一致

**問題場景**：
1. 數據庫中 a=3，讀請求加載後尚未回寫緩存
2. 寫請求在緩存中寫入 a=4
3. 讀請求回寫緩存時，用老數據覆蓋新數據

**解決方案**：讀請求回寫時使用 **SETNX** 命令，僅當緩存中無數據時才寫入。若寫入失敗，重新從緩存讀取。

### Refresh Ahead 模式

**核心概念**：利用 CDC（Capture Data Change）接口異步刷新緩存，如使用 Canal 監聽數據庫 binlog 後刷新 Redis。

**一致性問題**：緩存未命中讀請求與寫請求衝突時可能不一致。

**解決方案**：讀請求回寫時使用 SETNX 命令，可大幅緩解問題。僅存數據寫入數據庫但尚未刷新到緩存的短暫不一致。

### Singleflight 模式

**核心概念**：緩存未命中時，同一 key 只有一個線程真正加載數據，其他線程原地等待。

**優點**：大幅減少數據庫併發壓力。若同時有 100 個線程訪問同一 key，最終只有 1 個線程查詢數據庫。

**缺點**：併發量不高時效果有限。適用於熱點數據場景。

### 刪除緩存模式

**核心概念**：更新數據時先更新數據庫，再刪除緩存。可由業務代碼控制，也可結合 Write Through 讓緩存層處理。

**一致性問題**：不一致源於讀線程緩存未命中與寫線程衝突，而非兩個寫線程衝突。

**潛在風險**：頻繁刪除緩存導致命中率下降，性能受損；緩存未命中疊加寫操作，數據庫壓力增大。

### 延遲雙刪模式

**核心概念**：第一次刪除後設定定時器，延遲一段時間後再次刪除。

**設計動機**：第二次刪除用於避開讀寫衝突導致的不一致場景。

**一致性分析**：
- 理論上仍可能不一致（第一次刪除到第二次刪除之間）
- 實務上，延遲時間足夠長，發生概率極低

**缺點**：兩次刪除進一步降低緩存命中率。

### 實務選擇建議

每種緩存模式都有缺陷。面試時可根據偏好選擇，關鍵是清楚分析優劣與一致性問題。

**推薦方案**：延遲雙刪。一致性問題較輕微，雖命中率略降，但對低頻寫入的業務場景完全可接受。

## 💡 重點摘要

- **Cache Aside、Read Through、Write Through、Refresh Ahead 都無法徹底解決緩存一致性問題**
- **Write Back 在使用 Redis 且不考慮數據丟失的前提下，一致性表現最佳**，但存在數據丟失風險
- **Singleflight 適用於熱點數據**，有效控制數據庫併發壓力
- **刪除緩存的一致性問題源於讀寫衝突**，而非寫寫衝突
- **延遲雙刪是實務推薦方案**，一致性問題較輕，適合低頻寫入場景
