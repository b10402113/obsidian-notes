# 無分庫分表鍵查詢：多維度查詢的解決方案

## 📝 課程概述

本單元探討分庫分表架構下的核心難題：當資料依買家 ID 分庫分表後，賣家、客服或運營等角色如何查詢訂單？透過四種解決方案的對比與整合，建立完整的面試答題框架。

## 核心觀念與實作解析

### 為什麼需要無分庫分表鍵查詢？

分庫分表鍵的選擇完全由業務驅動。以電商訂單為例，買家查詢自己的訂單是最主要場景，因此依買家 ID 分庫分表收益最大。但這也意味著：賣家查訂單、客服找訂單、運營分析等場景變得複雜——這些查詢都不具備分庫分表鍵。

### 方案一：主鍵內嵌分庫分表鍵

若主鍵設計時將買家 ID 編碼其中，查詢時只需解析主鍵即可定位目標庫表。

**優點**：零額外成本、無需第三方工具
**局限**：僅支援「有主鍵」的查詢場景

### 方案二：引入中間表

建立一張映射表，記錄訂單 ID、賣家 ID、買家 ID（或目標庫表資訊）。

**查詢流程**：
1. 根據賣家 ID 在中間表找到訂單 ID 和買家 ID
2. 根據買家 ID 定位庫表，查詢完整訂單資料

**設計要點**：
- 若主鍵已內嵌買家 ID，中間表可省略買家 ID 列
- 中間表欄位應盡可能少，避免放入頻繁更新的欄位（如狀態）

**核心缺陷**：
- **性能瓶頸**：中間表無法再分庫分表，寫壓力難以分散
- **結構僵化**：新查詢場景需修改表結構，大表改結構風險極高
- **一致性難題**：中間表越多，維護成本越高

### 方案三：二次分庫分表（冗餘 Sharding）

複製一份資料，按另一個維度（如賣家 ID）重新分庫分表。

**優化策略**：
- 不需全量複製：只複製關鍵表、關鍵欄位
- BLOB、TEXT 等大欄位不需同步，必要時回原表查詢
- 類似覆蓋索引的優化思路：高頻查詢所需欄位全量複製，避免二次查詢

**權衡**：
- 中間表：成本低，但寫瓶頸、需回表
- 二次分庫分表：成本高，但性能好、欄位更完整

### 方案四：使用其他中間件（如 Elasticsearch）

為支援複雜多變的查詢場景，引入搜尋引擎。

**設計原則**：只同步與搜尋相關的欄位，減輕 ES 壓力

### 方案五：廣播（兜底方案）

當所有方案都無法支援時，直接向所有庫表發送查詢請求並彙總結果。

**缺陷**：對資料庫壓力極大，大多數請求浪費在空表上

### 資料同步：雙寫 vs 監聽 Binlog

| 方案 | 實作方式 | 適用場景 |
|------|----------|----------|
| 雙寫 | 改造 ORM 或分庫分表中間件 | 中間件可控時 |
| 監聽 Binlog | 使用 Canal 等框架異步同步 | Proxy 或 Sidecar 形態 |

**失敗處理**：重試機制 → 異步修復程序 → 人工介入

### 綜合架構方案

在實際架構中，可組合多種方案：
- **賣家查詢**：二次分庫分表
- **複雜搜尋**：Elasticsearch
- **商品-訂單映射**：中間表
- **極端場景**：廣播作為兜底

**進階議題**：若允許賣家直接修改賣家庫，需處理雙向同步與衝突覆蓋問題。更穩妥的做法是「賣家庫只讀，所有寫入走買家庫」。

## 💡 重點摘要

- 分庫分表鍵選擇由業務主查詢決定，實務中候選項有限，選擇相對單純
- 中間表適合低頻更新場景，二次分庫分表適合高頻查詢但成本較高
- 主鍵內嵌分庫分表鍵是最優雅的方案，但僅限有主鍵的查詢
- 廣播是性能最差的兜底方案，應避免在核心路徑使用
- 綜合架構需考慮資料一致性、同步成本與衝突處理
