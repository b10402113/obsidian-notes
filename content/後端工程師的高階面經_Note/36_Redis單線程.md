# Redis 單線程：為什麼 Redis 用單線程而 Memcached 用多線程？

## 📝 課程概述
本單元深入探討 Redis 高性能背後的技術原理，釐清「Redis 是單線程」的真正含義，並解析 epoll 系統調用與 Reactor 模式如何協同運作，最後比較 Redis 與 Memcached 的線程模型差異及 Redis 6.0 引入多線程的設計考量。

## 核心觀念與實作解析

### Redis 單線程的真正含義

當我們說「Redis 是單線程」時，實際上是指**處理命令的過程是單線程的**。然而，Redis 的其他功能如持久化、資料同步等，都是由獨立的線程負責。因此嚴格來說，Redis 是多線程架構。

特別值得注意的是，Redis 6.0 之後，連 IO 模型都改為多線程，進一步發揮多核 CPU 的優勢。

### Redis 高性能的兩大關鍵

Redis 的高性能源自兩個層面：
1. **純內存操作**：所有命令都在內存中執行，速度極快
2. **高效的 IO 模型**：採用 epoll + Reactor 模式

### epoll 模型詳解

epoll 是 Linux 系統中處理 IO 多路復用的機制。簡單來說，**epoll 會幫你管理一堆套接字（socket），當你需要讀寫時，只需詢問哪些套接字已就緒**。

在 Linux 中，萬物皆檔案，套接字也是檔案描述符（file descriptor）。因此 epoll 的本質就是對檔案描述符進行增刪改查。

#### epoll 的核心結構

- **紅黑樹**：每個節點代表一個檔案描述符
- **雙向鏈表（就緒列表）**：存放已就緒的檔案描述符

#### epoll 的三個系統調用

| 系統調用 | 功能 |
|---------|------|
| `epoll_create` | 創建 epoll 結構 |
| `epoll_ctl` | 對 epoll 中的檔案描述符進行增、刪、改 |
| `epoll_wait` | 返回符合條件的檔案描述符（查詢） |

#### epoll_wait 的超時參數

| 參數值 | 行為 |
|-------|------|
| -1 | 永久阻塞，直到有符合條件的檔案描述符 |
| 0 | 立即返回，不管是否有符合條件的檔案描述符 |
| 正整數 N | 最多等待 N 毫秒 |

#### epoll 與中斷機制

epoll 如何知道資料到了？答案是**中斷**：
- 當網卡收到資料時，會觸發硬體中斷，網卡驅動通知 epoll 有資料到達
- 超時機制則依賴時鐘中斷，內核檢查發起 `epoll_wait` 的線程是否超時

### epoll、poll、select 比較

| 模型 | 特點 | 性能 |
|------|------|------|
| select | 每次調用都要傳入所有檔案描述符，內核逐一檢查 | O(n)，受 FD_SETSIZE 限制 |
| poll | 與 select 類似，但無檔案描述符數量限制 | O(n) |
| epoll | 只返回就緒的檔案描述符，使用事件通知機制 | O(1) |

**核心差異**：epoll 會提前將符合條件的檔案描述符放到就緒列表，而 select/poll 需要每次調用時才檢查。

### Reactor 模式

Reactor 模式廣泛應用於高性能 IO 處理，其核心架構是**一個分發器 + 一堆處理器**。

客戶端與服務端的 IO 交互主要有兩類事件：
- **連接事件** → 交給 Acceptor 處理
- **讀寫事件** → 交給 Handler 處理

#### Redis 的單線程 Reactor

在 Redis 單線程模型中，Reactor、Handler、Acceptor 雖然在邏輯上有區分，但實際上都由同一個線程執行：

1. Reactor 調用 epoll，獲取符合條件的檔案描述符
2. 若為連接事件，完成連接初始化並監聽讀寫事件
3. 若為讀寫事件，執行對應的讀寫操作

#### Reactor 模式的變種

1. Acceptor 多線程化
2. Handler 多線程化
3. Reactor 多線程化（主線程只監聽連接，其他線程處理讀寫）

### Redis 為何選擇單線程？

Redis 使用單線程模型的優勢：

| 優勢 | 說明 |
|------|------|
| 無上下文切換開銷 | 避免線程切換的 CPU 開銷 |
| 無並發競爭問題 | 天然線程安全，無需鎖機制 |
| 瓶頸不在 CPU | 內存操作極快，瓶頸在網絡 IO 和內存大小 |
| 易於理解和調試 | 單線程邏輯清晰 |

### Memcached 為何使用多線程？

Memcached 採用多線程設計的考量：

| 優勢 | 劣勢 |
|------|------|
| 充分利用多核 CPU 性能 | 線程上下文切換開銷 |
| - | 需要鎖來保護共享資源 |

實際上，兩者的性能表現不相上下，這更多是設計者的偏好選擇。

### Redis 6.0 為何引入多線程？

Redis 6.0 引入多線程只有一個原因：**性能**。

在高併發場景下，利用多線程並發處理 IO 任務、命令解析和資料回寫。這些線程稱為 **IO 線程**。

#### 多線程模式下的運作機制

```
客戶端請求 → 主線程收到可讀事件
           → 將客戶端放入可讀列表
           → IO 線程讀取並解析命令
           → 主線程執行命令
           → 將響應放入可寫列表
           → IO 線程寫回響應
```

主線程負責：
- 接收事件
- 創建連接
- 執行命令

IO 線程負責：
- 讀寫資料
- 命令解析

#### 何時啟用多線程？

大多數情況下**不建議啟用**多線程模式。Redis 單線程性能已足夠應付絕大多數場景。遇到性能瓶頸時，可考慮：
- 啟用多線程（據測試可提升約 50% QPS）
- 擴展 Redis Cluster 規模（更好的可用性）

## 💡 重點摘要

- 「Redis 單線程」指命令處理是單線程，持久化等功能仍由其他線程處理；Redis 6.0 後 IO 也支援多線程
- Redis 高性能的兩大支柱：純內存操作 + epoll + Reactor 模式
- epoll 的核心是紅黑樹管理檔案描述符、就緒列表返回已就緒的描述符，性能優於 select/poll
- Reactor 模式 = 分發器 + 處理器，將連接事件交給 Acceptor，讀寫事件交給 Handler
- Redis 單線程優勢：無上下文切換、無並發競爭、易於調試；Memcached 多線程則充分利用多核 CPU
- Redis 6.0 引入多線程是為了在高併發場景下提升 IO 性能，但大多數場景無需啟用
