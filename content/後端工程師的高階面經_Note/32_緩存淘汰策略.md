# 緩存淘汰策略：如何淘汰才能維持命中率

## 📝 課程概述

本單元探討緩存淘汰策略的核心原理與實務應用，從最基本的 LRU、LFU 算法出發，延伸到 Redis 支持的淘汰機制，最後引導你設計針對業務特性的客製化淘汰策略，讓你在面試中展現比「背八股文」更深刻的理解。

## 核心觀念與實作解析

### 為什麼需要淘汰機制

使用緩存時必須控制內存使用量，尤其是本地緩存。若緩存佔用過多內存，可能導致應用內存不足，甚至觸發頻繁 GC（如 Java 的 full GC）。當內存達到上限卻需加入新數據時，最基本的做法是直接報錯，但大多數業務無法接受這種方案——我們需要騰出空間給更有可能被使用的新數據。

### 主流淘汰算法

#### LRU（Least Recently Used）

最近最少使用算法。核心思路：當緩存容量不足時，淘汰最長時間未被訪問的 key。

**實作方式**：使用鏈表串接所有 key，每次被訪問的 key 移至隊尾，隊首即為最久未訪問的 key。Java 可透過 `LinkedHashMap` 輕易實現。

**變種**：可定義「訪問」為讀或寫操作。若只在寫時移動 key，則傾向保留寫頻繁的數據。

#### LFU（Least Frequently Used）

最不經常使用算法。根據對象的訪問次數決定淘汰對象，淘汰訪問次數最少的數據。

**實作思路**：每次讀寫時對象計數加 1，並調整排序位置。若多個對象訪問頻次相同且為最低，可選擇淘汰最先插入者或隨機刪除。

**變種**：統計一段時間內的訪問次數而非整個生命週期，但實作複雜度較高。

#### 算法選擇建議

實務上優先考慮 **LRU**，因為大多數應用滿足時間局部性（最近訪問的數據未來也較可能被訪問）。

**LRU 的劣勢場景**：
- 歷史記錄訪問：越舊的記錄越可能已被淘汰
- 遍歷操作：當前遍歷對象不會被淘汰，但已被遍歷的對象反而應該淘汰，導致緩存完全無命中

### Redis 的淘汰策略

透過 `maxmemory` 控制整個 Redis 實例的內存使用量，透過 `maxmemory_policy` 設置淘汰算法。

**限制**：無法直接控制單一業務的內存使用量，但可透過控制鍵值對數量和單一鍵值對大小來間接控制。

**實作技巧**：在 Redis 中額外記錄鍵值對數量，監聽刪除命令維護計數。需區分全新鍵值對與更新既有鍵值的情況。

### 面試亮點：針對業務特性的淘汰策略

**核心思路**：根據業務重要性設計淘汰優先級。

#### 優先級淘汰方案

為每個鍵值對綁定優先級，觸發淘汰時優先淘汰低優先級數據。

**Redis 實作**：
1. 使用有序集合（sorted set）按優先級排序，元素個數即鍵值對個數
2. 新增鍵值對時執行 lua 腳本：檢查數量是否超限，若超限則從有序集合取出最低優先級的 key 並刪除
3. 監聽刪除事件，維護有序集合

#### 三種衍生策略

**大對象優先淘汰**：一次性騰出較多內存，適合本地緩存場景。

**小對象優先淘汰**：若大對象經複雜計算得出，淘汰大對象會導致快取未命中時響應時間暴增。小對象計算簡單，即便重新計算影響也小。抽象來說：**代價低的優先淘汰**。

**低熱度優先淘汰**：根據數據冷熱程度淘汰。例如內容平台先淘汰小博主數據，保留大博主數據（粉絲多，訪問概率高）。

### 面試回答框架

**問題切入**：緩存使用注意事項、內存控制原因、緩存問題排查、命中率優化。

**回答邏輯**：
1. 控制內存使用量是安全使用緩存的關鍵
2. 優先考慮增加內存降低淘汰機率，但內存有限需選擇合適策略
3. 補充說明公司實際使用的策略（如 volatile-lru）
4. 引導話題：提及針對業務特性的客製化策略，展現靈活設計能力

**案例示範**：透過優先淘汰小客戶數據，保證大客戶體驗，平均響應時間下降 40%。

## 💡 重點摘要

- 緩存淘汰是控制內存使用量的必要機制，直接報錯不是可接受的方案
- LRU 適合時間局部性強的應用，但遍歷場景會導致零命中率
- Redis 透過 `maxmemory` 和 `maxmemory_policy` 控制淘汰行為
- 針對業務特性設計淘汰策略是面試亮點：大對象優先、小對象優先、低熱度優先
- 實務上應優先增加內存，再考慮淘汰策略的選擇
