# 緩存穿透、擊穿與雪崩問題解析

## 📝 課程概述
本單元深入探討 Redis 緩存系統中最常見的三種異常情況：穿透、擊穿與雪崩。這些問題在高併發場景下可能導致大量請求直接落在資料庫上，進而引發系統崩潰。理解這些問題的成因與解決方案，是後端工程師面試中的必備知識。

## 核心觀念與實作解析

### 三個核心概念的區別

**緩存穿透（Cache Penetration）**
- 定義：資料既不在緩存中，也不在資料庫中
- 典型場景：攻擊者偽造大量請求，查詢不存在的資料
- 問題關鍵：資料庫查詢失敗後無法回寫緩存，下次請求仍會落在資料庫上

**緩存擊穿（Cache Breakdown）**
- 定義：資料不在緩存中，但存在於資料庫中
- 典型場景：熱點資料緩存失效，大量併發請求同時查詢
- 問題關鍵：雖然最終會回寫緩存，但瞬間壓力可能壓垮資料庫

**緩存雪崩（Cache Avalanche）**
- 定義：大量緩存資料在同一時刻過期
- 典型場景：應用啟動時批量載入資料，設置相同的過期時間
- 問題關鍵：一次性載入的資料集同時失效，導致大規模請求落在資料庫上

### 解決緩存穿透

**方案一：回寫特殊值**

當查詢發現資料庫中也沒有資料時，往緩存寫入一個特殊值標記「資料不存在」。後續請求看到這個特殊值，直接返回，避免重複查詢資料庫。

缺點：
- 攻擊者使用不同的不存在的 key，方案失效
- 大量不存在的 key 佔用 Redis 記憶體
- 可能導致 Redis 記憶體不足，淘汰有用資料

**方案二：布隆過濾器（Bloom Filter）**

在查詢緩存前，先用布隆過濾器判斷 key 是否可能存在：

```
請求 → 布隆過濾器 → 不存在則直接返回
                  → 可能存在則查詢緩存 → 查詢資料庫
```

優點：
- 假陽性機率極低（如萬分之一），有效攔截惡意請求
- 記憶體佔用極小

變體：先查緩存，緩存未命中再查布隆過濾器
- 對正常請求更友好（大概率命中緩存，無需查布隆過濾器）
- 保護效果略弱於先查布隆過濾器

### 解決緩存擊穿

使用 **singleflight 模式**：當大量請求同時查詢同一個 key 時，只讓一個請求真正去查詢資料庫，其餘請求等待結果返回。

優點：實現簡單，效果顯著，完美解決熱點資料的擊穿問題

### 解決緩存雪崩

核心思路：在批量載入資料時，為每筆資料設置**不同的過期時間**

實作方式：在預設過期時間基礎上，加上隨機偏移量

```
過期時間 = 基礎過期時間 + 隨機偏移量
```

偏移量設計原則：
- 與過期時間成正比
- 過期時間 15 分鐘 → 偏移量 0～180 秒
- 過期時間 4 小時 → 偏移量 0～10 分鐘
- 過期時間 10 秒 → 偏移量 0～3 秒

### 通用防護：限流機制

緩存問題的核心風險是大量請求落在資料庫上，因此限流是最後一道防線。

**服務層限流**
- 隱含假設：資料庫能撐住限流閾值內的流量
- 注意：設定閾值時需考慮緩存未命中的情況

**資料庫層限流**
- 更可靠的保護措施
- 可在資料庫代理或 ORM 層實現
- 無論緩存穿透、擊穿還是雪崩，都能保護資料庫

### 亮點方案：集群互為備份

**基本概念**
使用兩個或多個 Redis 集群，互為備份，提升整體可用性。

**經濟適用版方案**

```
業務 1 → 主要使用集群 1，集群 2 作為備份
業務 2 → 主要使用集群 2，集群 1 作為備份
```

**容錯流程**

1. **偵測故障**：業務與主集群保持心跳，發現連接失敗後觸發容錯
2. **分級處理**：
   - 非核心業務：直接熔斷
   - 核心業務：按預設比例轉發到備份集群
3. **漸進式放量**：從小流量開始，觀察無問題後逐步調大比例
4. **逐步恢復**：主集群恢復後，逐步將流量遷回

**低成本變體**
自建小型 Redis 集群或單機 Redis 作為備份，只需撐住核心流量一段時間即可。

## 💡 重點摘要
- 緩存穿透是資料完全不存在，擊穿是緩存中無資料但資料庫有，雪崩是大面積緩存同時失效
- 解決穿透用布隆過濾器或回寫特殊值，解決擊穿用 singleflight，解決雪崩用隨機過期時間
- 限流是最後防線，應在服務層和資料庫層都部署
- 集群互為備份是提升緩存可用性的有效方案，關鍵在漸進式流量切換
- 面試前收集公司 Redis 部署方式、故障案例、保護措施等實戰經驗
