# 資料庫鎖：明明有行鎖，怎麼突然就加了表鎖？

## 📝 課程概述
本單元深入探討 MySQL 的鎖機制，從鎖與索引的關聯出發，解析行鎖、表鎖、記錄鎖、間隙鎖、臨鍵鎖等核心概念，並提供面試中展示技術亮點的實戰案例。掌握這些知識，能在面試中自信應對鎖相關問題，並在實際工作中優化死鎖與效能瓶頸。

## 核心觀念與實作解析

### 鎖與索引的關鍵關聯

在 MySQL 的 InnoDB 引擎中，**鎖是借助索引實現的**，更具體地說，鎖住的是索引的葉子節點。這個核心概念能解釋大部分鎖相關的疑問：

- **查詢使用了索引**：鎖住該索引對應的範圍
- **查詢未使用任何索引**：退化為表鎖，鎖住整張表

當查詢條件的值不存在時，例如 `SELECT * FROM your_tab WHERE id = 15 FOR UPDATE`，InnoDB 會利用最接近 15 的相鄰節點，構造一個臨鍵鎖。若其他事務嘗試插入 id=15 的記錄，將被阻塞。

範圍查詢如 `SELECT * FROM your_tab WHERE id > 33 FOR UPDATE`，會構造 (33, supremum] 的臨鍵鎖，鎖住整個範圍。

### 鎖的釋放時機

一個常見誤區是認為鎖在語句執行完畢後立即釋放。實際上，**鎖是在整個事務結束後才釋放的**，也就是執行 ROLLBACK 或 COMMIT 時才釋放。

### 樂觀鎖與悲觀鎖

這兩者是並發控制的邏輯概念：

| 特性 | 樂觀鎖 | 悲觀鎖 |
|------|--------|--------|
| 加鎖時機 | 修改資料時才檢測 | 初始時直接加鎖 |
| 實現方式 | CAS 思路，如 `UPDATE ... WHERE a = old_value` | `SELECT ... FOR UPDATE` |
| 適用場景 | 讀多寫少（互聯網應用） | 寫多讀少（金融領域） |
| 效能 | 較好 | 較差 |

樂觀鎖範例：
```sql
SELECT * FROM your_tab WHERE id = 1; -- 取得 a = 1
-- 業務邏輯處理
UPDATE your_tab SET a = 3, b = 4 WHERE id = 1 AND a = 1;
-- 透過受影響行數判斷是否成功
```

悲觀鎖範例：
```sql
SELECT * FROM your_tab WHERE id = 1 FOR UPDATE; -- 直接加鎖
-- 業務邏輯處理
UPDATE your_tab SET a = 3, b = 4 WHERE id = 1;
```

### 行鎖與表鎖

- **行鎖**：鎖住一行或多行資料
- **表鎖**：鎖住整張表

InnoDB 同時支援行鎖與表鎖，但行鎖依賴索引實現。若查詢未命中任何索引，InnoDB 只能使用表鎖。

### 共享鎖與排它鎖

從互斥性角度分類：

- **共享鎖 (S Lock)**：一個執行緒加鎖後，其他執行緒可繼續加同類型鎖
- **排它鎖 (X Lock)**：一個執行緒加鎖後，其他執行緒無法再加鎖

讀鎖本身是共享的，寫鎖是排它的。

### 意向鎖

意向鎖是一個信號，告訴其他事務「我要加鎖了」，並非真正物理意義上的鎖。結合共享鎖與排它鎖，衍生出：

- **意向共享鎖 (IS)**：希望獲得共享鎖
- **意向排它鎖 (IX)**：希望獲得排它鎖

典型應用：在增刪改查時對表結構加意向共享鎖，防止查詢時有人修改表結構；修改表結構時加意向排它鎖，這也是修改表結構會阻塞所有增刪改查語句的原因。

### 記錄鎖、間隙鎖、臨鍵鎖

這是面試中最難理解的三個概念，掌握細節能成為面試亮點。

#### 記錄鎖 (Record Lock)

鎖住特定的某一條記錄。觸發條件：
- 使用主鍵或唯一索引作為查詢條件
- 等值條件且命中記錄

```sql
SELECT * FROM your_tab WHERE id = 31 FOR UPDATE;
-- 只命中一條記錄，加記錄鎖
```

若查詢條件未命中任何記錄，則使用間隙鎖。

#### 間隙鎖 (Gap Lock)

鎖住某一段記錄範圍。觸發條件：
- 範圍查詢（<, <=, BETWEEN）

```sql
SELECT * FROM your_tab WHERE id BETWEEN 50 AND 100 FOR UPDATE;
-- (50, 100) 被間隙鎖鎖住，50 和 100 被記錄鎖鎖住
```

重要特性：**記錄鎖之間互斥，但間隙鎖之間不互斥**，即使兩個間隙鎖重疊，仍可加鎖成功。

#### 臨鍵鎖 (Next-Key Lock)

記錄鎖與間隙鎖的組合，是解決可重複讀隔離級別下幻讀問題的關鍵。

- 間隙鎖：左開右開 `(a, b)`
- 臨鍵鎖：左開右閉 `(a, b]`

若 id 只有 (1, 4, 7) 三條記錄，臨鍵鎖會鎖住 (1, 4]。

#### 快速判斷口訣

1. **遇事不決臨鍵鎖**：預設都是臨鍵鎖
2. **右邊缺省間隙鎖**：若值不在條件範圍內，用間隙鎖
3. **等值查詢記錄鎖**：主鍵或唯一索引的等值查詢用記錄鎖（普通索引不適用）

> 重要提醒：間隙鎖與臨鍵鎖只在**可重複讀 (RR)** 隔離級別下生效。

### 面試亮點案例

#### 案例一：缺索引導致表鎖

```
問題：業務響應時間偶爾突然延長
排查：EXPLAIN 分析正常 SQL 沒問題，但新功能執行的 SQL 未命中索引
原因：未命中索引觸發表鎖，慢 SQL 長時間持有表鎖，拖累其他正常 SQL
解決：為該 SQL 建立索引，避免表鎖
```

#### 案例二：臨鍵鎖引發死鎖

業務邏輯：先 `SELECT FOR UPDATE` 查詢，若無資料則計算後插入，若有資料則計算後更新。

```sql
BEGIN;
SELECT * FROM biz WHERE id = ? FOR UPDATE;
-- 業務邏輯
INSERT INTO biz(id, data) VALUE(?, ?);
COMMIT;
```

死鎖原因：
- 兩個執行緒同時查詢不存在的 id，都獲得 (78, supremum] 臨鍵鎖
- 兩個執行緒分別想插入 id=79 和 id=80，互相等待對方釋放間隙鎖
- 產生死鎖錯誤

解決方案：
1. **先插入預設值**：插入成功則執行「無資料」邏輯，插入失敗則執行「有資料」邏輯（觸發行鎖而非臨鍵鎖）
2. **調整隔離級別為 RC**：消除間隙鎖（影響較大）
3. **改用樂觀鎖**：用 CAS 操作替代悲觀鎖

#### 案例三：棄用悲觀鎖

原始悲觀鎖寫法：
```go
Begin()
data := SelectForUpdate(id)
newData := calculate(data)
Update(id, newData)
Commit()
```

改用樂觀鎖：
```go
for {
  data := Select(id)
  newData := calculate(data)
  success := CAS(id, newData, data)
  // UPDATE xxx SET data = newData WHERE id = 1 AND data = oldData
  if success {
    break
  }
}
```

實務上可引入 `version` 列或 `update_time` 確保資料未被變更。此改造可提升約 30% 效能。

## 💡 重點摘要

- 鎖與索引密切相關，鎖是加在索引項上的；未命中索引則退化為表鎖
- 鎖在事務結束時才釋放，非語句執行完畢即釋放
- 樂觀鎖適合讀多寫少場景，效能較好；悲觀鎖適合寫多讀少場景
- 記錄鎖鎖住特定記錄，間隙鎖鎖住範圍（不互斥），臨鍵鎖是兩者組合
- 臨鍵鎖與間隙鎖只在可重複讀隔離級別下生效
- 面試前準備實際案例：死鎖排查、鎖優化、樂觀鎖應用場景
