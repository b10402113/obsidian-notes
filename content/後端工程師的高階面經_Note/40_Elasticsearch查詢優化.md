# Elasticsearch 查詢效能優化

## 📝 課程概述

本單元深入探討 Elasticsearch 的查詢效能優化策略，從底層的倒排索引機制出發，逐步解析如何在面試中展現對 Elasticsearch 效能調校的實戰能力。透過理解索引原理與多種優化方案，幫助你在面試中建立競爭優勢。

## 核心觀念與實作解析

### Elasticsearch 索引機制

Elasticsearch 使用**倒排索引（Inverted Index）**，與傳統資料庫索引不同。正排索引是從文件對應到關鍵字，倒排索引則是從關鍵字對應到文件。這種設計讓搜尋引擎能夠快速找到包含特定關鍵字的所有文件，無需遍歷全部文件。

#### 索引建立流程

Elasticsearch 依賴 Lucene 維護索引，基本原理如下：

1. **分詞處理**：寫入新文件時，使用分詞器將每個欄位的值切割成關鍵字（Term）
2. **統計與映射**：建立關鍵字到文件 ID、出現頻率、位置的映射，稱為 **Posting List**

每個欄位獨立統計，並記錄兩種位置資訊：詞序位置與偏移量（關鍵字的起始位置）。

#### 關鍵字查找機制

當關鍵字數量龐大時，Elasticsearch 使用 **Term Dictionary** 來組織：

- **前綴樹（Trie Tree）**：業界成熟的字典樹結構，盡可能將關鍵字索引載入記憶體
- **FST（Finite State Transducers）**：進一步壓縮公共前綴與後綴，大幅降低記憶體開銷

查找關鍵字的過程分為兩步：

1. 根據 FST 找到對應的 Block
2. 在 Block 內遍歷找到關鍵字（若 Block 細分為 Floor Block，則先根據前綴找到 Floor Block）

### 面試準備要點

面試前需了解公司內部 Elasticsearch 相關數據：

- 部署架構：節點數量、記憶體配置
- JVM 配置：垃圾回收器選擇、停頓時間
- 客製化配置：哪些參數與預設值不同及其原因
- 效能表現：能支撐的讀寫流量

若對 Elasticsearch 效能優化有深入理解，這是重要的競爭優勢。

### 優化方案詳解

#### 優化分頁查詢

分頁查詢使用 `FROM X SIZE Y` 語法，類似 SQL 的 `OFFSET X LIMIT Y`。若查詢命中 N 個分片，資料量為 `N * (X + Y)`，偏移量越大，效能越差。

**優化方案**：

1. **Scroll / Scroll Scan**：適合一次性查詢大量資料（如資料匯出）
2. **Search After**：更通用的方案，每次查詢帶上上次返回的 `search_after` 欄位

**面試話術**：

> 我使用 Search After 優化 Elasticsearch 分頁查詢，類似分庫分表中禁用跳頁查詢的方案。查詢資料量不再與偏移量相關，只與每頁大小及命中的分片數量有關。

#### 增大刷新間隔

資料先寫入 Buffer，經過 refresh 才寫入 Page Cache。頻繁刷新會造成效能損耗。

**調整參數**：`index.refresh_interval`

**面試話術**：

> 我將 `index.refresh_interval` 調大到 30 秒，效能提升約 20%。

#### 批量提交策略

**策略一：化單個為批量**

將即時同步改為非同步批次同步，降低對 Elasticsearch 的壓力。

**實例**：資料庫資料同步到 Elasticsearch 時，從每次寫請求都操作 ES，改為每秒批次同步一次，業務方響應時間下降 50%。

**策略二：結合 Kafka 與降級機制**

- **Kafka 批次消費**：從每次消費一條訊息改為一次拉取 100 條，解決訊息積壓問題
- **降級機制**：業務繁忙時調大批次，觸發降級時依序丟棄 INFO、WARN 級別日誌

#### 優化不必要欄位

常見錯誤是將資料庫全量資料同步到 Elasticsearch，但實際需要搜尋的欄位可能只是少數。

**優化方案**：

- 只同步需要搜尋的欄位
- 查詢時先在 Elasticsearch 取得主鍵，再回資料庫查詢完整資料

**面試話術**：

> 我接手的歷史系統原本全量同步資料到 ES，佔用大量記憶體與磁碟。梳理業務後，發現僅少數欄位需要被搜尋。修改同步邏輯後，受影響的請求不足 10%，權衡之下可接受。這類似分庫分表中使用中間表支援無分庫分表鍵查詢的方案。

#### 冷熱分離

業界常用方案，根據資料存取頻率分類：

- **熱資料**：存放在高效能伺服器（SSD）
- **冷資料**：存放在廉價伺服器（HDD）

**實作方式**：使用 Elasticsearch Index Lifecycle Management（ILM）自動遷移資料。

**實例**：日誌資料三天內在熱節點，三天後遷移至冷節點，全程自動化。

### 其他常規優化

#### 優化垃圾回收

Elasticsearch 需要大堆記憶體，CMS 在超過 8G 的堆上表現較差。

**優化方案**：將垃圾回收器從 CMS 換成 G1 或 ZGC。

**面試話術**：

> 原本使用 CMS，GC 停頓時間達一百多毫秒。更換為 G1 後，停頓時間控制在 15ms 以內。目前也在調研 ZGC，其在特大堆上的表現更好。

#### 優化 Swap

Elasticsearch 對記憶體依賴嚴重，觸發 Swap 會導致效能驟降。

**優化方案**：

1. 作業系統層面禁用 Swap，或將 `vm.swappiness` 設為極小值
2. 在 Elasticsearch 設定 `bootstrap.memory_lock` 為 true

#### 調整檔案描述符

Elasticsearch 需要大量檔案描述符，建議調整至 65536 或更高。

**面試話術**：

> 曾遇過檔案描述符耗盡問題，導致多個核心業務受影響。後續除調大最大檔案描述符數量，也考慮將業務逐步遷移到不同的 Elasticsearch 叢集，確保隔離性。

### 效能優化通用思路

任何查詢優化都可從三個方向思考：

1. **優化查詢本身**：改寫 SQL、優化索引
2. **優化中介軟體**：調整參數、優化 JVM
3. **優化作業系統**：調整記憶體、網路 I/O、磁碟 I/O 相關參數

## 💡 重點摘要

- **倒排索引**是 Elasticsearch 高效搜尋的核心，透過關鍵字映射到文件，配合 FST 壓縮技術降低記憶體開銷
- **Search After** 是優化分頁查詢的關鍵方案，避免深度分頁造成的效能問題
- **批量提交**能有效降低 Elasticsearch 壓力，結合 Kafka 與降級機制可進一步提升系統韌性
- **冷熱分離**是業界標準方案，透過 ILM 自動遷移資料，兼顧效能與成本
- 效能優化可從**查詢本身、中介軟體、作業系統**三個層次系統性思考
