# 超時控制：確保用戶在預期時間內拿到響應

## 📝 課程概述
本單元深入探討超時控制的設計理念與實踐方法，說明如何透過合理的超時設置保障用戶體驗、及時釋放系統資源，並介紹鏈路超時控制方案，幫助你在面試中展現對系統可用性的深刻理解。

## 核心觀念與實作解析

### 超時控制的兩大目標

超時控制有兩個核心目標：

**一、確保客戶端在預期時間內拿到響應**

這體現了「壞響應也比沒響應好」的用戶體驗理念。當用戶發起請求後，無論成功或失敗，都應該在合理時間內獲得明確的反饋，而不是無限等待。

**二、及時釋放資源**

超時控制能夠避免資源被長時間佔用，主要影響兩類資源：

- **線程資源**：若無超時控制，線程會被持續佔用。以 Go 語言為例，協程會一直被持有而無法釋放。
- **連接資源**：包括 RPC 連接、數據庫連接等。缺乏超時控制可能導致連接洩露、線程洩露，進而引發系統故障。

### 超時控制的兩種形態

**調用超時控制**

針對單次調用設置超時時間。例如調用下游接口時，為該次調用設置 500ms 的超時限制。

**鏈路超時控制**

整條調用鏈路共用一個總超時時間。以 A → B → C 的調用鏈為例：
- 若總超時時間為 1s
- A 調用 B 的超時時間為 1s
- 若 B 收到請求時已過去 200ms，則 B 調用 C 的超時時間不能超過 800ms

鏈路超時控制在微服務架構中應用廣泛，特別是在核心服務或對響應時間有嚴格要求的場景。例如某大廠 App 首頁接口硬性規定響應時間不得超過 50ms。

### 如何確定合理的超時時間

超時時間設置過長會導致資源釋放不及時，設置過短則會導致頻繁超時、業務無法正常執行。確定超時時間的四種方法：

**一、根據用戶體驗確定**

直接諮詢產品經理，了解用戶可接受的最長等待時間。例如產品經理認為用戶最多等待 300ms，則超時時間設置為 300ms。

**二、根據響應時間確定**

使用被調用接口的 **99 線** 或 **999 線** 作為超時時間：
- **99 線**：99% 的請求響應時間都在該值以內
- **999 線**：99.9% 的請求響應時間都在該值以內

此方法需要接口接入 Prometheus 等可觀測性工具。若接口為新接口無歷史數據，則需採用其他方法。

**三、根據壓力測試確定**

通過壓測獲取被調用接口的 99 線和 999 線數據。壓測環境應盡可能接近線上環境。

**四、根據代碼計算**

分析接口代碼中的各類操作，計算響應時間：
```
接口響應時間 = 數據庫響應時間 × 3 + Redis 響應時間 + 消息發送響應時間
```
可在此基礎上增加緩衝時間。例如計算值為 200ms，可設置為 300ms。

### 超時後能否中斷業務？

**基本情況**：調用超時後，服務端通常會繼續執行，除非服務端主動檢測請求是否已超時。

**實際問題**：客戶端收到超時響應，但服務端可能已執行成功。例如：
- 用戶提交註冊，客戶端超時
- 服務端實際已成功寫入數據庫
- 用戶重試時遇到「手機號已註冊」錯誤

### 誰來監聽超時時間？

**框架客戶端監聽**
- 發起請求前已超時 → 直接返回超時響應，不發起請求
- 請求發出後觸發超時 → 返回超時錯誤給應用代碼，丟棄後續服務端響應

**框架服務端監聽**
- 收到請求時已超時 → 不調用業務代碼，直接返回超時響應
- 等待業務響應時觸發超時 → 釋放連接，丟棄後續業務響應

## 鏈路超時控制深入探討

### 超時時間如何傳遞？

超時時間通常放在協議頭中傳遞：
- RPC 協議：放在 RPC 協議頭（如 Dubbo 頭部）
- HTTP：放在 HTTP 頭部
- gRPC：基於 HTTP，同樣使用 HTTP 頭部

### 傳遞什麼值？

**方案一：剩餘超時時間**

以毫秒為單位傳遞數值（如剩餘 1000ms）。

**缺點**：服務端需減去網絡傳輸時間，但實際難以準確獲知網絡傳輸耗時。

**方案二：超時時間戳**

傳遞絕對超時時間點。

**缺點**：受時鐘同步影響。若 A、B 機器時鐘存在偏差，可能導致誤判。正常情況下時鐘偏差很小可忽略，但時鐘回撥或跨雲商場景需注意。

### 網絡傳輸時間如何計算？

**方法一**：性能測試。在模擬線上環境下，測試平均大小請求的傳輸時間，取平均值。

**方法二**：忽略不計。同機房調用傳輸時間通常小於 1ms，相較幾百毫秒的超時時間可忽略。跨機房場景則需納入計算。

### 下游服務無法滿足超時要求怎麼辦？

**正確做法**：要求下游服務優化性能，滿足鏈路超時要求。

**妥協方案**：若上游超時時間可調整，適當放寬。

## 💡 重點摘要

- 超時控制的核心目標是保障用戶體驗與及時釋放系統資源（線程、連接），避免資源洩露引發故障
- 超時時間設置需平衡用戶體驗與系統可用性，過長會資源浪費，過短會影響業務執行
- 鏈路超時控制適用於對響應時間有嚴格要求的場景，關鍵在於超時時間的傳遞與計算
- 框架客戶端與服務端均可監聽超時，提前中斷無意義的請求處理，節省資源
- 面試亮點：深入討論鏈路超時控制、協議頭傳遞機制、剩餘時間與時間戳的優劣比較
