# NoSQL 面試核心知識整合

## 📝 課程概述
本單元以面試問題為導向，系統性整理 Elasticsearch 與 MongoDB 兩大 NoSQL 技術的核心知識點。透過高可用架構設計、查詢性能優化等關鍵議題的探討，幫助學習者建立完整的 NoSQL 知識網絡，掌握面試中高頻出現的技術問題。

## 核心觀念與實作解析

### Elasticsearch 高可用架構

在面試中談論 Elasticsearch 高可用時，需要從節點角色配置到容錯機制全方位理解。

**節點角色與部署策略**

Elasticsearch 的節點可分為多種角色：主節點（Master Node）、數據節點（Data Node）、協調節點（Coordinating Node）等。一個節點確實可以同時扮演多個角色，但在生產環境中應該合理分離角色以提高穩定性。

實踐中，建議將候選主節點（Master-eligible Node）與數據節點分離部署。特別注意的是投票節點（Voting Node）的引入——投票節點參與選舉但本身不能成為主節點，這個設計是為了在大規模集群中平衡選舉效率與容錯能力。

**數據寫入流程與可靠性保障**

當一個寫入請求發送到 Elasticsearch 後，會經歷：協調節點路由 → 主分片寫入 → Translog 記錄 → 副本同步的流程。需要特別理解的是，Elasticsearch 並非實時搜索引擎，而是近實時（Near Real-time）的。

Translog 是保證數據可靠性的關鍵機制，它記錄未持久化的操作，但並不能保證數據「絕對」不丟失——這取決於 Translog 的刷盤策略配置。Commit Point 則標記了已持久化的段文件集合，是數據恢復的重要依據。

**段合併與查詢一致性**

Elasticsearch 的段（Segment）合併過程中，新查詢會自動使用合併後的段，而進行中的查詢繼續使用舊段，這通過文件句柄和引用計數機制實現無縫切換，不會影響查詢結果的一致性。

### Elasticsearch 查詢性能優化

性能優化是面試中的重點考查方向，需要從索引設計、JVM 調優、系統層面多維度思考。

**索引設計原則**

索引設計直接決定查詢效率。應該根據查詢模式設計映射（Mapping），避免不必要的字段索引，合理使用 keyword 類型與 text 類型。對於分頁查詢慢的問題，可以使用 scroll API 或 search_after 替代傳統的 from/size 分頁。

**JVM 調優與垃圾回收**

Elasticsearch 的 JVM 堆內存配置不宜超過 32GB，因為超過後會禁用壓縮指針優化。當頻繁出現 Full GC 時，需要排查是否為堆內存不足、查詢數據量過大或段文件過多。垃圾回收算法選擇上，G1 GC 在大堆內存場景下表現較好。

**系統層面優化**

文件描述符耗盡是 Elasticsearch 常見問題，因為每個段文件、網絡連接都需要文件描述符。swap 對性能影響嚴重，應該通過 `bootstrap.memory_lock: true` 鎖定內存，避免數據被交換到磁盤。

### MongoDB 高可用架構

MongoDB 的高可用建立在複製集（Replica Set）和分片集群（Sharded Cluster）兩大機制之上。

**分片機制與數據分佈**

MongoDB 通過分片鍵（Shard Key）將數據分佈到多個分片上。分片的基礎單位是塊（Chunk），當塊大小超過閾值或分片間數據不均衡時，會觸發塊遷移。負載均衡（Rebalancing）是自動進行的，確保數據均勻分佈。

配置服務器（Config Server）存儲集群元數據，是分片架構的核心組件。配置服務器本身也需要高可用，應該部署為複製集架構。

**複製機制與選舉**

MongoDB 的複製機制通過 oplog（操作日誌）實現。主節點的寫操作記錄到 oplog，從節點異步拉取並重放。oplog 的大小需要合理配置，過小可能導致從節點無法追上同步。

寫入語義（Write Concern）控制寫入可靠性級別：`w: 1`（默認，僅主節點確認）、`w: majority`（多數節點確認）、`w: all`（所有節點確認）。選擇何種語義需要在性能與可靠性間權衡。

**故障轉移與機房感知**

當主節點崩潰時，剩餘節點通過選舉產生新主節點。可以通過為節點設置優先級（Priority），讓同機房的從節點在選舉中優先成為主節點，實現機房感知的高可用架構。

### MongoDB 查詢性能優化

MongoDB 性能優化的核心在於索引策略與查詢執行理解。

**索引設計與 ESR 規則**

索引設計應遵循 ESR 規則：Equality（等值查詢）→ Sort（排序）→ Range（範圍查詢）。這個順序決定了索引字段的排列方式，確保查詢能最大化利用索引。違反 ESR 規則會導致索引掃描效率下降或需要內存排序。

**查詢執行流程**

理解查詢在 MongoDB 中的執行路徑至關重要：mongos 路由 → 確定分片 → 執行查詢 → 合併結果。mongos 作為查詢路由器，其性能會影響整體響應時間，可以通過增加 mongos 實例數量分擔負載。

**文檔設計優化**

大文檔會帶來性能問題：讀取時佔用更多內存、傳輸帶用更多帶寬、更新時產生更大 oplog。解決方案包括：嵌入文檔減少關聯查詢、字段投影只查詢必要字段、適當拆分集合。

操作系統層面的優化包括：調整 vm.swappiness 減少 swap 使用、優化文件系統（使用 XFS）、合理配置 ulimit 參數。

## 💡 重點摘要

- Elasticsearch 高可用核心在於節點角色分離、Translog 持久化機制，以及理解其近實時而非實時的特性
- Elasticsearch 查詢優化需從索引設計、JVM 調優、文件描述符管理三個層面協同考慮
- MongoDB 高可用依賴複製集與分片集群架構，寫入語務的選擇體現了性能與可靠性的權衡
- MongoDB 索引設計必須遵守 ESR 規則，這直接決定查詢是否能有效利用索引
- NoSQL 面試回答應從架構設計原理出發，結合實際場景說明技術選型的 Why 與 How
