**Q1.** 在 Kubernetes 中，應用的「版本」指的是什麼？

A) 容器镜像的标签（如 nginx:1.21-alpine）
B) Pod 的名称
C) 整个 Pod 模板的内容，使用摘要算法计算 Hash 值作为版本号
D) Deployment 的 metadata.name

<details>
<summary>答案</summary>
<b>C)</b> 在 Kubernetes 里应用的版本不仅仅是容器镜像标签，而是整个 Pod 模板的变化。即使 template 里只变动了一个字段，也会形成一个新的应用版本。Kubernetes 使用摘要算法计算 template 的 Hash 值作为版本号，Pod 名字中的那串随机字符串就是 Pod 模板的 Hash 值（版本号）。

<b>A 错误：</b>虽然镜像标签是版本的一部分，但不是完整的版本定义。修改容器名称或其他 template 字段也会触发版本更新。
<b>B 错误：</b>Pod 名称包含版本 Hash 值，但 Pod 名称本身不是版本定义。
<b>D 错误：</b>Deployment 的名称是固定标识符，不随版本更新而改变。
</details>

**Q2.** Kubernetes 滾動更新的核心特點是什麼？

A) 先销毁所有旧 Pod，再一次性创建所有新 Pod
B) 逐个创建新 Pod，同时逐个销毁旧 Pod，保证系统始终有足够数量的 Pod 运行
C) 创建新 Pod 后等待确认，然后一次性替换所有旧 Pod
D) 使用蓝绿部署策略，同时运行两个完整版本

<details>
<summary>答案</summary>
<b>B)</b> Kubernetes 的滚动更新不是一次性销毁所有旧 Pod 再创建新 Pod，而是在逐个创建新 Pod，同时也在销毁旧 Pod，保证系统里始终有足够数量的 Pod 在运行，不会有"空窗期"中断服务。这是一个"此消彼长"的过程，由 Deployment 控制的两个同步进行的"应用伸缩"操作。

<b>A 错误：</b>这会造成服务中断，不符合滚动更新的设计理念。
<b>C 错误：</b>不是等待确认后一次性替换，而是持续滚动进行。
<b>D 错误：</b>蓝绿部署需要双倍资源，Kubernetes 默认采用的是滚动更新策略。
</details>

**Q3.** 以下哪个命令用于查看 Deployment 的更新状态？

A) kubectl rollout status deployment ngx-dep
B) kubectl get deployment ngx-dep
C) kubectl describe deployment ngx-dep
D) kubectl logs deployment ngx-dep

<details>
<summary>答案</summary>
<b>A)</b> kubectl rollout status 命令专门用于查看应用更新的状态，会实时显示滚动更新的进度。它会输出更新过程中 Pod 的变化情况，直到更新完成。

<b>B 部分正确：</b>kubectl get 可以查看 Deployment 的基本信息，但不能显示更新过程的详细状态。
<b>C 部分正确：</b>kubectl describe 可以看到更多细节，包括 Pod 的变化情况，但不是专门的更新状态查看命令。
<b>D 错误：</b>kubectl logs 用于查看 Pod 的日志输出，不用于查看更新状态。
</details>

**Q4.** kubectl rollout pause 和 kubectl rollout resume 命令支持哪些对象？

A) Deployment、DaemonSet、StatefulSet
B) 仅 Deployment
C) Deployment 和 DaemonSet
D) Deployment 和 StatefulSet（1.24版本及以上）

<details>
<summary>答案</summary>
<b>B)</b> 这两个命令目前只支持 Deployment，不能用在 DaemonSet、StatefulSet 上。不过最新的 Kubernetes 1.24 版本已经支持了 StatefulSet 的滚动更新功能。

<b>A 错误：</b>DaemonSet 不支持 pause/resume 命令。
<b>C 错误：</b>DaemonSet 不支持这些命令。
<b>D 部分正确：</b>虽然 1.24 支持 StatefulSet 滚动更新，但题目没有明确版本，且 pause/resume 功能在 StatefulSet 上的支持情况需要确认文档。
</details>

**Q5.** annotations 和 labels 的主要区别是什么？

A) annotations 用于筛选对象，labels 用于记录详细信息
B) annotations 是给 Kubernetes 内部对象使用的扩展属性，labels 是给外部用户筛选、过滤对象使用的
C) annotations 和 labels 功能完全相同，只是名称不同
D) annotations 只能用于 Deployment，labels 可以用于所有对象

<details>
<summary>答案</summary>
<b>B)</b> annotations 字段给 Kubernetes 内部的各种对象使用，像是"扩展属性"；labels 主要面对 Kubernetes 外部的用户，用来筛选、过滤对象。比喻来说：annotations 是包装盒里的产品说明书，labels 是包装盒外的标签贴纸。

<b>A 错误：</b>说反了，labels 用于筛选，annotations 用于扩展信息。
<b>C 错误：</b>两者的用途有明确区别。
<b>D 错误：</b>两者都可以用于多种 Kubernetes API 对象。
</details>

## 第二部分：是非題（每題 3 分，共 15 分）

**Q6.** Pod 名字中包含的随机字符串（如 "6796..."）是 Pod 模板的 Hash 值，也就是 Pod 的"版本号"。 _(True/False)_

<details>
<summary>答案</summary>
<b>True</b> - 在 Kubernetes 里，Pod 名字里的那串随机数就是 Pod 模板的 Hash 值，由摘要算法计算 template 内容得出，作为 Pod 的"版本号"。当 template 内容变化时，Hash 值也会改变，Pod 名字就会不同，表示版本已更新。
</details>

---

**Q7.** minReadySeconds 字段属于 Pod 模板的一部分，因此会影响应用的版本号。 _(True/False)_

<details>
<summary>答案</summary>
<b>False</b> - minReadySeconds 字段不属于 Pod 模板（template），它是在 Deployment 的 spec 层级，用于设置确认 Pod 就绪的等待时间。因为它不改变 template 内容，所以不会影响 Pod 的版本号（Hash 值）。这个字段主要用于控制滚动更新的节奏，让 Kubernetes 在创建新 Pod 后等待一段时间，确认 Pod 运行正常再继续更新。
</details>

---

**Q8.** kubectl rollout undo 命令的本质仍然是滚动更新，只是使用旧版本的 Pod 模板。 _(True/False)_

<details>
<summary>答案</summary>
<b>True</b> - kubectl rollout undo 的操作过程和 kubectl apply 是一样的，执行的仍然是"滚动更新"，只不过使用的是旧版本 Pod 模板，把新版本 Pod 数量收缩到 0，同时把老版本 Pod 扩展到指定值。整个过程仍然是"此消彼长"的滚动更新过程，只是版本号变化方向相反。
</details>

---

**Q9.** Deployment 直接控制 Pod 的创建和管理。 _(True/False)_

<details>
<summary>答案</summary>
<b>False</b> - Deployment 并不是直接控制 Pod。Pod 的归属对象是 ReplicaSet（RS）。Deployment 控制 ReplicaSet，ReplicaSet 再控制 Pod 的数量。版本这个概念可以等同于是 ReplicaSet。可以通过 kubectl get rs 查看 ReplicaSet 信息，每个 ReplicaSet 对应一个版本。
</details>

---

**Q10.** 在滚动更新过程中，新旧版本的 Pod 会共存一段时间，这段时间内它们共同对外提供服务。 _(True/False)_

<details>
<summary>答案</summary>
<b>True</b> - 在滚动更新过程中，新版本 Pod 数量逐渐增加，旧版本 Pod 数量逐渐减少，这个过程是渐进的，存在新旧版本 Pod 共存的阶段。好处是可以不间断对外提供服务，但确实线上会暂时存在不同版本的问题。这是滚动更新策略的设计权衡，优先保证服务的可用性。
</details>

## 第三部分：填空題（每題 5 分，共 20 分）

**Q11.** Kubernetes 使用 **\_\_\_\_\_** 算法计算 Pod template 的 Hash 值作为应用版本号，Pod 名字中的随机字符串就是这个 Hash 值。

<details>
<summary>答案</summary>
<b>摘要算法</b>（或哈希算法、摘要功能）

Kubernetes 使用摘要（Hash）算法计算 template 的内容，生成一个 Hash 值作为"版本号"。虽然这个 Hash 值不太方便人工识别，但是很实用，能够准确标识 Pod 模板的任何变化。即使 template 里只变动了一个字段，Hash 值也会完全不同，形成新的版本。
</details>

**Q12.** 滚动更新是由 Deployment 控制的两个同步进行的 **\_\_\_\_\_** 操作，老版本缩容到 0，同时新版本扩容到指定值。

<details>
<summary>答案</summary>
<b>"应用伸缩"</b>（或应用扩缩容、扩缩容）

滚动更新的本质就是两个同时进行的扩缩容操作：一个是对旧版本的缩容（减少 Pod 数量），另一个是对新版本的扩容（增加 Pod 数量）。这两个操作同步进行，形成"此消彼长"的效果，保证整个更新过程中始终有足够的 Pod 提供服务。
</details>

**Q13.** 要在 Deployment 的更新历史中添加版本说明信息，需要在 metadata 中添加 **\_\_\_\_\_** 字段。

<details>
<summary>答案</summary>
<b>annotations.kubernetes.io/change-cause</b>

通过在 Deployment 的 metadata.annotations 中添加 kubernetes.io/change-cause 字段，可以为每次更新添加说明信息。例如：kubernetes.io/change-cause: "v1, ngx=1.21"。这样在 kubectl rollout history 命令的输出中，CHANGE-CAUSE 列就会显示这些说明，而不是默认的 <none>。
</details>

<summary>答案</summary>

## 第四部分：簡答題（每題 10 分，共 30 分）

**Q15.** 解释 Kubernetes 滚动更新过程中 Pod 数量变化的详细步骤，假设从 V1 版本（4个Pod）更新到 V2 版本。

<details>
<summary>答案</summary>
<b>滚动更新 Pod 数量变化过程：</b>

**初始状态：**
- V1 Pod（如 ngx-dep-54b865d75）数量：4

**第一步：**
- 创建 1 个 V2 Pod（如 ngx-dep-d575d5776）
- V1 Pod 数量减少到 3
- 系统中总 Pod 数量：4（3个V1 + 1个V2）

**第二步：**
- V2 Pod 数量增加到 2
- V1 Pod 数量减少到 2
- 系统中总 Pod 数量：4（2个V1 + 2个V2）

**第三步：**
- V2 Pod 数量增加到 3
- V1 Pod 数量减少到 1
- 系统中总 Pod 数量：4（1个V1 + 3个V2）

**最终状态：**
- V2 Pod 数量达到预期值 4
- V1 Pod 数量变为 0
- 更新过程完成

<b>关键要点：</b>
- 整个过程保证始终有足够数量的 Pod 运行（不会少于期望值）
- 新 Pod 数量增加像"滚雪球"，越滚越大
- 这是一个"此消彼长"的渐进过程
- 没有"空窗期"，服务不会中断
</details>

**Q16.** 比较 Kubernetes 的"滚动更新"与"灰度发布"（金丝雀发布）的相同点和不同点。

<details>
<summary>答案</summary>
<b>相同点：</b>

1. <b>渐进式更新：</b>两者都是渐进式的发布方式，不是一次性替换所有实例
2. <b>版本共存：</b>更新过程中都存在新旧版本共存的情况
3. <b>降低风险：</b>都能降低发布风险，避免一次性发布导致的全面故障
4. <b>可回滚：</b>都可以在发现问题时进行回滚操作

<b>不同点：</b>

1. <b>本质定位：</b>
   - 滚动更新是 Kubernetes 的<b>能力</b>（内置功能）
   - 灰度发布是<b>发布策略</b>（业务层面的功能）

2. <b>流量控制：</b>
   - 滚动更新：Pod 数量逐步变化，但流量通常平均分配给所有 Pod
   - 灰度发布：可以精确控制流量比例（如 5%、10%、20%...），按比例引流到新版本

3. <b>版本比例：</b>
   - 滚动更新：新旧版本 Pod 数量是"此消彼长"，最终完全替换
   - 灰度发布：可以长期保持小比例的新版本运行，进行观察验证

4. <b>应用场景：</b>
   - 滚动更新：适合常规版本升级，快速完成替换
   - 灰度发布：适合重大功能更新、风险较高的版本，需要逐步验证

5. <b>Kubernetes 实现：</b>
   - 滚动更新：Deployment 默认策略
   - 灰度发布：需要结合 Service、Ingress 等实现流量分流

<b>总结：</b>Kubernetes 基于滚动更新的能力，可以实现 Pod 的水平扩展/收缩，从而能够提供类似灰度发布、金丝雀发布的功能，但两者在控制粒度和应用场景上有明显区别。
</details>

**Q17.** 直接部署旧版本的 YAML 文件也可以实现版本回退，那么使用 kubectl rollout undo 命令的优势是什么？

<details>
<summary>答案</summary>
<b>kubectl rollout undo 相比直接部署旧 YAML 的优势：</b>

<b>1. 版本快照保证正确性：</b>
- kubectl rollout history 中的每个版本就像代码库的 tag，是类似快照文件的存在
- 快照信息正确记录了当时的完整配置状态，包括镜像、标签、环境变量、存储卷等所有细节
- 通过版本回退能最大限度保证正确性，Kubernetes 已经确保这些信息的完整性
- 而直接部署旧 YAML 文件，无法保证该文件在之后是否被修改过，存在变数

<b>2. 降低部署风险：</b>
- 使用旧 YAML 部署，如果文件内容已被改动（甚至可能是错误的改动），会造成部署风险
- 版本历史中的快照是经过验证的配置，使用 undo 可以精确还原到之前的正确状态
- 避免因配置文件意外修改导致的二次故障

<b>3. 运维管理语义明确：</b>
- kubectl rollout undo 明确表达了"版本回退"的操作意图
- 利于运维团队理解和管理操作历史
- 在审计日志、操作记录中清晰体现回退行为
- 直接部署旧 YAML 只是普通的"应用更新"，不体现回退语义

<b>4. 操作便捷性：</b>
- 不需要重新准备或查找旧的 YAML 文件
- 可以通过 --to-revision 参数精确指定任意历史版本
- kubectl rollout history 可以快速查看所有版本及其详细信息
- 一个命令完成回退，操作流程简单清晰

<b>5. 配置一致性：</b>
- 版本快照包含当时所有的配置细节，不会遗漏
- 避免 YAML 文件版本不一致、字段缺失等问题
- 确保回退后的配置与历史版本完全一致

<b>总结：</b>虽然两种方式最终效果相同（都是滚动更新），但 kubectl rollout undo 通过版本快照机制提供了更高的可靠性、安全性和运维可管理性，是更推荐的版本回退方式。
</details>

## 第五部分：配對題（共 10 分）

**Q18.** 将以下 kubectl rollout 子命令与其功能描述进行匹配：

| 命令 | 功能描述 |
|------|---------|
| 1. kubectl rollout status | A. 查看更新历史记录 |
| 2. kubectl rollout pause | B. 继续暂停的更新过程 |
| 3. kubectl rollout history | C. 实时查看更新进度 |
| 4. kubectl rollout undo | D. 暂停正在进行的更新 |
| 5. kubectl rollout resume | E. 回退到历史版本 |

<details>
<summary>答案</summary>
<b>1-C, 2-D, 3-A, 4-E, 5-B</b>

<b>详细说明：</b>

<b>1-C：</b>kubectl rollout status 用于实时查看应用更新的状态，显示滚动更新的进度，直到更新完成。

<b>2-D：</b>kubectl rollout pause 用于暂停正在进行的更新，可以检查、修改 Pod，或进行测试验证。

<b>3-A：</b>kubectl rollout history 用于查看更新历史记录，显示版本列表。可以加 --revision 参数查看特定版本详细信息。

<b>4-E：</b>kubectl rollout undo 用于回退到历史版本。默认回退到上一个版本，也可以用 --to-revision 参数指定任意版本。

<b>5-B：</b>kubectl rollout resume 用于继续之前暂停的更新过程，让滚动更新继续进行。

<b>注意事项：</b>
- pause 和 resume 命令目前只支持 Deployment
- Kubernetes 1.24 版本开始支持 StatefulSet 的滚动更新
- 这些命令为运维人员提供了精细的更新控制能力
</details>
