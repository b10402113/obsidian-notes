## Section A: 多項選擇題 (每題 5 分)

**Q1.** Kubernetes 中名字空間（Namespace）的主要作用是什麼？

A) 提高容器運行性能
B) 在集群中創建邏輯上的區域，實現資源和對象的隔離
C) 增加節點的物理存儲容量
D) 自動擴展集群的計算資源

<details>
<summary>答案</summary>
<b>B)</b> 名字空間是一個邏輯概念，可以把集群切分成彼此獨立的區域，實現資源隔離，避免命名衝突和資源爭搶。選項A、C、D都與名字空間的核心功能無關。
</details>

---

**Q2.** 在 Kubernetes 中，要將一個 Pod 放入特定的名字空間，需要在 Pod 的配置中添加哪個字段？

A) 在 spec 中添加 namespace 字段
B) 在 metadata 中添加 namespace 字段
C) 在 status 中添加 namespace 字段
D) 在 labels 中添加 namespace 字段

<details>
<summary>答案</summary>
<b>B)</b> 必須在 metadata 字段中添加 namespace，指定該對象所屬的名字空間。其他選項都不是正確的位置。
</details>

---

**Q3.** 當刪除一個名字空間時，該名字空間內的所有對象會發生什麼變化？

A) 對象會被自動移動到 default 名字空間
B) 對象會被保留，但無法訪問
C) 對象會一起被刪除
D) 對象會被標記為待刪除狀態

<details>
<summary>答案</summary>
<b>C)</b> 因為名字空間里的對象都從屬於名字空間，一旦名字空間被刪除，它里面的所有對象也會消失。這是 Kubernetes 的設計特性，需要特別小心。
</details>

---

**Q4.** ResourceQuota API 象的簡稱是什麼？可以通過哪個命令查看？

A) 簡稱是 rq，使用 kubectl api-resources 查看
B) 簡稱是 quota，使用 kubectl api-resources 查看
C) 簡稱是 res，使用 kubectl get quota 查看
D) 簡稱是 ns，使用 kubectl get ns 查看

<details>
<summary>答案</summary>
<b>B)</b> ResourceQuota 的簡稱是 quota，可以使用 kubectl api-resources 查看所有 API 資源的簡稱。選項A、C的簡稱錯誤，選項D查看的是名字空間。
</details>

---

**Q5.** 在 ResourceQuota 中，要限制名字空間中可以創建的 Pod 數量，應該使用哪個字段？

A) maxPods
B) podCount
C) pods
D) count/pods

<details>
<summary>答案</summary>
<b>C)</b> 核心對象配額使用對象的名字（英語複數形式），如 pods、configmaps、secrets、services。選項A和B不是標準字段，選項D是其他 API 對象的格式。
</details>

---

**Q6.** LimitRange 對象的主要作用是什麼？

A) 為名字空間設置全局資源配額
B) 為 API 象添加默認的資源配額限制
C) 監控集群的資源使用情況
D) 自動擴展節點的容量

<details>
<summary>答案</summary>
<b>B)</b> LimitRange 能為 API 對象添加默認的資源配額限制，當 Pod 沒有明確設置 resources 字段時，可以自動為其添加默認值，省去反复設置配額的煩心事。選項A是 ResourceQuota 的功能。
</details>

## Section B: 是非題 (每題 3 分)

**Q7.** Kubernetes 的名字空間是一個實體對象，會在集群中創建實際的物理隔離。 _(True/False)_

<details>
<summary>答案</summary>
<b>False</b> - Kubernetes 的名字空間不是實體對象，只是一個邏輯上的概念。它可以把集群切分成彼此獨立的區域，實現類似容器技術里 namespace 的隔離效果，但並不創建物理隔離。
</details>

---

**Q8.** 在名字空間添加資源配額限制後，所有在其中運行的 Pod 都必須用 resources 字段聲明資源需求，否則無法創建。 _(True/False)_

<details>
<summary>答案</summary>
<b>True</b> - 如果 Pod 沒有 resources 字段，就可以無限制使用 CPU 和内存，這與名字空間的資源配額相衝突。為了保證資源總量可管可控，Kubernetes 會拒絕創建這樣的 Pod。
</details>

---

**Q9.** 要查看其他名字空間中的對象，可以使用 kubectl get 命令而不需要指定 -n 參數。 _(True/False)_

<details>
<summary>答案</summary>
<b>False</b> - kubectl get 默認查看的是 default 名字空間，想要操作其他名字空間的對象必須用 -n 參數明確指定，如 kubectl get pod -n test-ns。
</details>

---

**Q10.** Kubernetes 初始化集群時預設的 4 個名字空間是：default、kube-system、kube-public、kube-node-lease。 _(True/False)_

<details>
<summary>答案</summary>
<b>True</b> - Kubernetes 初始化集群時會預設這 4 個名字空間。default 是用戶對象默認的名字空間，kube-system 是系統組件所在的名字空間，kube-public 和 kube-node-lease 也有各自的用途。
</details>

---

**Q11.** ResourceQuota 可以限制名字空間中 PVC 的存儲總量和 PVC 的數量。 _(True/False)_

<details>
<summary>答案</summary>
<b>True</b> - ResourceQuota 可以使用 requests.storage 限制 PVC 的存儲總量，也可以用 persistentvolumeclaims 限制 PVC 的個數，實現全面的存儲配額控制。
</details>

## Section C: 填空題 (每題 4 分)

**Q12.** Kubernetes 的名字空間可以把集群切分成 **\_\_\_\_\_\_** 的區域，實現類似容器技術里 namespace 的 **\_\_\_\_\_\_** 效果。

<details>
<summary>答案</summary>
<b>彼此獨立，隔離</b> 名字空間把集群切分成彼此獨立的區域，實現隔離效果，應用只能在自己的名字空間里分配資源和運行，不會干擾其他名字空間。
</details>

---

**Q13.** ResourceQuota 對象必須依附在某個名字空間上，所以在它的 **\_\_\_\_\_\_** 字段里必須明確寫出 **\_\_\_\_\_\_**。

<details>
<summary>答案</summary>
<b>metadata，namespace</b> ResourceQuota 必須在 metadata 字段中指定 namespace，否則就會應用到 default 名字空間。
</details>

---

**Q14.** 在 LimitRange 中，**\_\_\_\_\_\_** 字段是默認的資源上限，對應容器里的 resources.limits；**\_\_\_\_\_\_** 字段是默認申請的資源，對應容器里的 resources.requests。

<details>
<summary>答案</summary>
<b>default，defaultRequest</b> default 字段設置默認的資源上限（limits），defaultRequest 字段設置默認申請的資源（requests），這兩個字段只適用於 Container 類型。
</details>

**Q15.** 在 ResourceQuota 中，限制其他 API 象配額需要使用 **\_\_\_\_\_\_** 的形式，例如 count/jobs.batch、**\_\_\_\_\_\_**。

<details>
<summary>答案</summary>
<b>count/name.group，count/deployments.apps</b> 其他 API 對象配額使用 count/name.group 的形式，如 count/jobs.batch、count/cronjobs.batch、count/deployments.apps。
</details>

## Section D: 簡答題 (每題 8 分)

**Q16.** 請解釋為什在大規模 Kubernetes 集群中需要使用名字空間？它解決了哪些問題？

<details>
<summary>答案</summary>
在大規模集群中，會有非常多的用戶創建各式各樣的應用，可能有百萬數量級別的 Pod，使得：

<b>問題 1：命名衝突概率增加</b>
不同團隊可能使用相同名稱（如"Web"），導致名稱被占用，其他團隊無法使用。

<b>問題 2：資源爭搶</b>
某個團隊的應用可能消耗過多資源，導致其他團隊無法正常工作。

<b>解決方案：</b>
名字空間將集群"局部化"，為每類用戶創建專屬"工作空間"，避免衝突和爭搶。

<b>比喻：</b>
Kubernetes 是大牧場，API 對象是雞鸭牛羊，名字空間是圈養的圍栏，有效、安全地利用集群資源。
</details>

---

**Q17.** ResourceQuota 可以限制哪些類型的資源？請列舉至少 4 類並說明具體字段。

<details>
<summary>答案</summary>
<b>1. CPU 和内存配額：</b>
- requests.cpu：Pod 的 CPU 需求總量
- requests.memory：Pod 的内存需求總量
- limits.cpu：Pod 的 CPU 上限總量
- limits.memory：Pod 的内存上限總量

<b>2. 存儲容量配額：</b>
- requests.storage：PVC 的存儲總量
- persistentvolumeclaims：PVC 的個數

<b>3. 核心對象配額：</b>
- pods：Pod 數量
- configmaps：ConfigMap 數量
- secrets：Secret 數量
- services：Service 數量

<b>4. 其他 API 對象配額：</b>
- count/jobs.batch：Job 數量
- count/cronjobs.batch：CronJob 數量
- count/deployments.apps：Deployment 數量

<b>關鍵要點：</b>
核心對象使用複數形式，其他 API 象使用 count/name.group 格式。
</details>

**Q18.** 說明 LimitRange 對象中 type 字段可以設置哪些值，以及每種類型的用途。

<details>
<summary>答案</summary>
LimitRange 的 type 字段可以設置三種值：

<b>1. Container（容器級別）：</b>
- 用途：為容器設置默認資源配額
- 可用字段：default（默認上限）、defaultRequest（默認申請）
- 作用：當容器沒有 resources 字段時自動添加默認值

<b>2. Pod（Pod 級別）：</b>
- 用途：限制 Pod 的資源使用上限
- 可用字段：max、min
- 作用：設置 Pod 能使用的資源最大最小值

<b>3. PersistentVolumeClaim（PVC 級別）：</b>
- 用途：限制 PVC 的存儲請求範圍
- 可用字段：max、min
- 作用：控制 PVC 可以申請的存儲容量範圍

<b>使用場景：</b>
Container 最常用，可以省去为每個容器手動設置 resources 的麻煩。
</details>

| -------- | -------- |
| 1. default | A. 系統組件所在的名字空間 |
