**Q1.** 在使用 kubeadm 安裝 Kubernetes Master 節點之前，需要完成哪四項準備工作？

A) 安裝 Docker、修改主機名、設置時區、配置防火牆
B) 修改主機名、修改 Docker 配置、修改網絡設置、關閉交換分區
C) 創建用戶帳號、安裝依賴包、配置 SSH、設置環境變量
D) 下載鏡像、配置倉庫、安裝工具、啟動服務

<details>
<summary>答案</summary>
<b>B) 修改主機名、修改 Docker 配置、修改網絡設置、關閉交換分區</b>

這四項準備工作是 Kubernetes 集群正常運行的基礎：
- 修改主機名：便於識別和管理節點
- 修改 Docker 配置：將 cgroup 驅動改為 systemd，與 Kubernetes 保持一致
- 修改網絡設置：啟用 br_netfilter 模塊，確保網絡正常工作
- 關閉交換分區：Kubernetes 要求關閉 swap 以保證性能穩定
</details>

**Q2.** 使用 kubeadm init 初始化 Master 節點時，參數 `--pod-network-cidr=10.10.0.0/16` 的作用是什麼？

A) 指定 Kubernetes API Server 的 IP 地址範圍
B) 指定 Pod 的 IP 地址範圍，供網絡插件使用
C) 指定 Service 的虛擬 IP 地址範圍
D) 指定節點的 IP 地址範圍

<details>
<summary>答案</summary>
<b>B) 指定 Pod 的 IP 地址範圍，供網絡插件使用</b>

這個參數定義了 Pod 網絡的 CIDR 地址範圍，Flannel 等網絡插件會根據這個範圍為 Pod 分配 IP 地址。在安裝 Flannel時，YAML文件中的 net-conf.json 也必須配置相同的網絡範圍，否則網絡將無法正常工作。
</details>

**Q3.** 為什麼 Master 節點初始化完成後，節點狀態會顯示為 "NotReady"？

A) Kubernetes API Server 尚未啟動
B) 還未安裝網絡插件
C) Worker 節點尚未加入集群
D) Docker 服務未正常運行

<details>
<summary>答案</summary>
<b>B) 還未安裝網絡插件</b>

節點狀態為 "NotReady" 表示節點的基本功能已啟動，但網絡功能尚未就緒。只有安裝了 Flannel 等網絡插件後，Pod 才能獲得 IP 地址並進行網絡通信，節點狀態才會變為 "Ready"。
</details>

**Q4.** 在創建 Deployment 的 YAML 文件時，以下哪個命令可以生成樣板文件？

A) `kubectl run ngx --image=nginx:alpine --dry-run=client -o yaml`
B) `kubectl create deploy ngx-dep --image=nginx:alpine --dry-run=client -o yaml`
C) `kubectl apply -f deploy.yml --dry-run=client`
D) `kubectl get deploy ngx-dep -o yaml`

<details>
<summary>答案</summary>
<b>B) kubectl create deploy ngx-dep --image=nginx:alpine --dry-run=client -o yaml</b>

`kubectl create deploy` 命令配合 `--dry-run=client -o yaml` 參數可以在不實際創建對象的情況下生成 YAML樣板文件。這是一個常用的技巧，可以避免手寫 YAML 文件時出現格式錯誤。視頻中將這兩個參數設為環境變量 `out` 以簡化命令輸入。
</details>

**Q5.** DaemonSet 與 Deployment 的主要區別是什麼？

A) DaemonSet 可以自動擴縮容，Deployment 不能
B) DaemonSet 在每個節點上只運行一個 Pod副本，Deployment 可以運行任意數量的副本
C) DaemonSet 不支持使用鏡像，Deployment 支持
D) DaemonSet 只能在 Master 節點運行，Deployment 只能在 Worker 節點運行

<details>
<summary>答案</summary>
<b>B) DaemonSet 在每個節點上只運行一個 Pod副本，Deployment 可以運行任意數量的副本</b>

DaemonSet 的設計目的是確保在集群的每個節點上都運行一個指定的 Pod副本，通常用於系統級服務（如日誌收集、監控代理）。Deployment則可以指定 replicas 數量，Pod 可能集中在部分節點上運行，不一定覆蓋所有節點。
</details>

**Q6.** 在 DaemonSet 的 YAML 文件中添加 `tolerations` 字段的目的是什麼？

A) 提高 Pod 的資源限制
B) 允許 Pod 在 Master 節點上運行，容忍節點的污點
C) 增加 Pod 的副本數量
D) 配置 Pod 的網絡策略

<details>
<summary>答案</summary>
<b>B) 允許 Pod 在 Master 節點上運行，容忍節點的污點</b>

Master 節點默認有一個污點 `node-role.kubernetes.io/master:NoSchedule`，普通Pod 不會被調度到Master節點。通過添加 tolerations字段，DaemonSet 的Pod 可以"容忍"這個污點，從而在Master節點上也能運行，確保覆蓋集群的所有節點。
</details>

**Q7.** Service 的 ClusterIP類型與 NodePort類型的主要區別是什麼？

A) ClusterIP 只能在集群內部訪問，NodePort 可以從集群外部訪問
B) ClusterIP 使用固定端口，NodePort 使用隨機端口
C) ClusterIP 不支持負載均衡，NodePort 支持
D) ClusterIP 只能用於 Deployment，NodePort 只能用於 DaemonSet

<details>
<summary>答案</summary>
<b>A) ClusterIP 只能在集群內部訪問，NodePort 可以從集群外部訪問</b>

ClusterIP 是 Service 的默認類型，分配一個虛擬IP地址，只能在集群內部通過域名或 IP訪問。NodePort類型會在每個節點上開放一個端口（默範圍 30000-32767），外部客戶端可以通過任意節點的IP地址加該端口訪問Service，從而實現對外暴露服務。
</details>

**Q8.** 在 Kubernetes 中，Service 如何實現對後端 Pod 的負載均衡？

A) 通過配置文件手動指定每個 Pod 的權重
B) Service 自動使用 iptables 或 IPVS規則，隨機或轮询分发流量
C) 依賴外部負載均衡器設備
D) Pod 自行協商處理請求

<details>
<summary>答案</summary>
<b>B) Service 自動使用 iptables 或 IPVS規則，隨機或轮询分发流量</b>

Service 通過標籤選擇器（selector）找到匹配的後端 Pod，然後自動配置 iptables 或 IPVS規則，將流量分發到這些 Pod。在視頻演示中，多次執行 `curl ngx-svc` 可以看到請求被分發到不同的Pod，證明負載均衡功能正常工作。
</details>

**Q9.** Ingress 與 Ingress Controller 的關係是什麼？

A) Ingress Controller 是 Ingress 的子對象
B) Ingress 定義路由規則，Ingress Controller 實現這些規則並處理實際流量
C) Ingress 和 Ingress Controller 是同一個對象的不同名稱
D) Ingress Controller管理 Ingress 的生命周期

<details>
<summary>答案</summary>
<b>B) Ingress 定義路由規則，Ingress Controller 實現這些規則並處理實際流量</b>

Ingress 是 Kubernetes 的 API對象，定義了域名、路徑到Service的映射規則。Ingress Controller 是實際運行的應用（如 Nginx Ingress Controller），它監聽 Ingress對象，將路由規則配置到Nginx 等反向代理中，然後處理外部流量並轉發到後端 Service。
</details>

**Q10.** 在 Ingress Controller 的 YAML 文件中，參數 `-ingress-class=ngx-ink` 的作用是什麼？

A) 定義 Ingress Controller 的名稱
B) 指定 Ingress Controller 要監聽的 Ingress Class，實現多個Ingress Controller 的區分
C) 配置 Ingress Controller 的負載均衡算法
D) 設置 Ingress Controller 的健康檢查端口

<details>
<summary>答案</summary>
<b>B) 指定 Ingress Controller 要監聽的 Ingress Class，實現多個Ingress Controller 的區分</b>

當集群中有多個 Ingress Controller時，每個 Ingress Controller 通過 -ingress-class 參數指定自己負責的 Ingress Class。只有 Ingress對象的 ingressClassName字段與之匹配時，該 Ingress Controller才會處理這個路由規則。這樣可以在同一集群中運行多個不同的Ingress Controller，各自處理不同的流量。
</details>

**Q12.** Worker 節點加入集群後，可以直接使用 kubectl命令管理集群，無需額外配置。 _(True/False)_

<details>
<summary>答案</summary>

**Q13.** DaemonSet 的 YAML 文件中必須包含 replicas字段，定義要運行的副本數量。 _(True/False)_

<details>
<summary>答案</summary>
<b>False</b>

DaemonSet 不需要 replicas字段，因為它的特性是自動在每個節點上運行一個 Pod。 replicas字段是 Deployment特有的，用於指定 Pod 的副本數量。視頻中從 Deployment生成DaemonSet樣板時，特意用 `sed -e '/replicas/d'` 刪除了這個字段。
</details>

**Q14.** Service 的域名格式可以是 `ngx-svc.default.svc.cluster.local`，其中包含了名稱空間和集群域名後綴。 _(True/False)_

<details>
<summary>答案</summary>
<b>True</b>

Kubernetes 為Service 提供了完整的域名格式：`<service-name>.<namespace>.svc.cluster.local`。這是標準的 DNS 域名，可以在集群內任意位置使用。簡寫形式 `ngx-svc` 或 `ngx-svc.default` 也能正常解析，Kubernetes DNS會自動補充後綴部分。
</details>

**Q15.** Ingress 可以直接將外部流量轉發到 Pod，不需要 Service作為中介。 _(True/False)_

<details>
<summary>答案</summary>
<b>False</b>

Ingress 的路由規則只能指向 Service，不能直接指向 Pod。Ingress 接收外部流量後，根據域名和路徑匹配，轉發到對應的Service，然後 Service再負載均衡到後端的 Pod。這樣的設計保證了架構的層次清晰，Service提供了穩定的抽象層，Pod 的變化不會影響Ingress的配置。
</details>

**Q18.** 在安裝 Flannel網絡插件時，YAML文件中的 **\_\_\_\_\_\_\_\_\_**字段配置必須與 kubeadm init的 **\_\_\_\_\_\_\_\_\_**參數保持一致，否則 Pod網絡將無法正常工作。

<details>
<summary>答案</summary>
<b>net-conf.json 中的 Network、--pod-network-cidr</b>

Flannel 的 YAML 文件中，net-conf.json部分的 Network字段定義了 Pod 網絡的地址範圍（如 "10.10.0.0/16"）。這個範圍必須與 kubeadm init時指定的--pod-network-cidr參數完全一致，否則Flannel 分配的IP地址與 Kubernetes預期的範圍不匹配，Pod 之間將無法通信。
</details>

## 第四部分：簡答題 (每題 8 分)

**Q19.** 說明在 Kubernetes集群中使用 kubectl scale 命令擴展 Deployment 的過程，以及這個操作與手動修改 YAML文件再 apply 的區別。

<details>
<summary>答案</summary>

<b>kubectl scale命令直接修改運行中的 Deployment對象的 replicas字段，立即觸發控制器創建新的 Pod副本：</b>
```bash
kubectl scale --replicas=5 deploy ngx-dep
```

<b>區別：</b>
- **kubectl scale**：直接操作，立即生效，不改變YAML源文件，適合臨時調整或測試
- **修改 YAML 再 apply**：更新源文件，保持聲明式配置的一致性，適合生產環境的正式更新，配置變化會被記錄和追溯

<b>最佳實踐：</b>
生產環境應優先使用修改YAML文件的方式，確保配置可追溯、可復現。kubectl scale 適合快速測試或臨時應對流量高峰，但要注意後續可能需要同步更新YAML文件。

<b>關鍵點：</b>
- kubectl scale 直接修改 etcd 中的對象狀態
- YAML apply 是聲明式更新，保持"配置即代碼"的理念
- 兩種方式觸發的控制器行為相同，但管理方式不同
</details>

**Q20.** 在 WordPress部署示例中，為什麼需要為MariaDB 和WordPress 分別創建 Service對象？Service 在這個架構中起到了什麼作用？

<details>
<summary>答案</summary>

<b>Service的作用：</b>

<b>1. 為 MariaDB創建 Service：</b>
- 提供穩定的訪問入口：Pod 的IP地址可能變化（如重建、重啟），Service 提供固定的虛擬IP或域名
- 解耦配置：WordPress ConfigMap中使用域名`mariasvc`而非固定IP，配置更穩定靈活
- 支持負載均衡：如果未來 MariaDB擴展為多副本，Service 可自動分發請求

<b>2. 為 WordPress創建 Service：</b>
- 集群內部訪問：其他服務或Pod 可以通過域名訪問WordPress
- NodePort對外暴露：設置 NodePort類型，指定端口 30088，外部用戶可以通過節點IP+端口訪問WordPress

<b>3. 架構意義：</b>
- **抽象層**：Service屏蔽了Pod 的動態性，提供穩定的服務端點
- **域名解析**：Kubernetes DNS自動為 Service分配域名，簡化配置
- **微服務架構**：Service是微服務間通信的基礎，支持服務發現和負載均衡

<b>關鍵點：</b>
- MariaDB使用 ClusterIP類型（默範），只在集群內部可訪問
- WordPress使用NodePort類型，對外暴露服務
- Service 域名格式：`<service-name>.<namespace>.svc.cluster.local`
</details>

**Q21.** 將以下 Kubernetes對象與其主要功能進行配對：

|對象|功能|
|---|---|
|1. Deployment|A. 在每個節點上運行一個Pod副本|
|2. DaemonSet|B. 定義外部流量到Service的路由規則|
|3. Service|C. 管理應用的副本數量，支持滾動更新|
|4. Ingress|D. 提供服務發現和負載均衡|

<details>
<summary>答案</summary>
<b>1-C, 2-A, 3-D, 4-B</b>

<b>配對解釋：</b>
- **Deployment**：最常用的控制器，管理 Pod副本數量，支持滾動更新、回滾等運維操作，適合無狀態應用
- **DaemonSet**：確保每個節點運行一個 Pod，適合系統級服務（日誌收集、監控代理、網絡插件）
- **Service**：為Pod提供穩定的訪問入口，實現服務發現和負載均衡，支持ClusterIP、NodePort、LoadBalancer類型
- **Ingress**：管理集群入口流量，基於域名和路徑路由到不同Service，支持 TLS、虛擬主機等進階功能
</details>

**Q22.** 將以下命令與其用途進行配對：

|命令|用途|
|---|---|
|1. kubectl apply -f file.yml|A. 生成YAML樣板文件，不實際創建對象|
|2. kubectl get pod -o wide|B. 列出對象並顯示詳細信息（如節點名、IP）|
|3. kubectl create deploy --dry-run=client -o yaml|C. 執行端口映射，將本地端口映射到Pod|
|4. kubectl port-forward pod-name local:remote|D. 創建或更新YAML文件中定義的Kubernetes對象|

<details>
<summary>答案</summary>
<b>1-D, 2-B, 3-A, 4-C</b>

<b>配對解釋：</b>

- **kubectl get pod -o wide**：列出 Pod並顯示額外信息，包括運行的節點、IP地址，方便排查問題
- **kubectl create --dry-run=client -o yaml**：生成樣板YAML，配合重定向`>`保存到文件，避免手寫錯誤

</details>
