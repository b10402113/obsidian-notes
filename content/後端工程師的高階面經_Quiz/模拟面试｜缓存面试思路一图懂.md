## Section A: Multiple Choice (24 points)

**Q1.** [Easy] Redis 是如何删除过期 key 的？

A) 立刻删除，一旦过期就立即清除
B) 使用惰性删除和定期删除相结合的策略
C) 每個 key 都啟動一個定時器監控
D) 不删除，等待下次訪問時才處理

<details>
<summary>Answer</summary>
<b>B) 使用惰性删除和定期删除相结合的策略</b>

面試題問到「Redis 是怎麼删除过期 key 的？」Redis採用兩種策略：惰性删除（访问key時检查是否过期并删除）+定期删除（定期隨機抽取部分key檢查並删除過期的）。這樣既保證不占用太多CPU時間，又能及时清理過期数据。
</details>

**Q2.** [Easy] 什麼是緩存穿透問題？

A) 大量請求同時訪問同一個热点 key，key 过期後大量請求穿透到數據庫
B) 查询根本不存在的數據，緩存無法命中，請求直接穿透到數據庫
C) 大量 key 同時过期，所有請求穿透到數據庫
D) 緩存和數據庫數據不一致，导致穿透

<details>
<summary>Answer</summary>
<b>B) 查詢根本不存在的數據，緩存無法命中，請求直接穿透到數據庫</b>

面試題問到「什麼是緩存穿透、擊穿和雪崩？」緩存穿透是指查詢不存在的數據（如id=-1），緩存和數據庫都没有，每次查詢都會穿透到數據庫。解决方案包括：緩存空值、布隆過濾器、参数校驗等。
</details>

**Q3.** [Medium] LRU 和 LFU 兩種淘汰策略的區別是什麼？

A) LRU基於時間，LFU 基於訪問頻率
B) LRU 基於訪問頻率，LFU 基於時間
C)兩者沒有區別，都是淘汰最少使用的數據
D) LRU 淘汰最新數據，LFU 淘汰最舊數據

<details>
<summary>Answer</summary>
<b>A) LRU基於時間，LFU 基於訪問頻率</b>

面試題問到「什麼情況下使用 LFU，什麼情況下使用 LRU？」LRU（Least Recently Used）淘汰最近最少使用的數據，基於時間维度；LFU（Least Frequently Used）淘汰訪問頻率最低的數據，基於頻率维度。LRU適合訪問模式變化較快的場景，LFU適合热点數據稳定的場景。
</details>

**Q4.** [Medium] Cache Aside 模式的工作流程是什麼？

A) 先寫緩存，再寫數據庫
B) 先讀緩存，緩存沒有則讀數據庫並寫入緩存；更新時先寫數據庫再删除緩存
C) 只操作緩存，不直接操作數據庫
D) 所有操作都先經過數據庫，再同步到緩存

<details>
<summary>Answer</summary>
<b>B) 先讀緩存，緩存沒有則讀數據庫並寫入緩存；更新時先寫數據庫再删除緩存</b>

面試題問到「什麼是 Cache Aside，它能不能解決數據一致性问题？」Cache Aside是最常用的緩存模式：讀操作先查緩存，沒有則查數據庫並寫緩存；寫操作先更新數據庫，再删除緩存（而非更新緩存）。這種模式可以一定程度上減少不一致問題，但不能完全解決。
</details>

**Q5.** [Medium] Redis 真的是單線程的吗？

A) 是，Redis 所有操作都只用一個線程
B) 否，Redis 實際上是多線程的
C) Redis 核心處理是單線程，但某些操作（如网络 IO）可以使用多線程
D) Redis 從一開始就是多線程設計

<details>
<summary>Answer</summary>
<b>C) Redis 核心處理是單線程，但某些操作（如網絡 IO）可以使用多線程</b>

面試題問到「Redis 真的是單線程的吗？」Redis 核心的命令處理仍然是單線程，保證操作的原子性和簡化設計。但從Redis 6開始，引入多線程來處理網絡 IO（讀寫 socket），提高網絡吞吐量，而不影響核心邏輯的單線程特性。
</details>

**Q6.** [Hard] 使用分布式鎖時，如果鎖過期了但業務還沒執行完畢，該怎麼處理？

A) 业务執行完畢後重新加鎖
B) 使用鎖續約機制（watch dog），定期延長鎖的有效期
C) 忽略鎖過期，繼續執行業務
D) 立終止業務執行

<details>
<summary>Answer</summary>
<b>B) 使用鎖續約機制（watch dog），定期延長鎖的有效期</b>

面試題問到「分布式鎖為什麼要續約？續約失敗了怎麼辦？」業務執行時間可能超過鎖的過期時間，需要watch dog機制自動續約：後台线程定期（如每10秒）檢查鎖是否還持有，如果持有則延長過期時間。續約失敗時，應停止業務執行，避免锁被其他客户端持有後產生並發問題。
</details>

**Q7.** [Hard] 為什麼 Redis 可以用單線程達到高性能，而 Kafka 等中間件不能？

A) Redis 只處理内存數據，Kafka處理磁盤數據
B) Redis 使用 epoll 高效IO多路復用，且操作簡單快速；Kafka 需要處理複雜的磁盤IO和網絡傳輸
C) Redis 不需要處理並發問題，Kafka 需要
D) Redis 的用戶量比 Kafka 小

<details>
<summary>Answer</summary>
<b>B) Redis 使用 epoll 高效IO多路復用，且操作簡單快速；Kafka 需要處理複雜的磁盤IO和網絡傳輸</b>

面試題問到「為什麼 Redis 可以用單線程，但是 Kafka 之類的中間件確不能使用單線程呢？」Redis性能好的原因：内存操作極快、IO多路復用（epoll）高效處理大量連接、單线程避免上下文切換开销、操作簡單（O(1)或O(logN))。Kafka需要處理磁盤IO、數據複製、分區管理等複雜操作，多线程才能充分利用多核CPU和處理並發。
</details>

## Section B: True/False (12 points)

**Q8.** [Easy] Redis 在生成 RDB 文件時會包含已過期的 key。_(True/False)_

<details>
<summary>Answer</summary>
<b>False</b>

面試題問到「當 Redis 生成 RDB 文件的時候，會怎麼處理過期的 key？」Redis 在生成 RDB（快照持久化）時會忽略已過期的key，只保存未過期的數據。過期key不會被寫入 RDB 文件，避免恢復時产生无效數據。
</details>

**Q9.** [Medium] 緩存雪崩是指大量 key 同時过期，導致大量請求穿透到數據庫。_(True/False)_

<details>
<summary>Answer</summary>
<b>True</b>

面試題問到「什麼是緩存穿透、擊穿和雪崩？」緩存雪崩是指大量key在同一時間過期（如設置相同過期時間），或Redis崩潰，導致所有請求穿透到數據庫，造成數據庫壓力骤增甚至崩潰。解决方案：過期時間設隨機值、多級緩存、限流熔斷等。
</details>

**Q10.** [Medium] 使用分布式鎖可以完全解決緩存一致性问题。_(True/False)_

<details>
<summary>Answer</summary>
<b>False</b>

面試題問到「使用分布式鎖能不能解決數據一致性問題，有什缺点？」分布式鎖可以減少並發更新導致的一致性问题，但不能完全解決：性能开销大、锁獲取失敗影響可用性、锁過期或續約失敗仍可能不一致、分布式鎖本身也有可靠性問題。需要結合其他方案（如延迟双删、消息队列等）。
</details>

**Q11.** [Hard] Redis 的定期删除循環執行越頻繁越好，可以更快清理過期key。_(True/False)_

<details>
<summary>Answer</summary>
<b>False</b>

面試題問到「Redis 定期删除的循環是不是執行得越頻繁就越好？」定期删除执行太頻繁會占用過多CPU時間，影響Redis處理正常請求的性能。Redis設置了合理的執行频率（如每秒10次）和每次執行的時間限制（如不超过25ms），平衡清理效率和性能。
</details>

## Section C: Fill-in-the-Blank (12 points)

**Q12.** [Easy] 緩存擊穿是指某個**\_\_\_\_\_\_** key 过期，大量並發請求穿透到數據庫。

<details>
<summary>Answer</summary>
<b>熱點</b>

緩存擊穿（Cache Breakdown）是指某個熱點key（如秒殺商品信息）過期，大量並發請求同時查詢該key，都穿透到數據庫造成瞬間壓力。解决方案：熱點數據不設過期時間、使用分布式鎖、提前刷新等。面試題問到「什麼是緩存穿透、擊穿和雪崩？」
</details>

**Q13.** [Medium] Redis 使用的IO多路復用技術是**\_\_\_\_\_\_**，可以高效處理大量並發連接。

<details>
<summary>Answer</summary>
<b>epoll</b>

面試題問到「什麼是 epoll？和 poll、select 比起來，有什麼優勢？」epoll是Linux高效的IO多路復用機制，相比 select/poll：支持更多連接（不受文件描述符數量限制）、只返回活跃連接（不需要遍历所有）、使用事件驱动机制，性能更好。Redis 利用 epoll單线程處理大量連接。
</details>

**Q14.** [Medium] Singleflight 模式用於解決**\_\_\_\_\_\_**問題，避免多個相同請求同時穿透到數據庫。

<details>
<summary>Answer</summary>
<b>緩存擊穿/重复請求</b>

Singleflight模式用於合并相同的並發請求：當多個請求同時查詢同一個key且緩存沒有時，只發送一個請求到數據庫，其他請求等待第一個請求的结果返回。这可以有效解决緩存击穿問題，避免重复穿透到數據庫。
</details>

**Q15.** [Hard] Redis 實現分布式鎖的基本命令是使用**\_\_\_\_\_\_**命令加鎖，確保操作的原子性。

<details>
<summary>Answer</summary>
<b>SET NX EX</b>

Redis 分布式锁使用 SET key value NX EX timeout 命令：NX表示key不存在才設置（加鎖），EX设置過期時間，整個命令原子執行。相比旧方案（SETNX + EXPIRE兩個命令），新方案原子性更好。面試題問到「怎麼用 Redis來實現一個分布式鎖？」
</details>

## Section D: Short Answer (24 points)

**Q16.** [Medium] 說明緩存穿透、擊穿和雪崩三種問題的區別，以及各自的解决方案。

<details>
<summary>Answer</summary>
<b>緩存三大問題對比：</b>

<b>1. 緩存穿透（Cache Penetration）：</b>

<b>問題描述：</b>
- 查询根本不存在的數據（如id=-1、不存在的用戶）
- 緩存和數據庫都没有該數據
- 每次查詢都穿透到數據庫，造成無效查詢
- 可能被恶意攻擊利用

<b>解决方案：</b>
- 緩存空值：將不存在的key緩存為null，設置較短過期時間
- 布隆過濾器：快速判断數據是否可能存在，不存在直接返回
- 參數校驗：前端校驗請求參數合理性（如id必為正數）
- 限流熔斷：限制異常請求频率

<b>2. 緩存擊穿（Cache Breakdown）：</b>

<b>問題描述：</b>
- 某個熱點key過期（如秒殺商品信息）
- 大量並發請求同時查詢該過期key
- 都穿透到數據庫造成瞬間高壓力
- 熱點數據过期時間設置不當引發

<b>解决方案：</b>
- 熱點數據不設過期：关键熱點數據永不过期，後台定期更新
- 分布式鎖：第一個請求加鎖查數據庫並寫緩存，其他等待
- Singleflight模式：合并相同並發請求，只穿透一次
- 提前刷新：監控key使用情况，快過期時提前异步刷新

<b>3. 緩存雪崩（Cache Avalanche）：</b>

<b>問題描述：</b>
- 大量key同時過期（如批量設置相同過期時間）
- 或Redis服務崩潰，所有緩存失效
- 所有請求穿透到數據庫
- 數據庫壓力骤增甚至崩潰

<b>解决方案：</b>
- 隨機過期時間：過期時間加隨機值，避免同時過期
- 多級緩存：本地緩存+Redis緩存，降低穿透概率
- 限流熔斷：Redis崩潰時限流保護數據庫
- 高可用部署：Redis哨兵或集群模式避免單點故障
- 緩存預加載：Redis恢復後快速預加載熱點數據

<b>三者的關鍵區別：</b>
-穿透：數據不存在，每次都穿透
-擊穿：熱點數據過期，大量並發穿透
-雪崩：大量數據過期或緩存崩潰，全面穿透

<b>綜合防護策略：</b>
- 合理設置過期時間（隨機化）
- 多級緩存架構
- 熱點數據特殊處理
- 監控告警和自动恢復
- 限流熔斷保護數據庫
</details>

**Q17.** [Hard] 在更新數據時如何保證緩存一致性？請說明 Cache Aside模式的問題和解决方案，包括延迟双删、消息队列等方案。

<details>
<summary>Answer</summary>
<b>緩存一致性問題與解决方案：</b>

<b>1. Cache Aside 模式的問題：</b>

<b>標準流程：</b>
- 读：先查緩存 → 緩存沒有則查數據庫 → 寫入緩存
-寫：先更新數據庫 → 删除緩存（而非更新緩存）

<b>潛在問題：</b>

<b>問題一：并发讀寫導致脏數據</b>
- 線程A讀數據（緩存沒有）
- 線程B更新數據庫並删除緩存
- 線程A將舊數據寫入緩存（產生不一致）
- 解决：設置緩存較短過期時間作為兜底

<b>問題二：更新數據庫成功但删除緩存失敗</b>
- 更新數據庫成功
- 删除緩存失敗（網絡、Redis故障等）
- 緩存仍是舊數據，不一致
-解决：重試删除、消息队列補償

<b>問題三：先删除緩存再更新數據庫</b>
- 線程A删除緩存
- 線程B讀取數據庫舊值並寫入緩存
- 線程A更新數據庫
-緩存是舊數據，不一致
- 不推薦先删緩存再更新數據庫

<b>2. 延迟双删方案：</b>

<b>步骤：</b>
- 第一次删除緩存
- 更新數據庫
- 延迟一段時間（如500ms）
-第二次删除緩存

<b>原理：</b>
- 第一次删除清除舊緩存
- 延迟等待并发讀取完成並寫入緩存
- 第二次删除清除可能寫入的脏緩存

<b>問題：</b>
- 延迟時間難確定（需估算并发讀取時間）
- 仍可能在高並發場景下失效
- 第二次删除也可能失敗

<b>改進：</b>
- 使用消息队列確保第二次删除執行
- 延迟時間動態調整

<b>3. 消息队列異步删除方案：</b>

<b>步骤：</b>
- 更新數據庫成功
- 發送消息到队列（包含要删除的key）
- 消費者接收消息並删除緩存
- 删除失敗則重試或記錄待修復

<b>優點：</b>
- 確保删除操作最终执行（消息队列可靠性）
- 解耦更新和删除操作
- 支持重試和失敗補償
- 可監控消息队列狀態

<b>實現方式：</b>
- 使用現有消息队列（Kafka、RabbitMQ）
- 使用專門的補償服務

<b>4. Binlog监听方案（Canal等）：</b>

<b>原理：</b>
- 監聽數據庫 binlog變更事件
- 解析變更數據（表、key、操作類型）
- 異步删除或更新緩存

<b>優點：</b>
- 完全解耦業務代碼和緩存操作
- 保證數據庫變一定能觸發緩存更新
- 支持多種緩存策略

<b>缺點：</b>
- 架构複雜度增加
- binlog解析和緩存更新有延迟
- 需要額外維護Canal等服務

<b>5. 最终一致性策略：</b>

<b>核心思想：</b>
- 緩存一致性難做到強一致
- 追求最终一致性（短暫不一致可接受）

<b>措施：</b>
- 设置合理的緩存過期時間（兜底方案）
- 使用消息队列保證删除最终執行
- 監控不一致情况並告警
- 定期對比緩存和數據庫數據並修復

<b>6. 特殊場景處理：</b>

<b>高並發寫場景：</b>
- 先更新數據庫，異步批量删除緩存
- 使用消息队列削峰

<b>本地緩存+Redis：</b>
- 更新時先更新數據庫
- 然后廣播删除本地緩存和Redis緩存
- 使用消息通知所有節點

<b>讀多寫少場景：</b>
- 更新時直接删除緩存即可
- 设置較短過期時間兜底
</details>
