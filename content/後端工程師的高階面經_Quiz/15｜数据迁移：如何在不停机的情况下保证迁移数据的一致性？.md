## 第一部分:選擇題 (每題 5 分,共 25 分)

**Q1.** mysqldump 和 XtraBackup 的主要區別是什麼?

A) mysqldump 是物理備份工具,XtraBackup 是邏輯備份工具
B) mysqldump 是邏輯備份工具導出 SQL,XtraBackup 是物理備份工具直接複製存儲文件
C) mysqldump 支持增量備份,XtraBackup 不支持
D) mysqldump 更快,XtraBackup 更慢

<details>
<summary>答案</summary>
<b>B) mysqldump 是邏輯備份工具導出 SQL,XtraBackup 是物理備份工具直接複製存儲文件</b>

mysqldump 是邏輯備份工具,導出的內容是一條條 SQL語句。XtraBackup 是物理備份工具,相當於直接複製 InnoDB 的底層存儲文件。兩者在備份方式、速度和恢復機制上有很大差異。
</details>

**Q2.** 在 innodb_autoinc_lock_mode = 1 時,對於 INSERT INTO VALUES語句,自增鎖在什麼時候释放?

A) INSERT語句执行完畢後
B) 申请主鍵後立刻释放
C) 整個事务提交後
D) 数据寫入磁盘後

<details>
<summary>答案</summary>
<b>B) 申请主鍵後立刻释放</b>

innodb_autoinc_lock_mode=1時,如果是普通的 INSERT INTO VALUE 或 VALUES語句,申请了主鍵就释放鎖,而不是整個 INSERT語句执行完畢才释放。但對於 INSERT SELECT 等語句,因為無法確定要插入多少行,所以整個語句执行完畢才释放。
</details>

**Q3.** 在数据迁移的双写阶段,為什麼必須將源表的自增主鍵值寫入目標表,而不是讓目標表自己生成主鍵?

A) 因為目標表不支持自增主鍵
B) 因為兩表生成的主鍵值可能不同,需要保持数据完全一致
C) 因為性能考慮,使用源表主鍵更快
D) 因為主鍵必須唯一,不能由兩表分別生成

<details>
<summary>答案</summary>
<b>B) 因為兩表生成的主鍵值可能不同,需要保持数据完全一致</b>

在並發場景下,源表和目標表各自生成的自增主鍵可能不同。例如兩次並發插入,源表可能生成 ID=1,2,但目標表可能生成 ID=3,4。為了保持源表和目標表数据完全一致,必須在源表插入時拿到自增主鍵值,然後用這個值作為目標表插入的主鍵。
</details>

**Q4.** 使用 mysqldump 加快导入速度時,以下哪項<b>不應該</b>做?

A) 关闭唯一性检查和外键检查
B) 关闭 binlog
C) 调整 innodb_flush_log_at_trx_commit 為 0
D) 关闭所有数据库連接

<details>
<summary>答案</summary>
<b>D) 关闭所有数据库連接</b>

关闭所有数据库連接是不合理的,會影響正常業務。正確的做法包括:关闭唯一性检查和外键检查(源表已保证)、关闭 binlog(导入不需要)、调整 redo log 刷盘时机為 0(提高性能)。這些都是為了加快导入速度的合理優化。
</details>

**Q5.** 在增量校验和修复数据時,使用 binlog 作為觸發器的方案是指什麼?

A) 直接用 binlog 中的数据覆蓋目標表
B) 收到 binlog後用主键查詢源表和目標表進行比較和修复
C) 比較源表的 binlog 和目標表的 binlog
D) 用 binlog 重放所有修改操作

<details>
<summary>答案</summary>
<b>B) 收到 binlog後用主键查詢源表和目標表進行比較和修复</b>

binlog 作為觸發器的方案是:收到 binlog後,用 binlog 中的主键去查詢源表和目標表,比較兩者数据。如果不一致,就用源表的数据去修复目標表。binlog只觸發校验動作,實際比较和修复還是查詢数据库當前数据。
</details>

## 第二部分:是非題 (每題 4 分,共 16 分)

**Q6.** 在数据迁移過程中,侵入式双寫方案(直接修改業務代码)是最推薦的方案。 _(True/False)_

<details>
<summary>答案</summary>
<b>False</b>

錯誤。侵入式方案不太可行或代價很高。因為这意味着所有業務都要检查一遍然後修改,修改後還要測試,工作量大还容易出错。推薦使用非侵入式方案,如通過 ORM 框架的 Hook、ConnPool 等機制實現双寫,可以在運行期隨時切換狀態。
</details>

---

**Q7.** 使用 update_time 進行增量校验時,如果表采用硬刪除而非软刪除,會導致源表已刪除的数据在目標表中無法被檢測到。 _(True/False)_

<details>
<summary>答案</summary>
<b>True</b>

正確。如果不是软刪除,源表刪除数据後,目標表没刪除,在匹配逻辑裡找不到這條数据。補救措施是反向全量校验:從目標表查全量数据,去源表找對應数据,如果源表没找到,说明源表已刪,目標表也可以刪除。
</details>

---

**Q8.** 在双寫過程中,如果寫入源表成功但寫入目標表失敗,應該立刻發消息到消息队列進行修复。 _(True/False)_

<details>
<summary>答案</summary>
<b>False</b>

錯誤。雖然可以考虑這個方案,但實際上难以實施,因為難以確定被影響的行。例如一個 UPDATE語句在目標表執行失敗,無法根據 UPDATE語句推断出源表上哪些行被影響。正確的做法是不管這個失敗,依靠後續的增量校验和修复機制來發現和處理問題。
</details>

**Q9.** 在数据迁移方案中,切換双寫顺序(先寫目標表)的目的是為了在發現問題時能夠回滾,提供后悔药。 _(True/False)_

<details>
<summary>答案</summary>
<b>True</b>

正確。直接從双寫切換到目標表單寫風險太大,萬一出問題無法回滾。引入先寫目標表階段,如果發現数据迁移出現問題,還可以回滾為先寫源表再寫目標表,確保業務沒問題。這是一個重要的風險控制步骤。
</details>

<details>
<summary>答案</summary>

**Q12.** 在校验和修复數据時解決主從同步延遲問題的方案是<b>\_\_\_\_</b>。

<details>
<summary>答案</summary>
<b>双重校验(先读从库,不一致再读主库)</b>

双重校验方案:第一次校验读从库,如果发现数据不一致,再读主库,用主库数据再校验一次。修复時以主库数据為準。這樣既能減輕主库压力,又能避免主從延迟導致的校验錯誤。前提是主從延迟和小概率事件。
</details>

## 第四部分:簡答題 (共 41 分)

**Q13.** (20 分) 詳細描述數據遷移方案的完整8個步骤,並說明為什麼需要切換双寫順序這個中間步驟。

<details>
<summary>答案</summary>
<b>參考答案:</b>

**完整8個步骤:**

1. **創建目標表**
   - 根據新表結構設計創建目標表

2. **初始化目標表数据**
   - 使用源表歷史備份或 mysqldump導出数据
   - 將源表数据導入目標表

3. **第一次校验與修复**
   - 校验備份/導出期間的數據差異
   - 用源表數據修復目標表數據

4. **業務開启双寫,以源表為準**
   - 實現非侵入式双寫机制(ORM Hook/ConnPool)
   - 先寫源表再寫目標表
   - 业务读源表

5. **開启增量校验和數據修复**
   - 利用 update_time 或 binlog 監聽變化
   - 定時校验並修復不一致數據
   - 保持一段時間確保稳定

6. **切換双寫順序,以目標表為準**
   - 读目標表
   - 先寫目標表再寫源表
   - 数据以目標表為準

7. **繼續增量校验和數據修复**
   - 保持校验机制
   - 以目標表數據為準進行修复

8. **切換為目標表單寫**
   - 读写都只操作目標表
   - 完成迁移,不可回滾

**切換双寫順序的必要性:**

**風險控制:**
- 直接從步驟4切換到步驟8風險太大
- 万一出問題無法回滾
- 步骤6提供后悔药

**回滾機制:**
- 如果發現切換到寫目標表出問題
- 可以回滾為先寫源表再寫目標表
- 確保业务不受影響

**平稳过渡:**
- 逐步切換數據源
- 观察目標表運行情况
- 確保無問題後才完全切換

**關鍵點:**
- 理解完整流程
- 掌握风险控制機制
- 了解可回滾設計
</details>

**Q14.** (21 分) 解釋如何在數據遷移中處理自增主鍵問題,包括 innodb_autoinc_lock_mode 参数的影響、批量插入的連續性問題,以及具體的解决方案。

<details>
<summary>答案</summary>
<b>參考答案:</b>

**自增主鍵問題的本质:**

在双寫時,源表和目標表各自生成的自增主鍵可能不同,尤其在並發場景下。為保持數據完全一致,必須用源表的主鍵值作为目標表的主鍵。

**innodb_autoinc_lock_mode 参数影響:**

**取值0:**
- 使用表自增鎖
- INSERT語句結束後才释放鎖

**取值1(默認):**
- INSERT INTO VALUES:申请主鍵後立刻释放
- INSERT SELECT:語句执行完畢才释放
- 批量插入VALUES主鍵連續

**取值2:**
- 所有語句申请主鍵後立刻释放
- VALUES批量插入主鍵仍連續

**批量插入的連續性:**

**連續情況(可推測全部ID):**
- INSERT INTO VALUES語句
- 一次申请足夠的連續主鍵
- 從返回的最後ID推測前面所有ID
- 即使 innodb_autoinc_lock_mode=2 也連續

**不連續情況(難以推測):**
- 多個 INSERT INTO VALUE語句
- INSERT SELECT語句
- 主鍵可能不連續
- 需要在双寫前改造业务

**具体解决方案:**

**方案1:获取并设置主键**
```go
// 1. 插入源表
INSERT INTO source_table VALUES(...)
// 2. 获取自增主键
lastID := GetLastInsertID()
// 3. 用源表主键插入目标表
INSERT INTO target_table(id, ...) VALUES(lastID, ...)
```

**方案2:改造批量插入**
- 將多個 INSERT INTO VALUE 改為 VALUES語句
- 將 INSERT SELECT 改為可控的批量插入
- 確保主鍵連續性

**方案3:处理批量插入**
```go
// VALUES批量插入
INSERT INTO source_table VALUES(v1, v2, v3)
lastID := GetLastInsertID()
// 推测全部ID
ids := []int{lastID-2, lastID-1, lastID}
// 插入目标表
INSERT INTO target_table VALUES(ids[0], v1), (ids[1], v2), (ids[2], v3)
```

**注意事項:**
- 双寫前檢查所有批量插入語句
- 改造不連續的主鍵生成邏輯
- 確保 VALUES語句的連續性
- 測試並验证主鍵一致性

**關鍵點:**
- 理解自增主鍵生成機制
- 掌握参数影響
- 了解連續性判斷方法
- 能設計具体解决方案
</details>
