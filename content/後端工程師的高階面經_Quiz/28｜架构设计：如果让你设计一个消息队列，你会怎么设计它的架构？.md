## Section A：选择题（30分）

**Q1.** 在设计消息队列时，为什么需要在 topic 内部引入分区（Partition）的设计？

A) 为了方便管理不同业务
B) 为了避免所有生产者和消费者竞争同一把锁，提高性能
C) 为了节省存储空间
D) 为了简化架构设计

<details>
<summary>答案</summary>
<b>B) 为了避免所有生产者和消费者竞争同一把锁，提高性能</b>

如果不划分分区，所有生产者要竞争同一把锁才能写入 topic，所有消费者也要竞争同一把锁才能读取数据，性能很差。引入分区后，topic 内部进一步细分，不同生产者可以并发写入不同分区，不同消费者可以并发读取不同分区，大幅提高并发性能。这是 Kafka 设计的核心精髓。
</details>

**Q2.** 在基于 MySQL 实现消息队列时，topic、逻辑表和物理表的关系是什么？

A) 一个 topic 对应多个逻辑表，一个逻辑表对应一个物理表
B) 一个 topic 对应一个逻辑表，一个分区对应一个物理表
C) 一个 topic 对应一个物理表，不需要逻辑表
D) 所有 topic 共用一张物理表

<details>
<summary>答案</summary>
<b>B) 一个 topic 对应一个逻辑表，一个分区对应一个物理表</b>

基于 MySQL 的设计中，一个 topic 是一个逻辑表，分区是对逻辑表分库分表后得到的物理表。例如 create_order topic 有 3 个分区，对应 create_order_0、create_order_1、create_order_2 三张物理表。每张物理表可用自增主键，对应 Kafka 的偏移量。这样保持了现代消息队列的基本结构。
</details>

**Q3.** 在消息发送过程中，为什么生产者应该采用推模型而不是拉模型？

A) 推模型性能更高
B) 消息产生速率与 broker 无关，broker 无法控制拉取频率和数量
C) 推模型更安全
D) 推模型代码更简单

<details>
<summary>答案</summary>
<b>B) 消息产生速率与 broker 无关，broker 无法控制拉取频率和数量</b>

生产者应该主动推送消息到 broker（推模型），因为消息产生速率完全跟 broker 没有关系。如果让 broker 来主动拉取，broker 不知道生产者产生消息的频率，不好控制拉的频率和拉的数量。生产者知道自己什么时候产生消息，主动推送更合理。
</details>

**Q4.** 在消费消息时，为什么消费者应该采用拉模型而不是推模型？

A) 拉模型性能更高
B) 消费者知道自己的消费速率，可以按需拉取
C) 拉模型更安全
D) 拉模型代码更简单

<details>
<summary>答案</summary>
<b>B) 消费者知道自己的消费速率，可以按需拉取</b>

消费者应该使用拉模型，因为消费者才知道自己的消费速率。消费者可以根据自身处理能力决定拉取频率和数量，例如每秒拉取 50 条消息。如果采用推模型，broker 不知道消费者能否及时处理，可能导致消息积压或消费者压力过大。
</details>

**Q5.** 在基于 MySQL 实现延迟消息时，如何解决"同时发送"问题（同一时刻多条消息）？

A) 使用 LIMIT 限制每次拉取数量
B) 不依赖数据库 LIMIT，自己计算：读够 50 条后检查后续消息是否时间相同
C) 增加一个序号列区分同一时刻的消息
D) 不支持同一时刻多条消息

<details>
<summary>答案</summary>
<b>B) 不依赖数据库 LIMIT，自己计算：读够 50 条后检查后续消息是否时间相同</b>

同时发送问题：用 LIMIT 50 可能拿到 40 条 .001 时刻和 10 条 .002 时刻的消息，下次查询会跳过剩余 40 条 .002 消息或重复消费。解决方案是不依赖数据库 LIMIT，自己计算：读够 50 条后检查后续消息，如果 send_time 与第 50 条相同，也加入当前批次。假设同一毫秒消息不多。
</details>

## Section B：是非题（20分）

**Q6.** 为了提高可用性，同一个 topic 的不同分区应该分散在不同的 broker 上存储。 _(对/错)_

<details>
<summary>答案</summary>
<b>对</b>

为了保证可用性，同一个 topic 的不同分区最好分散在不同的 broker 上存储。这样即便某一个 broker 崩溃了，这个 topic 也最多只有一个分区受到影响，不会导致整个 topic 不可用。在 MySQL 实现中，这意味着不同分区对应的表应分散在不同数据库、主从集群上。
</details>

**Q7.** 所有 topic 可以共用一张逻辑表，只需加一个 topic 列来区分不同业务。 _(对/错)_

<details>
<summary>答案</summary>
<b>错</b>

不采用所有 topic 共用一张逻辑表的原因：1) 一张表难以应付大数据与高并发场景，即便分库分表也要分几千张表，不必要；2) topic 天然就是业务隔离的，让不同 topic 用不同表，相互之间没有影响；3) 使用不同表能更好地安排不同数据库实例存储，提高可用性和性能。
</details>

**Q8.** 在基于 MySQL 的设计中，生产者可以直接连接数据库插入消息，而不必通过 broker。 _(对/错)_

<details>
<summary>答案</summary>
<b>对</b>

如果追求极致性能，可以让生产者直接把消息插入到数据库。生产者引入本地依赖，根据 topic、分区找到数据库配置，初始化连接池。发送消息调用本地方法执行 INSERT 语句。好处是省略了一次网络中间通信，生产者和 broker 一体。同样可以使用批量插入进一步提高性能。
</details>

**Q9.** 在 MySQL 实现中，记录消费偏移量时必须使用 MySQL 表，不能用其他中间件。 _(对/错)_

<details>
<summary>答案</summary>
<b>错</b>

记录消费偏移量可以用其他中间件，如 ZooKeeper。也可以用 Redis 结合异步刷新方案：Redis 记录偏移量，异步刷新到数据库。但存在风险：Redis 宕机导致最新偏移量未更新到 MySQL。例如数据库偏移量 950，消费者已到 1000，Redis 崩溃后恢复，消费者从 950 重新消费。解决方案是消费者做到幂等。
</details>

**Q10.** 基于 MySQL 实现消息队列的主要应用场景是 ToB 的私有化部署。 _(对/错)_

<details>
<summary>答案</summary>
<b>对</b>

MySQL 实现消息队列主要用于 ToB 场景。例如 A 公司研发软件，B 公司购买后要求本地部署。B 公司是小公司，不打算部署消息队列（缺乏技术力量维护）。A 公司可用 MySQL 封装消息队列，典型的例子是私有化部署的即时通讯工具。MySQL 实现避开了消息队列中性能影响大的 IO 内容，也用不上零拷贝技术。
</details>

## Section C：填空题（20分）

**Q11.** 在设计消息队列时，生产者应该使用 **\_\_\_\_** 模型（主动推送），消费者应该使用 **\_\_\_\_** 模型（按需拉取）。

<details>
<summary>答案</summary>
<b>推，拉</b>

生产者应该主动推送消息到 broker（推模型），因为消息产生速率与 broker 无关，broker 无法控制拉取频率和数量。消费者应该使用拉模型，因为消费者才知道自己的消费速率，可以按需拉取（如每秒拉取 50 条）。这样生产者和消费者都能根据自己的能力控制消息流。
</details>

**Q12.** 在基于 MySQL 实现消息队列时，记录消费偏移量需要额外的表，包含三个关键列：**\_\_\_\_**、**\_\_\_\_** 和 **\_\_\_\_**。

<details>
<summary>答案</summary>
<b>消费者组名字，分区，偏移量</b>

一个 topic 对应一张消费偏移量表，如 create_order_consumers。这张表有三个关键列：消费者组名字、分区和偏移量（consumed_offset）。每次消费者提交消息，broker 更新这张表的偏移量。每个 topic 消费者不多，数据量小，更新时只用行锁，性能好。也可重置偏移量从指定位置重新消费。
</details>

**Q13.** 在基于 MySQL 实现延迟消息时，需要在消息表增加 **\_\_\_\_** 列，记录预期发送时间，消费者查询条件为 **\_\_\_\_**。

<details>
<summary>答案</summary>
<b>send_time，send_time <= now() AND send_time > last_batch_send_max_time</b>

延迟消息支持：在消息表增加 send_time 列记录预期发送时间的毫秒数。消费者拉取消息执行 SELECT * WHERE send_time <= now() AND send_time > last_batch_send_max_time。last_batch_send_max_time 是消费者拉取出的上一批消息中最大的发送时间。此时记录的是时间戳而非偏移量。
</details>

## Section D：简答题（30分）

**Q14.** 请详细说明基于 MySQL 实现消息队列的整体架构设计，包括 topic、分区、broker、生产者和消费者各部分的设计要点。

<details>
<summary>答案</summary>
<b>Topic 设计：</b>

<b>基本结构：</b>
- 保留 topic 和分区设计（现代消息队列基本结构）
- 一个 topic 代表一个业务
- 一个 topic 对应一个逻辑表
- 一个分区对应一个物理表（分库分表后）
- 示例：create_order topic 有 3 个分区 → create_order_0、create_order_1、create_order_2
- 物理表使用自增主键，对应 Kafka 偏移量

<b>为什么分区：</b>
- 不分区：所有生产者竞争同一锁写入，所有消费者竞争同一锁读取，性能差
- 分区：不同生产者并发写入不同分区，不同消费者并发读取不同分区，提高性能

<b>为什么不共用表：</b>
- 一张表撑不住大数据高并发，分库分表需几千张表
- topic 天然业务隔离，不同 topic 不同表，互不影响
- 不同表可安排不同数据库实例存储

<b>Broker 与消息存储：</b>

<b>分区分散原则：</b>
- 同一 topic 不同分区分散在不同 broker
- 一个 broker 崩溃，最多影响一个分区，topic 仍可用

<b>MySQL 实现：</b>
- 分区对应的表分散在不同数据库、主从集群上
- 分库分表，更准确说是分数据源
- 四个分区可在四个不同主从集群上，流量分散，互不影响

<b>主从机制：</b>
- 主从集群 = 每个分区在从库有一份数据
- 一主两从 = 每个分区一个主分区两个从分区（类似 Kafka 副本）
- 使用 MySQL 主从机制，无需管理主从选举，降低落地难度

<b>发送消息：</b>

<b>推模型：</b>
- 生产者主动推送消息到 broker
- 消息产生速率与 broker 无关，broker 无法控制拉取频率

<b>批量发送：</b>
- 生产者凑够一个批次再发送，提高性能
- 生产者控制批次大小
- Fallback：一段时间内凑不够也要发送，防止消息长时间停留内存
- Kafka 的 linger.ms 控制等待时间

<b>直接插入：</b>
- 生产者通过本地依赖直连数据库
- 本地依赖根据 topic、分区找数据库配置，初始化连接池
- 调用本地方法执行 INSERT 语句
- 省略一次网络通信，生产者与 broker一体
- 可用批量 INSERT 进一步提高性能

<b>消费消息：</b>

<b>消费者组：</b>
- 一个业务方 = 一个消费者组
- 一个消费者组可有多个消费者
- 一个分区（一张表）对一个消费者组只能有一个消费者读取
- 保留 Kafka 设计：一分区一消费者，一消费者可消费多分区

<b>拉模型：</b>
- 消费者知道自己的消费速率，按需拉取
- 例如每秒从消息队列拉取 50 条消息

<b>记录偏移量：</b>
- 一个 topic 一张消费偏移量表，如 create_order_consumers
- 三列：消费者组名字、分区、偏移量
- 消费者提交 = broker 更新偏移量
- 可从指定偏移量重新消费（重置 committed_offset）

<b>直接拉取：</b>
- 消费者通过本地依赖直连数据库
- 直接从数据库读取消息并提交
- 省略网络通信

<b>改进方案：</b>
- 可用 ZooKeeper 记录偏移量
- 可用 Redis + 异步刷新：Redis 记录，异步刷新到数据库

<b>总结：</b>

基于 MySQL 实现消息队列，保留了现代消息队列的核心设计，利用数据库成熟机制（主从、分库分表）降低实现难度，适合 ToB 私有化部署场景。
</details>

**Q15.** 请解释基于 MySQL 实现延迟消息的方案，以及如何解决"同时发送"问题。

<details>
<summary>答案</summary>
<b>延迟消息实现方案：</b>

<b>表结构修改：</b>

1. 在消息表增加 send_time 列
2. 记录预期发送时间的毫秒数
3. 原消息表已有 id（自增主键）、topic、partition、message_body 等列

<b>消费者查询：</b>

消费者拉取延迟消息执行类似查询：
```sql
SELECT * FROM some_topic
WHERE send_time <= now()
AND send_time > $last_batch_send_max_time
```

<b>参数说明：</b>
- send_time <= now()：只拉取已到发送时间的消息
- last_batch_send_max_time：消费者上一批拉取消息中最大的 send_time
- 不用 LIMIT，因为要解决同时发送问题

<b>记录方式：</b>

此时记录的不是消费偏移量（id），而是时间戳：
- 记录消费者已消费到哪个时间点的延迟消息
- 消费偏移量表改为记录 last_batch_send_max_time

<b>同时发送问题：</b>

<b>问题描述：</b>

数据库中有：
- 40 条消息 send_time = 00:00.001
- 50 条消息 send_time = 00:00.002

<b>错误方案一：使用 LIMIT 50</b>
- 查询得到：40 条 .001 时刻 + 10 条 .002 时刻
- 下次查询 WHERE send_time > 00:00.002
- 剩余 40 条 .002 时刻消息被跳过（丢失）

<b>错误方案二：WHERE send_time >= 00:00.002</b>
- 查询得到：10 条 .002 时刻
- 下次查询这 10 条会再次拉出来（重复消费）

<b>正确解决方案：</b>

<b>核心思路：</b>
不依赖数据库 LIMIT，自己计算。

<b>具体步骤：</b>

1. 执行查询，不使用 LIMIT
2. 读取结果集，先读够 50 条
3. 检查第 50 条之后的数据
4. 如果 send_time 与第 50 条相同，也加入当前批次
5. 当前批次：40 条 .001 + 50 条 .002 = 90 条

<b>基本假设：</b>
某一时刻（毫秒）要发送的消息不会太多，例如几十条以内。

<b>算法流程：</b>

1. 查询返回结果集
2. 读取消息直到够 50 条
3. 检查第 50 条的 send_time = T
4. 继续读取后续消息，如果 send_time = T，加入批次
5. 直到遇到 send_time > T 或结果集结束
6. 记录 last_batch_send_max_time 为本批次最大 send_time

<b>应用场景：</b>

这个方案很容易实现延迟消息，是基于 MySQL 实现消息队列的重要优势。其他基于时间的场景（如定时任务）也可能遇到类似问题，解决思路有参考价值。

<b>方案难点：</b>

如果面试官问方案难点，可用同时发送问题来回答。这体现了对细节的深入理解和对边界条件的考虑能力。

<b>总结：</b>

基于 MySQL 实现延迟消息只需增加 send_time 列，查询逻辑简单。关键是要正确处理同时发送问题，不依赖数据库 LIMIT，自己计算批次边界，确保不丢失不重复。
</details>
