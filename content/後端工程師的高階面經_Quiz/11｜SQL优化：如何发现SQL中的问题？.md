**Q1.** 在 EXPLAIN 命令的執行計劃中,type 欄位表示查詢的方式。以下哪個選項按照性能從優到劣的正確排序是？

A) ALL > index > range > ref > eq_ref > const > system
B) system > const > eq_ref > ref > range > index > ALL
C) const > system > eq_ref > ref > range > index > ALL
D) system > eq_ref > const > ref > range > index > ALL

<details>
<summary>答案</summary>
<b>B) system > const > eq_ref > ref > range > index > ALL</b>

這是正確的性能排序。system 和 const 都表示只返回一行數據,查詢時間固定;eq_ref 和 ref 基於索引查找;range 是索引範圍掃描;index 是索引全表掃描;ALL 是全表掃描,性能最差。
</details>

**Q2.** 關於大表表結構變更,以下哪項描述是<b>錯誤</b>的？

A) 停機變更可以確保數據一致性,但會影響業務可用性
B) 在業務低谷期變更比停機變更好,但仍會有業務影響
C) 創建新表是唯一的不停機方案
D) 大表修改索引時會加表鎖,直到修改完成

<details>
<summary>答案</summary>
<b>C) 創建新表是唯一的不停機方案</b>

這是錯誤的。創建新表並不是唯一的不停機方案,只是其中一種選擇。文中提到三種方案:停機變更、業務低谷變更、創建新表。每種方案都有其適用場景和權衡。其他選項都是正確的描述。
</details>

**Q3.** 關於覆蓋索引的優化效果,以下哪項說法最準確？

A) 覆蓋索引可以完全避免磁盤 I/O
B) 覆蓋索引可以避免回表操作,提升查詢性能
C) 覆蓋索引只能用於單列索引
D) 覆蓋索引會增加存儲空間,因此不建議使用

<details>
<summary>答案</summary>
<b>B) 覆蓋索引可以避免回表操作,提升查詢性能</b>

覆蓋索引的關鍵優勢是避免回表,即不需要回到主鍵索引查找數據,因為查詢所需的所有列都已包含在索引中。雖然覆蓋索引確實會增加存儲空間,但對於高頻查詢來說,性能提升通常是值得的。
</details>

**Q4.** 在優化 `SELECT COUNT(*)` 查詢時,以下哪種方法<b>不適合</b>需要精確計數的場景？

A) 使用 EXPLAIN 返回的預估行數
B) 使用 Redis 維護計數
C) 使用額外的表記錄總數
D) 使用 Canal 監聽 binlog 更新計數

<details>
<summary>答案</summary>
<b>A) 使用 EXPLAIN 返回的預估行數</b>

EXPLAIN 返回的是預估值而非精確值,因此只適合對準確性要求不高的場景。其他三個選項都可以用於維護精確的計數,其中 B、C、D 都涉及使用額外的存儲機制來保持精確的總數。
</details>

**Q5.** 關於索引列的選擇,以下哪項<b>不是</b>推薦的索引設計原則？

A) 為外鍵列創建索引
B) 為頻繁出現在 WHERE 條件中的列創建索引
C) 為區分度很低的列（如性別）創建索引
D) 為頻繁出現在 ORDER BY 中的列創建索引

<details>
<summary>答案</summary>
<b>C) 為區分度很低的列（如性別）創建索引</b>

區分度很低的列不適合創建索引,因為索引的選擇性差。正確的做法是為區分度高的列創建索引,而且在創建組合索引時,應將區分度高的列盡可能放到左邊。其他選項都是推薦的索引設計原則。
</details>

## 第二部分：是非題 (每題 4 分,共 12 分)

**Q6.** 在 MySQL InnoDB 引擎中,`SELECT COUNT(*)` 執行速度較慢的原因是 InnoDB 沒有存儲數據總數。 _(True/False)_

<details>
<summary>答案</summary>
<b>True</b>

正確。MySQL InnoDB 引擎並沒有存儲表的數據總數,因此執行 COUNT(*) 時需要全表掃描來統計行數,這就是為什麼 COUNT(*) 在 InnoDB 上執行較慢的原因。
</details>

**Q7.** FORCE INDEX、USE INDEX 和 IGNORE INDEX 是良好的實踐,應該在所有查詢中廣泛使用。 _(True/False)_

<details>
<summary>答案</summary>
<b>False</b>

錯誤。這些索引提示不是良好的實踐,應該謹慎使用。只有在數據庫執行計劃異常（不用索引或使用錯誤索引）且無法通過其他方式優化時,才應考慮使用這些提示。正常情況下應該讓數據庫優化器自己選擇索引。
</details>

**Q8.** 將 HAVING 條件中的普通相等判斷移到 WHERE 子句中,可以提前過濾數據,減少後續處理的數據量。 _(True/False)_

<details>
<summary>答案</summary>
<b>True</b>

正確。數據庫執行順序是先執行 WHERE 過濾,再執行 HAVING 過濾。如果能將 HAVING 中不涉及聚合函數的條件提前到 WHERE 中,就能提前過濾掉不符合條件的數據,減少後續處理的數據量,從而提升查詢性能。
</details>

**Q9.** SQL 優化的兩個主要目標是<b>\_\_\_\_</b>和<b>\_\_\_\_</b>。

<details>
<summary>答案</summary>
<b>減少磁盤 I/O, 減少內存 CPU 消耗</b>

SQL 優化主要圍繞兩個目標:一是減少磁盤 I/O,可以通過避免全表掃描、使用索引、使用覆蓋索引來實現;二是減少內存 CPU 消耗,主要通過減少排序、分組、去重等操作來實現。
</details>

**Q10.** 在優化分頁查詢的大偏移量問題時,可以通過在 WHERE 條件中添加<b>\_\_\_\_</b>來確保 LIMIT 的偏移量始終為 0。

<details>
<summary>答案</summary>
<b>WHERE id > max_id (或類似的游標條件)</b>

通過記錄上一批數據的最大 ID(max_id),在下一頁查詢時添加 WHERE id > max_id 條件,這樣就可以確保 LIMIT 的偏移量始終為 0,避免數據庫讀取大量數據後再丟棄。這種方法可以保持查詢性能穩定。
</details>

## 第四部分：簡答題 (共 51 分)

**Q11.** (15 分) 解釋 EXPLAIN 命令返回結果中以下四個欄位的含義: type、possible_keys、key、rows。並說明如何利用這些信息判斷 SQL 是否需要優化。

<details>
<summary>答案</summary>
<b>參考答案:</b>

**type**: 表示查詢到所需行的方式,從好到壞依次是 system > const > eq_ref > ref > range > index > ALL。如果類型為 ALL,說明進行了全表掃描,需要優化。

**possible_keys**: 候選索引,表示查詢可能使用的索引。

**key**: 實際使用的索引。如果為 NULL,說明沒有使用索引。

**rows**: 掃描的行數。行數越多,查詢成本越高。

**判斷方法:**
- 檢查 type 是否為 ALL,如果是則需要優化
- 檢查 key 是否使用了預期的索引
- 檢查 rows 是否過大
- 結合 filtered 欄位,如果 rows 很大但 filtered 很低,說明掃描了大量無用數據

**關鍵點:**
- 理解四個欄位的含義
- 能夠判斷何時需要優化
- 理解優化思路
</details>

**Q12.** (18 分) 描述如何使用組合索引優化包含 WHERE 和 ORDER BY 的查詢,例如 `SELECT * FROM table WHERE uid = 123 ORDER BY update_time`。請從索引設計和執行原理兩個角度解釋為什麼這種優化有效。

<details>
<summary>答案</summary>
<b>參考答案:</b>

**索引設計方法:**
創建組合索引 `(uid, update_time)`,將過濾條件列和排序列組合在一起。

**執行原理:**
1. **索引有序性**: 索引本身就是有序的數據結構
2. **索引組織方式**: 在組合索引中,當 uid 確定後,update_time 本身就是有序的
3. **避免額外排序**: 數據庫可以直接按照索引中 update_time 的順序返回結果,不需要額外的排序操作

**優化前:**
- 數據庫根據 uid 查找數據
- 將所有符合 uid 條件的數據讀入內存
- 在內存中對數據按 update_time 排序
- 返回結果

**優化後:**
- 數據庫根據組合索引查找
- 索引中數據已經按 update_time 有序
- 直接返回結果,無需排序

**性能提升原因:**
- 避免了內存排序的 CPU 消耗
- 避免了額外的磁盤 I/O
- 查詢時間從秒級降到毫秒級

**關鍵點:**
- 理解索引有序性
- 理解組合索引的設計原理
- 能夠解釋優化前後的執行過程
</details>

**Q13.** (18 分) 假設你負責的系統有一個高頻查詢 `SELECT A, B, C FROM table WHERE A = ? AND B = ?`,該查詢響應時間較慢。請設計一個優化方案,包括如何分析問題、設計解決方案,以及預期的優化效果。

<details>
<summary>答案</summary>
<b>參考答案:</b>

**問題分析步驟:**

1. **使用 EXPLAIN 分析執行計劃**
   - 檢查 type 欄位,確認是否為 ALL(全表掃描)
   - 檢查 key 欄位,確認是否使用了索引
   - 檢查 rows 欄位,了解掃描行數
   - 檢查 filtered 欄位,了解過濾效率

2. **確定問題原因**
   - 可能沒有在 A、B 列上創建索引
   - 可能使用了錯誤的索引
   - 可能需要回表查詢

**解決方案:**

創建組合索引 `(A, B, C)` 作為覆蓋索引。

**為什麼選擇這個索引:**
1. A、B 出現在 WHERE 條件中,用於過濾
2. C 出現在 SELECT 中,避免回表
3. 組合索引順序: 過濾列在前,查詢列在後

**優化原理:**

1. **覆蓋索引**: 查詢所需的所有列(A、B、C)都在索引中
2. **避免回表**: 不需要回到主鍵索引查找數據
3. **減少 I/O**: 只掃描索引樹,不掃描表數據

**預期效果:**
- 查詢時間降到毫秒級(甚至 1ms 以內)
- 減少磁盤 I/O
- 降低 CPU 和內存消耗

**進一步優化考慮:**
- 如果 A、B 區分度不同,將區分度高的列放在索引左邊
- 如果查詢頻率極高,考慮使用緩存
- 監控索引大小,確保不會過度影響寫入性能

**關鍵點:**
- 能夠使用 EXPLAIN 分析問題
- 理解覆蓋索引的原理
- 能夠設計合適的組合索引
- 了解優化前後的對比
</details>
