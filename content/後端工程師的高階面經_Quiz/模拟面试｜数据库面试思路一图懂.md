## Section A: Multiple Choice (24 points)

**Q1.** [Easy] MySQL InnoDB 引擎中，什麼是聚簇索引？

A) 索引和數據分開存儲，索引指向數據行
B) 索引和數據一起存儲，葉節點包含完整數據行
C) 僅用於唯一約束的索引
D) 只能創建在主鍵上的索引

<details>
<summary>Answer</summary>
<b>B) 索引和數據一起存儲，葉節點包含完整數據行</b>

聚簇索引（Clustered Index）是 InnoDB 引擎的核心特性，索引結構與數據存儲在一起，B+ 樹的葉節點直接包含完整的數據行。一個表只能有一個聚簇索引，通常是主鍵。非聚簇索引的葉節點存儲的是主鍵值，需要通過回表來獲取完整數據。
</details>

**Q2.** [Easy] 什麼是回表？如何避免回表？

A) 回表是指查詢索引失敗後重新查表，可以通過優化索引避免
B) 回表是從非聚簇索引回到聚簇索引查找完整數據，可以通過覆蓋索引避免
C) 回表是數據庫崩後的恢復過程，可以通過備份避免
D) 回表是索引重建過程，無法避免

<details>
<summary>Answer</summary>
<b>B) 回表是從非聚簇索引回到聚簇索引查找完整數據，可以通過覆蓋索引避免</b>

面試題明確問到「什麼是回表？如何避免回表？」當查詢通過非聚簇索引找到主鍵值後，還需要回到聚簇索引查詢完整數據行，這就是回表。可以通過覆蓋索引（查詢列都在索引中）來避免回表，提高查詢性能。
</details>

**Q3.** [Medium] MySQL 在 RR（Repeatable Read）隔離級別下如何解決幻讀問題？

A) 通過行級鎖阻止其他事務插入數據
B) 通過 MVCC 和臨鍵鎖（Next-Key Lock）配合解決
C) 通過提高隔離級別到 Serializable 解決
D) MySQL RR 級別無法解決幻讀問題

<details>
<summary>Answer</summary>
<b>B) 通過 MVCC 和臨鍵鎖（Next-Key Lock）配合解決</b>

面試題問到「MySQL 是怎麼在 RR 級別下解決幻讀的？」InnoDB 通過 MVCC（多版本並發控制）解決快照讀的幻讀問題，通過臨鍵鎖（記錄鎖+間隙鎖）解決當前讀的幻讀問題。臨鍵鎖會鎖定記錄及其前面的間隙，防止其他事務插入新記錄。
</details>

**Q4.** [Medium] 在分庫分表主鍵生成中，雪花算法是如何做到全局唯一的？

A) 使用中心化服務分配 ID
B) 通過時間戳、機器 ID 和序列號組合保證唯一性
C) 依賴數據庫自增主鍵
D) 使用 UUID 隨機生成

<details>
<summary>Answer</summary>
<b>B) 通過時間戳、機器 ID 和序列號組合保證唯一性</b>

面試題問到「雪花算法是怎麼做到全局唯一的？」雪花算法通過組合時間戳（41位）、機器 ID（10位）和序列號（12位）來生成全局唯一的64位 ID。時間戳保證時間唯一性，機器 ID 保證不同機器生成的 ID 不衝突，序列號保證同一毫秒內的唯一性。
</details>

**Q5.** [Medium] 什麼是覆蓋索引？它有什優勢？

A) 覆蓋索引是指索引覆蓋了整個表的所有列
B) 蓋索引是指查詢所需的所有列都在索引中，無需回表
C) 覆蓋索引是主鍵索引的另一種稱呼
D) 覆蓋索引是唯一索引的特殊形式

<details>
<summary>Answer</summary>
<b>B) 覆蓋索引是指查詢所需的所有列都在索引中，無需回表</b>

覆蓋索引（Covering Index）是指查詢語句中需要的所有列都包含在索引中，可以直接從索引獲取數據，不需要回表到聚簇索引查詢完整數據行。優勢包括：減少 I/O 操作、提高查詢性能、避免鎖定數據行。
</details>

**Q6.** [Hard] 在數據遷移的雙寫過程中，如果一邊寫失敗了，應該怎麼處理？

A) 立終止整個遷移過程，回滾所有操作
B) 根據容錯方案處理，通常有重試、記錄錯誤日誌、告警等策略
C) 忽略失敗，繼續進行雙寫
D) 使用分布式事務保證兩邊都成功

<details>
<summary>Answer</summary>
<b>B) 根據容錯方案處理，通常有重試、記錄錯誤日誌、告警等策略</b>

面試題問到「如果雙寫的過程中，有一邊寫失敗了，怎麼辦？」數據遷移的雙寫過程中可能出現各種異常，需要設計完善的容錯方案。常見策略包括：重試機制、記錄錯誤日誌供後續修復、告警通知、異步修復數據等。使用本地事務或分布式事務保證強一致性會影響性能，實際中通常採用最終一致性方案。
</details>

**Q7.** [Hard] MySQL 為什麼使用 B+ 樹作為索引數據結構，而不使用 B 樹？

A) B+ 樹查詢速度比 B 樹更快
B) B+ 樹葉節點存儲數據，非葉節點只存索引，樹更矮，I/O 更少
C) B+ 樹更容易實現
D) B+ 湯占用更少的內存

<details>
<summary>Answer</summary>
<b>B) B+ 樹葉節點存儲數據，非葉節點只存索引，樹更矮，I/O 更少</b>

面試題問到「為什麼 MySQL 使用 B+ 樹作為索引的數據結構？為什麼不用 B樹？」B+ 樹的非葉節點只存儲索引鍵值，不存儲數據，因此每個節點可以存儲更多索引項，樹的高度更低。更低的樹高度意味更少的磁盤 I/O 操作，對於磁盤存儲的數據庫來說這是關鍵優勢。此外，B+ 樹葉節點形成鏈表，有利於範圍查詢。
</details>

## Section B: True/False (12 points)

**Q8.** [Easy] 級越多越好，可以為每個查詢列都創建索引。_(True/False)_

<details>
<summary>Answer</summary>
<b>False</b>

面試題問到「索引是不是越多越好？使用索引有什麼代價？」索引不是越多越好，過多索引會帶來代價：占用更多存儲空間、降低寫入性能（INSERT/UPDATE/DELETE 需要更新索引）、增加維護成本、可能導致索引選擇困難。需要根據實際查詢需求設計合理的索引。
</details>

**Q9.** [Medium] MVCC（多版本並發控制）可以用來解決脏讀、不可重複讀和幻讀問題。_(True/False)_

<details>
<summary>Answer</summary>
<b>True</b>

面試題問到「什麼是 MVCC？為什麼需要 MVCC？」MVCC 通過保存數據的多個版本，讓不同事務可以看到不同時間點的數據快照。在 Read Committed 和 Repeatable Read 雨離級別下，MVCC 可以解决脏读和不可重复读问题。配合锁机制还可以解决幻读问题。
</details>

**Q10.** [Medium] redo log 和 binlog 都是 MySQL 的日誌，功能完全相同。_(True/False)_

<details>
<summary>Answer</summary>
<b>False</b>

redo log 和 binlog 功能不同：redo log 是 InnoDB 引擎層的物理日誌，記錄數據頁的修改，用於崩潰恢復保證持久性；binlog 是 Server 層的邏輯日誌，記錄 SQL 語句，用於主從複製和數據恢復。兩者的刷盤時機、格式、用途都不同。面試題中詳細問到了兩者的區別和刷盤配置。
</details>

**Q11.** [Hard] 事務提交後，數據就一定不会丢失。_(True/False)_

<details>
<summary>Answer</summary>
<b>False</b>

面試題明確問到「我的事務提交了，就一定不会丟嗎？怎麼確保一定不会丟？」事務提交後數據可能會丢失，原因包括：redo log 配置為異步刷盤、page cache 未及時寫入磁盤、服務器崩潰、磁盤故障等。要確保數據不丢失需要配置 redo log 為每次提交都刷盤（innodb_flush_log_at_trx_commit=1），但這會影響性能。
</details>

## Section C: Fill-in-the-Blank (12 points)

**Q12.** [Easy] MySQL 的隔離級別包括 Read Uncommitted、Read Committed、**\_\_\_\_\_\_** 和 Serializable。

<details>
<summary>Answer</summary>
<b>Repeatable Read</b>

MySQL InnoDB 支持4種隔離級別：Read Uncommitted（讀未提交）、Read Committed（讀已提交）、Repeatable Read（可重複讀）、Serializable（可串行化）。默認使用 Repeatable Read 級別。面試題問到「什麼是隔離級別？隔離級別有哪幾種？」
</details>

**Q13.** [Medium] InnoDB 的鎖類型包括記錄鎖、**\_\_\_\_\_\_** 和臨鍵鎖（Next-Key Lock）。

<details>
<summary>Answer</summary>
<b>間隙鎖（Gap Lock）</b>

InnoDB 的行級鎖包括三種類型：記錄鎖（Record Lock）鎖定單個記錄、間隙鎖（Gap Lock）鎖定記錄之間的間隙、臨鍵鎖（Next-Key Lock）同時鎖定記錄和前面的間隙。臨鍵鎖是記錄鎖+間隙鎖的組合，用於解決幻讀問題。面試題問到「什麼是記錄鎖、間隙鎖和臨鍵鎖？」
</details>

**Q14.** [Medium] 分庫分表的事務解決方案包括 XA 事務、TCC、**\_\_\_\_\_\_**、AT 事務等。

<details>
<summary>Answer</summary>
<b>SAGA</b>

分布式事務的常見方案包括：XA 事务（兩階段提交）、TCC（Try-Confirm-Cancel）、SAGA（長事务拆分為多個短事务）、AT 事务（自動补偿）。面試題問到「什麼是 TCC？什麼是 SAGA？什麼是 AT 事務？」每種方案有不同的適用場景和優缺點。
</details>

**Q15.** [Hard] MySQL 的 undo log 主要用於實現**\_\_\_\_\_\_**和事務回滾。

<details>
<summary>Answer</summary>
<b>MVCC（多版本並發控制）</b>

undo log 記錄數據的舊版本，主要用途包括：實現 MVCC（讀取數據的歷史版本）、支持事務回滾（ROLLBACK）、支持崩溃恢复。面試題問到「什麼是 undo log？為什麼需要 undo log？」它是 InnoDB MVCC 機制的核心組成部分。
</details>

## Section D: Short Answer (24 points)

**Q16.** [Medium] 說明 MySQL InnoDB 的 MVCC 機制是如何工作的，包括 Read View 和 undo log 的作用。

<details>
<summary>Answer</summary>
<b>MVCC 工作機制：</b>

<b>1. Read View（讀視圖）：</b>
- 在事務開始時生成，記錄當前活躍事務的ID列表
- 包含：m_ids（活躍事務ID）、min_trx_id（最小活躍ID）、max_trx_id（下一個分配ID）、creator_trx_id（創建者ID）
- 用於判斷數據版本的可見性

<b>2. undo log（回滾日誌）：</b>
- 記錄數據的歷史版本
- 每次修改都會在 undo log 中記錄舊值
- 形成版本鏈，通過 trx_id 和 roll_pointer 連接

<b>3. 可見性判斷規則：</b>
- trx_id < min_trx_id：版本已提交，可見
- trx_id >= max_trx_id：版本在 Read View 生成後創建，不可見
- trx_id 在 m_ids 中：版本未提交，不可見
- trx_id = creator_trx_id：自己修改的，可見

<b>4. 不同隔離級別的 Read View：</b>
- RC級別：每次查詢都生成新的 Read View
- RR級別：只在事務開始時生成一次 Read View

<b>優勢：</b>
- 讀操作不加鎖，提高並發性能
- 解決脏讀、不可重複讀問題
- 配合鎖機制解決幻讀問題
</details>

**Q17.** [Hard] 在分庫分表的數據遷移中，如何設計雙寫方案以保證數據一致性？請說明整個遷移流程和關鍵步驟。

<details>
<summary>Answer</summary>
<b>雙寫數據遷移方案：</b>

<b>1. 遷移流程階段：</b>
- 階段一：雙寫（舊表+新表），以舊表為準
- 隀段二：雙寫，以新表為準
- 隊段三：單寫新表，停止寫舊表
- 隊段四：完全切換到新表

<b>2. 為什麼需要雙寫：</b>
- 保證數據不丢失
- 支持應用不停機切換
- 可以逐步驗證數據一致性
- 出錯時可以回滾

<b>3. 階段一設計（以舊表為準）：</b>
- 寫操作：先寫舊表成功，再寫新表（異步或同步）
- 讀操作：從舊表讀取
- 新表寫失敗：記錄日誌，後續修復
- 歷史數據：批量遷移到新表

<b>4. 隘段二設計（以新表為準）：</b>
- 寫操作：先寫新表成功，再寫舊表
- 讀操作：從新表讀取
- 切換原因：充分驗證新表可用

<b>5. 容錯方案：</b>
- 重試機制：寫失敗時重試
- 錯誤日誌：記錄失敗操作供修復
- 告警通知：異常時通知運維
- 異步修復：定期對比並修復差異

<b>6. 數據校驗：</b>
- 全量校驗：遷移完成後對比數據
- 增量校驗：定期校驗新數據
- 使用校驗工具：如 pt-table-checksum

<b>7. 回滾方案：</b>
- 任何階段都可以回滾到上一階段
- 階段一回滾：停止雙寫，只寫舊表
- 隘段二回滾：切回以舊表為準

<b>8. 性能優化：</b>
- 批量遷移歷史數據
- 異步寫新表減少延遲
- 分批次遷移避免鎖表
</details>
