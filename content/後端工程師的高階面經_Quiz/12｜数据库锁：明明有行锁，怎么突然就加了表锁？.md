## 第一部分:選擇題 (每題 5 分,共 30 分)

**Q1.** 在 MySQL InnoDB 引擎中,是如何實現的?

A) 鎖直接加在表數據上
B) 鎖借助索引實現,加在索引項上
C) 鎖只在內存中實現,不涉及物理存儲
D) 鎖只能加在主鍵索引上

<details>
<summary>答案</summary>
<b>B) 鎖借助索引實現,加在索引項上</b>

在 InnoDB 引擎中,鎖是借助索引來實現的,更加具體地來說,鎖住了索引的葉子節點。這意味著鎖和索引密切相關。如果查詢使用了索引,就會使用行鎖;如果沒有使用任何索引,就會退化為表鎖。
</details>

---

**Q2.** 關於鎖的釋放時機,以下哪項描述是正確的?

A) SQL語句執行完畢後立即釋放
B) 在 COMMIT 或 ROLLBACK 時釋放
C) 在下一條 SQL語句開始時釋放
D) 在客戶端斷開連接時釋放

<details>
<summary>答案</summary>
<b>B) 在 COMMIT 或 ROLLBACK 時釋放</b>

鎖並不是在語句執行完畢後立刻釋放,而是在整個事务結束後才釋放。換句話說,只有在執行 Rollback 或 Commit 的時候,鎖才會被釋放掉。這是一個常見的誤區,很多人誤以為鎖在語句執行完就釋放。
</details>

---

**Q3.** 乐观鎖最適合的應用場景是?

A) 寫多讀少的場景
B) 讀多寫少的場景,如大多數互聯網應用
C) 金融領域的金額操作
D) 需要強一致性的場景

<details>
<summary>答案</summary>
<b>B) 讀多寫少的場景,如大多數互聯網應用</b>

乐观鎖適用於讀多寫少的場景,互聯網中大部分應用都屬於這一類。悲观鎖則適用於寫多讀少的場景,比如在金融領域裡面對金額的操作就是以寫為主。相比之下,乐观鎖的性能要比悲观鎖好很多。
</details>

---

**Q4.** 如果查詢條件是主鍵等值查詢 `WHERE id = 15`,但 id=15 的數據不存在,會使用什麼類型的鎖?

A) 記錄鎖
B) 間隙鎖
C) 臨鍵鎖
D) 表鎖

<details>
<summary>答案</summary>
<b>C) 臨鍵鎖</b>

根據記憶口訣"遇事不決臨鍵鎖",大部分情況下都是使用臨鍵鎖。當查詢條件的值不存在時,InnoDB 引擎會利用最接近 15 的相鄰兩個節點,構造一個臨鍵鎖。臨鍵鎖可以看作是記錄鎖和間隙鎖的組合。
</details>

---

**Q5.** 關於間隙鎖的排它性,以下哪項描述是正確的?

A) 間隙鎖是排它的,兩個間隙鎖不能重叠
B) 間隙鎖不是排它的,兩個間隙鎖重叠也可以加鎖成功
C) 間隙鎖只在可重複讀隔離級別下是排它的
D) 間隙鎖的排它性取決於索引類型

<details>
<summary>答案</summary>
<b>B) 間隙鎖不是排它的,兩個間隙鎖重叠也可以加鎖成功</b>

記錄鎖和記錄鎖是排它的,但是間隙鎖和間隙鎖不是排它的。也就是說兩個間隙鎖之間即便重叠了,也還是可以加鎖成功的。這是間隙鎖的一個重要特性。
</details>

---

**Q6.** 在 MySQL InnoDB 中,如果一個查詢<b>沒有</b>使用任何索引,會發生什麼?

A) 使用記錄鎖
B) 使用間隙鎖
C) 使用臨鍵鎖
D) 退化為表鎖

<details>
<summary>答案</summary>
<b>D) 退化為表鎖</b>

InnoDB 引擎的行鎖是借助索引來實現的。如果查詢沒有命中任何索引,InnoDB 引擎就用不了行鎖,只能使用表鎖。這就是為什麼文章標題說"明明有行鎖,怎麼突然就加了表鎖"。這會對性能造成極大影響。
</details>

## 第二部分:是非題 (每題 4 分,共 12 分)

**Q7.** 間隙鎖和臨鍵鎖只在可重複讀(RR)隔離級別下才有效果。 _(True/False)_

<details>
<summary>答案</summary>
<b>True</b>

正確。間隙鎖和臨鍵鎖是只工作在可重複讀這個隔離級別下的。如果將隔離級別降低為已提交讀(RC),那麼就沒有間隙鎖了。這也是解決臨鍵鎖死鎖問題的一種思路,但影響較大。
</details>

---

**Q8.** 意向鎖是一個真正物理意義上的鎖。 _(True/False)_

<details>
<summary>答案</summary>
<b>False</b>

錯誤。意向鎖相當於一個信號,就是告訴別人我要加鎖了,所以意向鎖並不是一個真正物理意義上的鎖。意向鎖的"意向"強調的是你想要拿到這個鎖,但你最終能否拿到這個鎖,是不確定的。
</details>

---

**Q9.** 使用乐观鎖時,如果 UPDATE 語句的受影響行數為 0,說明更新成功。 _(True/False)_

<details>
<summary>答案</summary>
<b>False</b>

錯誤。使用乐观鎖時,業務方通過檢測受影響的行數是否為 0 來判斷更新是否<b>失敗</b>。如果受影響行數為 0,說明數據在 SELECT 和 UPDATE 之間已被別人修改過,更新失敗,需要重試或處理。
</details>

**Q10.** 在 MySQL InnoDB 引擎中,鎖是借助<b>\_\_\_\_</b>來實現的,鎖住的是<b>\_\_\_\_</b>。

<details>
<summary>答案</summary>
<b>索引, 紹子節點</b>

InnoDB 引擎中,鎖是借助索引來實現的。更加具體地來說,就是鎖住了索引的葉子節點。這解釋了為什麼鎖和索引密切相關,以及為什麼沒有使用索引的查詢會退化為表鎖。
</details>

**Q11.** 臨鍵鎖可以看作是<b>\_\_\_\_</b>和<b>\_\_\_\_</b>的組合。

<details>
<summary>答案</summary>
<b>記錄鎖, 間隙鎖</b>

臨鍵鎖(Next-Key Locks)是很独特的一種鎖,直觀上來說可以看做是一個記錄鎖和間隙鎖的組合。臨鍵鎖不僅會用記錄鎖鎖住命中的記錄,也會用間隙鎖鎖住記錄之間的空隙。
</details>

## 第四部分:簡答題 (共 46 分)

**Q12.** (15 分) 詳細解釋記錄鎖、間隙鎖和臨鍵鎖三者的區別,包括鎖的範圍、使用場景和排它性。

<details>
<summary>答案</summary>
<b>參考答案:</b>

**記錄鎖:**
- 鎖住特定的某一條記錄
- 使用場景:主鍵或唯一索引的等值查詢,且數據存在
- 排它性:記錄鎖之間是排它的

**間隙鎖:**
- 鎖住某一段記錄範圍,兩邊都是開的(左開右開)
- 使用場景:範圍查詢(<, <=, BETWEEN),或等值查詢但數據不存在
- 排它性:間隙鎖之間不是排它的,重叠也可以加鎖成功

**臨鍵鎖:**
- 記錄鎖和間隙鎖的組合,左開右閉
- 使用場景:默認情況下都使用臨鍵鎖(遇事不決臨鍵鎖)
- 排它性:兼具記錄鎖和間隙鎖的特性

**記憶口訣:**
1. 遇事不決臨鍵鎖
2. 右邊缺省間隙鎖
3. 等值查詢記錄鎖(主鍵/唯一索引)

**關鍵點:**
- 理解三種鎖的定義和區別
- 掌握使用場景判斷方法
- 理解排它性差異
</details>

**Q13.** (16 分) 描述臨鍵鎖引發死鎖的典型案例,包括死鎖產生的原因、時序過程和解決方案。

<details>
<summary>答案</summary>
<b>參考答案:</b>

**業務場景:**
先 SELECT FOR UPDATE 查詢數據。如果數據存在,執行計算後更新;如果不存在,執行不同計算後插入。

**死鎖原因:**
當 SELECT FOR UPDATE 查找的數據不存在時,數據庫會使用臨鍵鎖。假設數據庫最大 ID=78:
- 線程1查詢 id=79 不存在,獲得(78, supremum]臨鍵鎖
- 線程2查詢 id=80 不存在,獲得(78, supremum]臨鍵鎖
- 兩個臨鍵鎖重叠(因間隙鎖不排它)
- 線程1想插入 id=79,需要行鎖,等待線程2釋放臨鍵鎖
- 線程2想插入 id=80,需要行鎖,等待線程1釋放臨鍵鎖
- 形成死鎖

**死鎖時序:**
1. 線程1 SELECT FOR UPDATE (id=79) -> 臨鍵鎖(78, supremum]
2. 線程2 SELECT FOR UPDATE (id=80) -> 臨鍵鎖(78, supremum]
3. 線程1 INSERT id=79 -> 等待線程2釋放臨鍵鎖
4. 線程2 INSERT id=80 -> 等待線程1釋放臨鍵鎖 -> 死鎖!

**解決方案:**
1. **先插入默認數據**:不管有沒有數據,先插入。成功則執行不存在邏輯(持有行鎖);失敗則執行存在邏輯
2. **降低隔離級別**:改為 RC,消除間隙鎖(影響大,需DBA批准)
3. **使用乐观鎖**:放棄悲观鎖,代碼更復雜但性能更好

**關鍵點:**
- 理解臨鍵鎖死鎖機制
- 分析時序過程
- 掌握多種解決方案
</details>

**Q14.** (15 分) 解釋乐观鎖和悲观鎖的實現方式、適用場景和性能差異。並說明如何將悲观鎖改為乐观鎖。

<details>
<summary>答案</summary>
<b>參考答案:</b>

**乐观鎖:**
- 實現方式:利用 CAS思路,UPDATE時檢查數據未被修改
- SQL形態:`UPDATE table SET data=new WHERE id=1 AND data=old`
- 判斷成功:受影響行數>0表示成功,=0表示失敗需重試
- 適用場景:讀多寫少,大多數互聯網應用
- 性能:較好,無鎖等待

**悲观鎖:**
- 實現方式:直接加鎖保護臨界資源
- SQL形態:`SELECT ... FOR UPDATE`後執行 UPDATE
- 適用場景:寫多讀少,金融金額操作
- 性能:較差,有鎖等待和阻塞

**性能差異:**
乐观鎖性能比悲观鎖好很多,因為無鎖等待。悲观鎖會阻塞其他操作。

**改造方案(悲观鎖 -> 乐观鎖):**

原悲观鎖代碼:
```go
Begin()
data := SelectForUpdate(id)  // SELECT FOR UPDATE
newData := calculate(data)
Update(id, newData)  // UPDATE
Commit()
```

改為乐观鎖:
```go
for {
  data := Select(id)  // 普通 SELECT
  newData := calculate(data)
  // CAS: UPDATE時確認數據未變
  success := Update(id, newData, data)  // UPDATE SET data=new WHERE id=1 AND data=old
  if success { break }  // 更新成功,退出
  // 失敗則重試
}
```

**改造效果:**
- 性能提升30%
- 無鎖等待和阻塞
- 需處理重試邏輯

**關鍵點:**
- 理解兩種鎖的實現原理
- 掌握適用場景判斷
- 能夠進行代碼改造
</details>
