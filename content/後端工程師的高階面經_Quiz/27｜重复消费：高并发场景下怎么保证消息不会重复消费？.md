## Section A：选择题（30分）

**Q1.** 关于布隆过滤器，以下哪项描述是**正确的**？

A) 判断元素不存在时可能出错（假阳性）
B) 判断元素存在时一定准确无误
C) 判断元素不存在时一定准确，判断存在时可能出错（假阳性）
D) 不存在任何误判情况

<details>
<summary>答案</summary>
<b>C) 判断元素不存在时一定准确，判断存在时可能出错（假阳性）</b>

布隆过滤器通过哈希算法将元素映射到比特数组的 N 个点，将对应比特位设置为 1。查找时看对应比特位是否为 1：如果查询元素对应的 N 个点都是 1，元素 **可能** 存在（假阳性，实际不存在但误判存在）；如果任何一个点是 0，元素 **必然** 不存在。布隆过滤器适合判断元素必定不存在的场景。
</details>

**Q2.** Bit array（Bit map）与布隆过滤器的核心区别是什么？

A) Bit array 需要哈希函数
B) Bit array 不存在假阳性问题，判断是精确的
C) Bit array 性能比布隆过滤器差
D) Bit array 空间效率比布隆过滤器高

<details>
<summary>答案</summary>
<b>B) Bit array 不存在假阳性问题，判断是精确的</b>

Bit array 与布隆过滤器的核心区别是它不需要哈希函数，因为值本身就是一个数字。例如用户 ID 是数字，就把 ID 当成 bit array 的下标，对应比特位为 1 表示存在。Bit array 不存在假阳性的说法，判断是精确的。如果 key 是数字（如自增主键），bit array 性能更好，更节省内存。
</details>

**Q3.** 在使用唯一索引实现幂等的基本方案中，为什么要将业务操作和唯一索引插入放在一个本地事务中？

A) 提高数据库性能
B) 确保业务操作和唯一索引插入要么都成功要么都失败
C) 减少唯一索引冲突概率
D) 简化代码实现

<details>
<summary>答案</summary>
<b>B) 确保业务操作和唯一索引插入要么都成功要么都失败</b>

本地事务确保业务操作和唯一索引插入是原子操作，要么都成功要么都失败。如果插入唯一索引成功但业务操作失败，会出现数据不一致。使用事务后，只有事务提交了但消息提交失败的情况，下次消费时会遇到唯一索引冲突，被拦截。如果事务未提交，消息消费失败，应该重试。
</details>

**Q4.** 在布隆过滤器 + Redis + 唯一索引的高级方案中，更新系统的正确顺序是什么？

A) 先更新布隆过滤器，再更新 Redis，最后更新数据库
B) 先更新 Redis，再更新布隆过滤器，最后更新数据库
C) 先更新数据库唯一索引，再更新布隆过滤器和 Redis
D) 同时更新三个组件

<details>
<summary>答案</summary>
<b>C) 先更新数据库唯一索引，再更新布隆过滤器和 Redis</b>

正确的更新顺序是先更新数据库唯一索引，因为数据库里的数据是最准确的。将数据库更新操作放到业务本地事务中，与业务操作一起提交。数据库事务提交后，再更新布隆过滤器和 Redis。如果后面更新失败了也没关系，因为最终重复请求会被唯一索引拦截。这个方案最终依靠唯一索引兜底。
</details>

**Q5.** 在使用 Redis 存储近期处理过的 key 时，key 的过期时间应该如何设置？

A) 设置为永久不过期
B) 设置为业务处理时间的一半
C) 设置为预计重试请求到达时间加上余量
D) 随机设置过期时间

<details>
<summary>答案</summary>
<b>C) 设置为预计重试请求到达时间加上余量</b>

Redis key 的过期时间应确保重复请求到达时 key 还没过期。例如，预计重试请求会在 10 分钟内到达，则过期时间设置为 11 分钟，多出的一分钟作为余量。但也需考虑 Redis 能否容纳这么多 key。如果业务重试间隔很长（如一小时），不太适合引入 Redis，可使用简化方案（布隆过滤器 + 唯一索引）。
</details>

## Section B：是非题（20分）

**Q6.** 布隆过滤器判断元素不存在时是准确的，判断元素存在时可能出现假阳性。 _(对/错)_

<details>
<summary>答案</summary>
<b>对</b>

布隆过滤器的特点是：如果查询元素对应的 N 个点都是 1，元素 **可能** 存在，但也可能是假阳性（实际不存在但误判为存在）。如果任何一个点是 0，元素 **必然** 不存在。因此布隆过滤器在判断元素必定不存在的场景下效果非常好，常与其他手段结合使用。
</details>

**Q7.** 在非本地事务场景下使用唯一索引实现幂等时，可以保证业务操作和唯一索引插入的原子性。 _(对/错)_

<details>
<summary>答案</summary>
<b>错</b>

在没有本地事务的场景下（如分库分表），业务操作和唯一索引插入不能看作一个整体，无法保证原子性（要么都成功要么都失败）。只能追求最终一致性，依赖第三方异步检测系统定时扫描唯一索引和业务数据，判断是否一致，不一致时触发重试或标记状态。
</details>

**Q8.** 布隆过滤器 + Redis + 唯一索引方案的核心目标是确保到达数据库的流量最小化。 _(对/错)_

<details>
<summary>答案</summary>
<b>对</b>

该方案的核心思路是"层层削流"，目标是确保到达数据库的流量最小化。因为数据库撑不住高并发写流量，所以要设法让流量在到达数据库之前就返回。布隆过滤器判断未处理过的请求直接通过，判断已处理（可能假阳性）的请求去查 Redis，Redis 也没找到才查数据库唯一索引。
</details>

**Q9.** 本地布隆过滤器必须和负载均衡结合使用，确保同一个 key 的请求落到同一个实例上。 _(对/错)_

<details>
<summary>答案</summary>
<b>对</b>

本地布隆过滤器需要和负载均衡结合使用。通过一致性哈希等算法，确保同一个 key 的请求落到同一个实例上，这样该实例可以使用基于本地内存的布隆过滤器。在消息队列场景下，要求生产者把同一个 key 的消息发到同一个分区，消费者才能使用本地布隆过滤器。
</details>

**Q10.** 如果 key 是数字（如自增主键），可以使用 bit array 替代布隆过滤器，性能更好且不存在假阳性。 _(对/错)_

<details>
<summary>答案</summary>
<b>对</b>

如果 key 本身就是数字（如数据库自增主键），可以使用 bit array 替代布隆过滤器。bit array 不需要哈希函数，直接用数字作为下标，对应比特位为 1 表示存在。bit array 性能更好，更能节省内存，且不存在假阳性问题，判断是精确的。小技巧：最小 ID 为 5,000,000 时，比特位 0 表示 5,000,000。
</details>

## Section C：填空题（20分）

**Q11.** 消息重复消费的可能原因有两种：一是 **\_\_\_\_**（收到超时响应后重试），二是 **\_\_\_\_**（处理完但未提交就宕机）。

<details>
<summary>答案</summary>
<b>生产者重复发送，消费者重复消费</b>

重复消费的可能原因：1) 生产者重复发送：发送消息收到超时响应，不确定是否真的发送出去，重试导致同一消息发送多次；2) 消费者重复消费：处理完消息准备提交时宕机未提交，恢复后再次消费同一消息。解决原则是必须把消费逻辑设计成幂等的，同一消息不管消费多少次，系统状态都一样。
</details>

**Q12.** 在布隆过滤器 + Redis + 唯一索引方案中，基本流程是：先用 **\_\_\_\_** 判断，再用 **\_\_\_\_** 查询近期处理过的 key，最后用 **\_\_\_\_** 兜底。

<details>
<summary>答案</summary>
<b>布隆过滤器，Redis，唯一索引</b>

基本流程：1) 用布隆过滤器判断，如果判断未处理过，则确实未处理过，可直接处理；如果判断处理过（可能假阳性），进入下一步；2) 用 Redis 查询近期处理过的 key，如果有则已处理过，如果没有进入下一步；3) 用唯一索引，如果冲突则已处理过。布隆过滤器削减大部分流量，Redis 进一步削减，唯一索引兜底。
</details>

**Q13.** 在非本地事务场景下使用唯一索引实现幂等时，需要依赖 **\_\_\_\_** 系统定时扫描唯一索引和业务数据，判断是否一致，不一致时触发重试或标记状态。

<details>
<summary>答案</summary>
<b>异步检测</b>

非本地事务场景下，步骤是：1) 插入唯一索引（初始状态），2) 执行业务操作，3) 标记为完成状态。问题在于步骤 2 成功但步骤 3 失败。解决方案是异步检测系统定时扫描初始状态的唯一索引数据，检查业务数据是否一致。如果业务成功则标记唯一索引为成功；如果业务失败则触发重试。
</details>

## Section D：简答题（30分）

**Q14.** 请详细说明布隆过滤器 + Redis + 唯一索引方案的整体流程、核心目标，以及如何更新这三个组件。

<details>
<summary>答案</summary>
<b>核心目标：</b>

确保到达数据库的流量最小化（层层削流）。数据库撑不住高并发写流量，性能完全取决于数据库性能。需要高效数据结构帮助判断请求是否已被处理，在到达数据库前就返回。

<b>整体流程：</b>

<b>第一步：布隆过滤器判断</b>
- 请求到来时，用布隆过滤器判断是否处理过
- 如果布隆过滤器说未处理过 → 确实未处理过（准确），可直接处理
- 如果说处理过 → 可能是假阳性，进入下一步

<b>第二步：Redis 查询</b>
- 查询 Redis 中存储的近期处理过的 key
- 如果 Redis 有这个 key → 确实已处理过，直接返回
- 如果没有 → 进入下一步

<b>第三步：唯一索引兜底</b>
- 利用数据库唯一索引判断
- 如果唯一索引冲突 → 已处理过，返回
- 如果插入成功 → 未处理过，继续执行业务

<b>更新顺序：</b>

<b>原则：</b>
数据库数据是最准确的，先更新数据库。

<b>具体步骤：</b>

1. **先更新数据库唯一索引**：
   - 将数据库更新操作放到业务本地事务中
   - 与业务操作一起提交
   - 确保原子性

2. **数据库事务提交后，更新布隆过滤器和 Redis**：
   - 顺序不重要：可先更新布隆过滤器，或先更新 Redis，或并发更新
   - 如果更新失败了也没关系
   - 因为最终重复请求会被唯一索引拦截

<b>兜底机制：</b>

不管什么原因导致布隆过滤器或 Redis 失效（更新失败、假阳性），只要跑到插入唯一索引这一步，都能确保最终不会重复处理消息或请求。

<b>简化方案：</b>

1. 布隆过滤器 + 唯一索引：适合重试间隔很大的业务
2. Redis + 唯一索引：适合 Redis 资源充足、担心假阳性的场景

<b>总结：</b>

方案层层削减流量，最终依靠唯一索引兜底，确保高并发下的幂等性。
</details>

**Q15.** 请解释本地布隆过滤器的使用场景、如何实现、以及如何重建本地布隆过滤器。

<details>
<summary>答案</summary>
<b>使用场景：</b>

性能要求非常苛刻的情况下，利用本地内存进一步提高性能。本地内存访问比网络请求 Redis 快得多。

<b>实现方式：</b>

<b>关键前提：</b>
本地布隆过滤器必须和负载均衡结合使用。

<b>实现步骤：</b>

1. **负载均衡策略**：
   - 使用一致性哈希等算法执行负载均衡
   - 确保同一个 key 的请求落到同一个实例上
   - 这样该实例可以用本地内存的布隆过滤器

2. **消息队列场景**：
   - 生产者发送消息时，把同一个 key 的消息发到同一个分区
   - 对应消费者使用本地布隆过滤器
   - 消费者只需维护本地布隆过滤器，不需要查询远程 Redis

<b>为什么不能直接用本地布隆过滤器：</b>

不同实例内存不共享，同一个 key 的请求可能落到不同实例，导致判断不准确。必须通过负载均衡确保同一个 key 始终落到同一实例。

<b>重建本地布隆过滤器：</b>

服务器重启后，本地布隆过滤器丢失，需要重建。

<b>第一种思路：不重建，逐步构建</b>
- 直接处理新请求
- 在处理新请求过程中，逐步重建布隆过滤器
- 适合时效性很强的请求场景
- 例如：今天不可能收到昨天的重复请求
- 处理今天请求时自然构建今天的布隆过滤器

<b>第二种思路：利用历史数据构建</b>
- 用过去一段时间的数据构建布隆过滤器
- 例如预计今天收到的重复请求最多来自三天前
- 就用这三天内处理过的请求构建布隆过滤器

<b>布隆过滤器不准确也没关系：</b>

- 最终有唯一索引兜底
- 只需小心不要让太多流量最终落到唯一索引上
- 假阳性会导致去查唯一索引，但流量不大即可接受

<b>Redis 替换为本地内存：</b>

使用本地布隆过滤器后，可考虑把 Redis 替换为本地内存。但一般来说本地内存宝贵，不值得浪费换取一点性能提升。通过布隆过滤器的请求已经是少数，Redis 处理足够快。

<b>总结：</b>

本地布隆过滤器通过负载均衡确保同 key 同实例，利用本地内存极大提高性能。重建策略灵活，最终依赖唯一索引兜底。
</details>
