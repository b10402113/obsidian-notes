## Section A：选择题（30分）

**Q1.** 关于延迟队列，以下哪项描述是**正确的**？

A) 延迟队列中的元素没有过期时间
B) 当元素未到过期时间时，尝试获取元素会立即返回空
C) 延迟队列中获取的元素永远是最先过期的那个
D) 延迟消息会立即被消费者消费

<details>
<summary>答案</summary>
<b>C) 延迟队列中获取的元素永远是最先过期的那个</b>

延迟队列中的每个元素都有过期时间。当元素还没到过期时间时，如果尝试从队列获取元素，会被阻塞。当有元素过期时，会拿到最先过期的那个元素。延迟消息是指消息经过一段时间后才会被消费，在到时间之前一直存储在消息队列服务器上。
</details>

**Q2.** RabbitMQ 的延迟消息插件 `rabbitmq_delayed_message_exchange` 有哪两个主要限制？

A) 不支持持久化和高并发
B) 消息可能丢失和不支持高并发大数据量
C) 只支持固定延迟时间和不支持分布式
D) 性能低和不支持死信队列

<details>
<summary>答案</summary>
<b>B) 消息可能丢失和不支持高并发大数据量</b>

RabbitMQ 延迟消息插件有两个主要限制：1) 消息在投递到目标队列前存放在 Mnesia，如果未刷新磁盘或节点不可用，消息会丢失；2) 不支持高并发、大数据量，限制了其在订单超时取消等高并发场景的使用。
</details>

**Q3.** 在 Kafka 分区设置不同延迟时间的方案中，为什么会出现 rebalance 问题？

A) 因为消费者处理速度太快
B) 因为消费者睡眠期间不消费消息，Kafka 判断消费者崩溃
C) 因为分区数量太少
D) 因为消息延迟时间太长

<details>
<summary>答案</summary>
<b>B) 因为消费者睡眠期间不消费消息，Kafka 判断消费者崩溃</b>

在该方案中，消费者读取消息后需要根据延迟时间睡眠等待。睡眠期间不消费消息，Kafka 会判定消费者已崩溃，触发 rebalance。rebalance 后消费者可能被分配到不同分区，之前的睡眠就白睡了。解决方案是在睡眠前使用 Kafka 的 Pause 功能。
</details>

**Q4.** 在基于 MySQL 的延迟消息方案中，表交替方案的主要特点是什么？

A) 使用多个表轮询插入
B) 两个表按天交替读写，延迟时间不能超过一天
C) 按周分区进行读写
D) 使用分区表提高性能

<details>
<summary>答案</summary>
<b>B) 两个表按天交替读写，延迟时间不能超过一天</b>

表交替方案准备两个表（如 tab_0、tab_1），按天交替读写。当切换使用 tab_1 时，可以直接 TRUNCATE tab_0 的数据。TRUNCATE 很快，没有性能问题。但按天交替的方案对延迟时间有限制：延迟时间不能超过一天。
</details>

**Q5.** 在 MySQL 方案的分库分表策略中，如何保证延迟消息的有序性？

A) 随机插入到任意表
B) 确保同一个 biz_topic 的消息落到同一张表
C) 按发送时间排序
D) 使用全局锁

<details>
<summary>答案</summary>
<b>B) 确保同一个 biz_topic 的消息落到同一张表</b>

要保证延迟消息有序性，在分库分表时确保同一个 biz_topic 的消息都落到同一张表里。同时，发送到 delay_topic 时也按照 biz_topic 名字选择分区，保证消息转发到 biz_topic 的顺序与发送到 delay_topic 的顺序一致。
</details>

## Section B：是非题（20分）

**Q6.** 在 RabbitMQ 中，可以使用 TTL 功能和死信队列手动实现延迟消息。 _(对/错)_

<details>
<summary>答案</summary>
<b>对</b>

除了使用延迟消息插件，开发者可以手动实现延迟消息。准备一个 delay_queue 设置过期时间，不设置消费者。将 biz_queue 绑定为 delay_queue 的死信队列。消息在 delay_queue 过期后被转发到 biz_queue，消费者就能收到消息。这种方案避免了插件的缺点，但 TTL 只能在队列级别设置，不支持随机延迟时间。
</details>

**Q7.** 利用定时任务实现延迟消息可以支持高并发、大数据量场景。 _(对/错)_

<details>
<summary>答案</summary>
<b>错</b>

定时任务方案的最大缺点是支撑不住高并发。绝大多数定时任务中间件都无法支撑高并发、大数据的定时任务调度。该方案只适合应用规模小、延迟消息不多的场景。要支持高并发、大数据的延迟方案，还是需要利用消息队列。
</details>

**Q8.** 在分区设置不同延迟时间的方案中，一致性问题的解决方法是先提交消息再转发。 _(对/错)_

<details>
<summary>答案</summary>
<b>错</b>

一致性问题的解决方法是先转发 biz_topic，再提交。如果先提交再转发，可能出现消息已提交但转发前宕机的情况，导致消息丢失。先转发再提交，如果提交前宕机，下次恢复时会重复转发。但多发一次不是问题，只需消费者确保幂等性。实际上即便不用延迟消息，消费者也应该做到幂等。
</details>

**Q9.** Kafka 的暂停（Pause）功能意味着不再发起 Poll 请求，消费者完全停止。 _(对/错)_

<details>
<summary>答案</summary>
<b>错</b>

Kafka 的暂停功能并不是不再发起 Poll 请求，而是 Poll 了但不会真的拉取消息。这样可以让 Kafka 始终认为消费者还活着，避免因睡眠期间不消费消息而触发 rebalance。暂停相当于拉取 0 条数据。
</details>

**Q10.** 分区设置不同延迟时间方案的主要缺点是延迟时间必须预先设定，不支持随机延迟时间。 _(对/错)_

<details>
<summary>答案</summary>
<b>对</b>

该方案有两个主要缺点：1) 延迟时间必须预先设定，如只能延迟 1min、3min 或 10min，不支持随机延迟时间。有些业务场景需要根据具体数据计算延迟时间，该方案不适用；2) 分区间负载不均匀，如很多业务只需延迟 3min，则 1min 和 10min 分区数据很少，可能导致负载高的分区出现消息积压。
</details>

**Q12.** 在分区设置不同延迟时间方案中，为避免 rebalance 问题，需要在睡眠前使用 Kafka 的 **\_\_\_\_** 功能，睡眠结束后使用 **\_\_\_\_** 功能。

<details>
<summary>答案</summary>
<b>Pause（暂停），Resume（恢复）</b>

为了避免睡眠期间触发 rebalance，需要使用 Kafka 的 Pause 功能暂停消费（相当于 Poll 0 条数据），让 Kafka 认为消费者还活着。睡眠结束后使用 Resume 功能恢复消费，并重置 offset 到之前拉取的消息位置。
</details>

**Q13.** 基于 MySQL 的延迟消息方案中，提高性能的四个关键策略是 **\_\_\_\_**、**\_\_\_\_**、**\_\_\_\_** 和 **\_\_\_\_**。

<b>分区表、表交替、分库分表、批量操作</b>

</details>

## Section D：简答题（30分）

**Q14.** 请详细说明在 Kafka 分区设置不同延迟时间的方案中，rebalance 问题是如何产生的？以及如何解决这个问题？

<details>
<summary>答案</summary>
<b>关键要点：</b>

<b>Rebalance 问题产生原因：</b>

1. 消费者从分区读取消息后，需要根据消息的剩余延迟时间进行睡眠等待
2. 在睡眠期间，消费者不会消费任何消息
3. Kafka 会判定长时间不消费消息的消费者已经崩溃
4. 触发 rebalance 机制，重新分配分区给其他消费者
5. 等睡眠结束后，消费者可能被分配到不同的分区，之前的睡眠就白睡了

<b>解决方案：</b>

使用 Kafka 的 Pause 和 Resume 功能：

1. 拉取一条消息，记录 offset = N，查看剩余延迟时间 t
2. 暂停消费（Pause）：相当于 Poll 0 条数据，仍发起 Poll 请求
3. 睡眠等待时间 t
4. 睡眠结束后，恢复消费（Resume）
5. 从 offset = N 开始重新消费

<b>关键点：</b>

Pause 功能并不是不再发起 Poll 请求，而是 Poll 了但不会真的拉消息。这样可以让 Kafka 始终认为消费者还活着，避免触发 rebalance。
</details>

**Q15.** 请解释基于 MySQL 的延迟消息方案的整体架构，以及如何通过分库分表和批量操作来支撑高并发？

<details>
<summary>答案</summary>
<b>整体架构：</b>

1. 业务发送者将消息（带延迟时间）发送到 delay_topic
2. 延迟消费者消费 delay_topic，将消息转储到 MySQL 数据库
3. 延迟发送者轮询数据库，查找已到发送时间的消息
4. 延迟发送者将符合条件的消息转发到 biz_topic
5. 更新数据库状态为已发送
6. 业务消费者消费 biz_topic

<b>MySQL 性能瓶颈：</b>

延迟消息是写密集场景，MySQL 成为明显性能瓶颈。需要优化以支撑高并发。

<b>分库分表策略：</b>

1. 按 biz_topic 名字分库分表：确保同一 topic 的消息有序性
2. 轮询插入：不考虑有序性时，轮流往所有表插入数据
   - 因为查找时只按发送时间查找，随机插入不影响查询
   - 解决不同 topic 负载差异大的问题

<b>批量操作策略：</b>

1. 延迟消费者：消费一批数据后批量插入数据库，然后批量提交
2. 延迟发送者：发送一批数据后批量更新状态为已发送
3. 大幅减轻 MySQL 压力，提高整体性能

<b>一致性处理：</b>

批量操作会加剧一致性问题，但只需消费者做到幂等即可解决（类似分区延迟时间方案）。

<b>总结：</b>

分库分表解决写入瓶颈，批量操作减少数据库交互次数，共同支撑高并发场景。
</details>
