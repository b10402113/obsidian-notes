# 消息顺序：保证消息有序，一个 topic 只能有一个 partition 吗？测验

**难度：** 混合（简单/中等/困难）
**题目数：** 15 题
**建议时间：** 20-25 分钟

## Section A：选择题（30分）

**Q1.** 在 Kafka 中，关于分区和消息顺序，以下哪项描述是**正确的**？

A) Kafka 保证不同分区之间的消息顺序
B) 每个分区都是一个有序、可变的消息日志
C) Kafka 保证同一分区内的消息顺序，但不保证不同分区之间的顺序
D) 消息的顺序是指消息实例创建的时间顺序

<details>
<summary>答案</summary>
<b>C) Kafka 保证同一分区内的消息顺序，但不保证不同分区之间的顺序</b>

在 Kafka 中，每个分区都是一个有序、不可变的消息日志。每个消息在分区日志里有唯一的 offset 标识位置。Kafka 保证同一分区内的消息顺序，但不保证不同分区之间的顺序。如果业务上有先后顺序的消息被发送到不同分区，无法确定哪个消息先被消费。
</details>

**Q2.** 有序消息中提到的"生产者生产消息的顺序"是指什么？

A) 消息实例创建的时间顺序
B) Broker 收到消息的顺序
C) 消息发送到分区的顺序
D) 消息被消费的顺序

<details>
<summary>答案</summary>
<b>B) Broker 收到消息的顺序</b>

有序消息强调的是消费者消费消息的顺序与生产者生产消息的顺序一致，但这里的生产顺序不是指消息实例创建的时间，而是指 broker 收到消息的顺序。例如两个生产者分别创建 msg1 和 msg2，但如果 msg2 先到达 broker，则认为 msg2 先于 msg1。
</details>

**Q3.** 在多分区方案中，如何确保同一个业务的消息发送到同一个分区？

A) 随机选择分区
B) 根据业务特征（如业务 ID）计算目标分区
C) 由 Broker 自动分配
D) 使用轮询方式选择分区

<details>
<summary>答案</summary>
<b>B) 根据业务特征（如业务 ID）计算目标分区</b>

在多分区方案中，生产者发送消息时需要根据业务特征（如业务 ID）计算目标分区。最简单的策略是根据业务 ID 对分区数量取余，余数就是目标分区。这样可以确保同一个业务的所有消息都发送到同一个分区，保证业务内的消息有序。
</details>

**Q4.** 多分区方案的两个主要缺点是什么？

A) 性能差和消息丢失
B) 数据不均匀和增加分区引起消息失序
C) 消息积压和消费者崩溃
D) 分区过多和 Broker 压力大

<details>
<summary>答案</summary>
<b>B) 数据不均匀和增加分区引起消息失序</b>

多分区方案有两个主要缺点：1) 数据不均匀：因为按业务特征选择分区，可能导致某些分区数据多、某些少，热点用户数据集中在一个分区会引起消息积压；2) 增加分区引起消息失序：新增分区后，新消息可能被发送到新分区并被优先消费，导致顺序错乱。
</details>

**Q5.** 对于增加分区引起消息失序的问题，解决方案是什么？

A) 删除旧的分区
B) 新分区的消费者暂停一段时间再开始消费
C) 将所有消息重新发送
D) 使用全局锁

<details>
<summary>答案</summary>
<b>B) 新分区的消费者暂停一段时间再开始消费</b>

解决增加分区引起消息失序的方法是：新增加分区的消费者暂停一段时间（如三分钟），确保同一个业务在其他分区上的消息已经被消费完毕后再开始消费。这虽然不能彻底解决根本问题，但能在很大程度上缓解。本身增加分区是少见操作，再加上消息失序概率低，可以通过监控发现后手工修复。
</details>

## Section B：是非题（20分）

**Q6.** 单分区方案虽然能保证全局有序，但性能很差，无法支撑高并发。 _(对/错)_

<details>
<summary>答案</summary>
<b>对</b>

单分区方案的优点是简单且全局有序，但有一个严重问题：性能太差。一个 topic 只有一个分区，无法支撑高并发。生产端所有消息都发送到同一个 broker，可能撑不住压力；消费端只有一个消费者，容易出现消息积压。
</details>

**Q7.** 大部分业务场景要求的都是全局有序，而不是业务内有序。 _(对/错)_

<details>
<summary>答案</summary>
<b>错</b>

大部分业务场景要求的不是全局有序，而是业务内有序。例如在下单场景中，业务只会要求同一个订单的创建订单消息先于完成支付消息，不会要求订单 A 的创建消息先于订单 B 的支付消息。如果业务要求全局有序，除了换更强的机器外，基本没有优化手段。
</details>

**Q8.** 在异步消费方案中，同一个业务的消息会被转发到同一个内存队列。 _(对/错)_

<details>
<summary>答案</summary>
<b>对</b>

异步消费方案中，消费者线程从 Kafka 拉取消息后转发到基于内存的队列。转发时根据业务特征字段（如业务 ID）做哈希计算，对工作线程数量取余，得到对应的内存队列。同一个业务的消息会被转发到同一个队列，确保业务内有序。
</details>

**Q9.** 解决数据不均匀问题可以使用 Redis 的槽与槽分配方案或一致性哈希算法。 _(对/错)_

<details>
<summary>答案</summary>
<b>对</b>

解决数据不均匀问题的两种方案：1) 槽与槽分配：借鉴 Redis 方案，使用 1024 或 16384 个槽，根据业务特征计算哈希值映射到槽，再根据业务特征合理分配槽到分区，可动态调整映射关系；2) 一致性哈希：将分区分布在哈希环上，调整分区间隔控制数据分布，哈希值从环上找到对应分区。
</details>

**Q10.** 跨 topic 的有序消息可以完全依靠消息队列来解决。 _(对/错)_

<details>
<summary>答案</summary>
<b>错</b>

跨 topic 的有序消息不能依赖消息队列解决。如果 msg1 发送到 topic_a，msg2 发送到 topic_b，业务要求 msg1 先于 msg2 消费，必须引入协调者负责消息重组。协调者需要让 msg2 的消费者暂停，等 msg1 来了唤醒消费者 A 处理 msg1，再唤醒消费者 B 处理 msg2。这是一个全新的话题，面试基本不会出现。
</details>

## Section C：填空题（20分）

**Q11.** Kafka 使用 **\_\_\_\_** 日志来存储消息，每个消息在分区里有唯一的 **\_\_\_\_** 标识位置。

<details>
<summary>答案</summary>
<b>WAL（write-ahead-log），偏移量（offset）</b>

Kafka 使用 WAL（write-ahead-log）日志存储消息。每个分区都有对应的日志文件，新消息追加到文件末尾，已加入的消息不会被修改。每个消息在分区日志里有唯一的偏移量（offset），标识消息在分区中的位置。
</details>

**Q12.** 在多分区方案中，解决数据不均匀问题可以借鉴 **\_\_\_\_** 的槽与槽分配方案，使用 **\_\_\_\_** 个槽（一般业务）或 **\_\_\_\_** 个槽（大规模）。

<details>
<summary>答案</summary>
<b>Redis，1024，16384</b>

解决数据不均匀问题可以借鉴 Redis 的槽与槽分配方案。Redis 使用 16384 个槽，但一般业务用不上那么多，可考虑使用 1024 个槽。根据业务特征计算哈希值，映射到槽，再根据数据多少合理分配槽到不同分区，保证分区负载均匀。
</details>

**Q13.** Kafka 中每个分区都是一个 **\_\_\_\_**、**\_\_\_\_** 的消息日志。

<details>
<summary>答案</summary>
<b>有序、不可变</b>

在 Kafka 中，每个分区都是一个有序、不可变的消息日志。分区是逻辑上的概念，用于对消息进行水平划分和并行处理。每个 topic 可划分为一个或多个分区，每个分区维护自己的消息序列。
</details>

## Section D：简答题（30分）

**Q14.** 请详细说明单分区方案和多分区方案的优缺点，以及多分区方案如何解决数据不均匀问题。

<details>
<summary>答案</summary>
<b>单分区方案：</b>

<b>优点：</b>
- 简单易实现
- 保证全局有序

<b>缺点：</b>
- 性能差，无法支撑高并发
- 所有消息发送到同一个 broker，压力集中
- 只有一个消费者，容易消息积压

<b>多分区方案：</b>

<b>优点：</b>
- 支撑高并发，多个分区多个消费者
- 业务内有序（同一业务消息到同一分区）
- 分散 broker 和消费者压力

<b>缺点：</b>
- 数据不均匀：按业务特征选择分区，可能某些分区数据多、某些少
- 增加分区引起消息失序：新分区消息可能被优先消费

<b>解决数据不均匀问题：</b>

1. **槽与槽分配方案（借鉴 Redis）**：
   - 使用 1024 或 16384 个槽
   - 根据业务特征计算哈希值映射到槽
   - 根据数据多少合理分配槽到分区
   - 可动态调整槽与分区的映射关系（通过配置中心）
   - 保证分区负载均匀

2. **一致性哈希方案**：
   - 将分区分布在哈希环上
   - 根据业务特征计算哈希值，从环上找到对应分区
   - 调整分区在环上的间隔，控制数据分布
   - 数据较多的哈希值区域多插入分区节点

<b>总结：</b>
这两种方案都能通过手工调整确保数据或流量在每个节点上分布大体均匀。
</details>

**Q15.** 请解释什么是"增加分区引起消息失序"问题，并说明具体场景和解决方案。

<details>
<summary>答案</summary>
<b>问题定义：</b>

在多分区方案中，如果中途增加新的分区，可能引起消息失序。原本应该先消费的消息反而被后消费，打破了业务内的消息顺序。

<b>具体场景：</b>

1. 最开始 id 为 3 的订单消息 msg1 发送到分区 0
2. 分区 0 上积攒很多消息，msg1 迟迟不被消费
3. 扩容增加新分区（如分区 3）
4. 新消息 msg2（也是 id 为 3 的订单）到达
5. 根据业务 ID 计算分区，msg2 被发送到新分区 3
6. 分区 3 上没有积压数据，消费者 3 直接消费 msg2
7. 结果：msg2 被 msg1 先消费，违反顺序（msg1 应先于 msg2）

<b>解决方案：</b>

新增加分区的消费者暂停一段时间再开始消费：

1. 根据积压消息消费时间估算等待时间
2. 例如积压消息需要 1 分钟消费，新分区消费者等待 3 分钟
3. 大概率积压消息先被消费完
4. 然后新分区消费者开始工作，避免失序

<b>方案局限性：</b>

- 不能彻底解决根本问题，只能很大程度上缓解
- 本身增加分区是少见操作
- 消息失序概率也很低
- 可通过监控发现失序场景，手工修复

<b>关键前提：</b>

等待时间要根据积压消息数量估算。如果积压消息需要 30 分钟，新分区至少要等待 30 分钟以上。
</details>
