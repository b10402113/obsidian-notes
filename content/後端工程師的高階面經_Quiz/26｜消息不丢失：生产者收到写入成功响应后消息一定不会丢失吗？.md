# 消息不丢失：生产者收到写入成功响应后消息一定不会丢失吗？测验

**难度：** 混合（简单/中等/困难）
**题目数：** 15 题
**建议时间：** 20-25 分钟

## Section A：选择题（30分）

**Q1.** 在 Kafka 中，ISR（In-Sync Replicas）是指什么？

A) 所有分区集合
B) 与主分区保持主从同步的所有从分区
C) 不在同步状态的分区集合
D) 主分区本身

<details>
<summary>答案</summary>
<b>B) 与主分区保持主从同步的所有从分区</b>

ISR（In-Sync Replicas）是指和主分区保持了主从同步的所有从分区。例如，一个主分区有 3 个从分区，但其中一个因网络问题无法同步数据，那么 ISR 就是剩下的 2 个分区。与之对应的概念是 OSR，即不在 ISR 里面的分区集合。可通过 min.insync.replicas 参数配置 ISR 的最小数量。
</details>

**Q2.** 在 Kafka 的 acks 参数中，acks=all 的含义是什么？

A) 发送后不管，不关心 broker 是否收到
B) 主分区写入成功即认为发送成功
C) 不仅写入主分区，还同步给所有 ISR 成员
D) 写入所有分区才算成功

<details>
<summary>答案</summary>
<b>C) 不仅写入主分区，还同步给所有 ISR 成员</b>

acks=all 表示不仅写入了主分区，还同步给了所有 ISR 成员。这是最强的写入语义。acks=0 是 "fire and forget"，不关心 broker 是否收到；acks=1 是主分区写入成功即认为成功。通过 min.insync.replicas 可以控制 ISR 最小数量，不足时 acks=all 会发送失败。
</details>

**Q3.** 在本地消息表方案中，异步补发机制的作用是什么？

A) 提高消息发送速率
B) 找出未发送成功的消息进行补发
C) 减少数据库压力
D) 优化消息队列性能

<details>
<summary>答案</summary>
<b>B) 找出未发送成功的消息进行补发</b>

本地消息表方案中，异步补发机制会扫描本地消息表，找出已经过了一段时间（如三分钟）但还未发送成功的待发消息，然后补发。这确保了即使立即发送失败或事务提交后服务器宕机，消息最终也会被发送。补发机制会将分布式事务转化为本地事务 + 补偿机制。
</details>

**Q4.** 在 Kafka 中，unclean 选举机制可能导致什么问题？

A) 性能下降
B) 主分区负载过高
C) ISR 中的分区丢失数据
D) 选举出的主分区缺少部分数据

<details>
<summary>答案</summary>
<b>D) 选举出的主分区缺少部分数据</b>

unclean 选举是指当 ISR 里面没有任何分区时，Kafka 选择第一个从分区作为主分区。这种选举机制是为了保证 Kafka 依旧可用，但 unclean 选出的新主分区可能少了部分数据（因为该分区不在 ISR 中，未同步最新消息）。可通过配置禁用 unclean 选举来避免消息丢失。
</details>

**Q5.** 消息回查机制（事务消息）的基本流程是什么？

A) 直接发送消息给消费者
B) 先发准备请求，业务完成后再发确认请求，中间件才转发给消费者
C) 消费者主动请求消息
D) 生产者和消费者直接通信

<details>
<summary>答案</summary>
<b>B) 先发准备请求，业务完成后再发确认请求，中间件才转发给消费者</b>

消息回查机制是两阶段提交的简单应用。应用代码先发送准备请求（包含消息），消息队列不转发给消费者。业务操作完成后，发送确认请求，中间件才转发消息给消费者。如果未收到确认请求，中间件会回查业务方是否应该提交。RocketMQ 支持此机制，但 Kafka 和 RabbitMQ 不支持。
</details>

## Section B：是非题（20分）

**Q6.** 在 acks=1 的情况下，如果主分区写入成功后立即崩溃，从分区可能缺少这条消息。 _(对/错)_

<details>
<summary>答案</summary>
<b>对</b>

acks=1 只要求写入主分区就认为发送成功。如果在主分区写入后立即崩溃，主从同步可能还没完成。此时发起主分区选举，无论哪个从分区被选上，都可能缺少这条消息（因为未同步到 ISR）。这就是 acks=1 的潜在消息丢失风险。
</details>

**Q7.** Kafka 的刷盘参数 log.flush.interval.messages 和 log.flush.interval.ms 都设置了，只要任一条件满足就会刷新磁盘。 _(对/错)_

<details>
<summary>答案</summary>
<b>对</b>

Kafka 支持定量刷和定时刷两种方式。log.flush.interval.messages 控制消息到多少条就强制刷盘，log.flush.interval.ms 控制间隔多少毫秒就刷盘。如果两个参数都设置了，只要任一条件满足就会刷新磁盘。Kafka 维护者建议依赖副本保证数据不丢失，而不是调整刷盘参数。
</details>

**Q8.** 本地消息表方案本质上是将分布式事务转化为本地事务加补偿机制。 _(对/错)_

<details>
<summary>答案</summary>
<b>对</b>

本地消息表方案的核心思想是将分布式事务转化为本地事务 + 补偿机制。例如，原本要执行业务操作并发送消息，转化为一个本地事务（包含业务操作和记录待发消息），然后通过补偿机制（异步补发）检查本地事务提交的数据，找出需要执行但未执行成功的下一步（发送消息），执行它。
</details>

**Q9.** 在 Kafka 上实现消息回查机制时，准备消息和提交消息必须保证有序。 _(对/错)_

<details>
<summary>答案</summary>
<b>对</b>

回查机制要求同一业务的准备消息一定要先于提交消息，否则可能先收到提交消息导致流程错乱。解决方案是发送时按照业务 ID 计算哈希值，对分区数量取余得到目标分区，确保同一业务的消息发送到同一分区，保持顺序。这与有序消息的解决方案一致。
</details>

**Q10.** 设置 acks=all 并禁用 unclean 选举后，消息绝对不会丢失。 _(对/错)_

<details>
<summary>答案</summary>
<b>错</b>

设置 acks=all 并禁用 unclean 选举后，消息丢失概率非常低，但仍有可能。只有一种情况：消息队列完成主从同步后，主分区和 ISR 的所有从分区都没来得及刷盘就全部崩溃，才会丢失消息。此时只能人工补发。消息在 page cache 中未刷盘，是 acks=all 情况下的唯一风险点。
</details>

## Section C：填空题（20分）

**Q11.** Kafka 的 acks 参数有三个取值：**\_\_\_\_** 表示发送后不管，**\_\_\_\_** 表示主分区写入成功，**\_\_\_\_** 表示主分区和 ISR 成员都同步成功。

<details>
<summary>答案</summary>
<b>0，1，all</b>

acks 参数控制写入语义：acks=0 是 "fire and forget"，不关心 broker 是否收到或是否持久化；acks=1 表示主分区写入成功即认为发送成功；acks=all 表示不仅写入主分区，还同步给所有 ISR 成员。acks=all 是最强的写入语义，可通过 min.insync.replicas 控制 ISR 最小数量。
</details>

**Q12.** 在 Kafka 中，ISR 是指 **\_\_\_\_**，与之对应的概念是 **\_\_\_\_**，指不在 ISR 里的分区集合。

<details>
<summary>答案</summary>
<b>与主分区保持主从同步的所有从分区，OSR</b>

ISR（In-Sync Replicas）是指和主分区保持主从同步的所有从分区。如果因网络等问题导致某个从分区无法同步，它会从 ISR 移出。OSR（Out-of-Sync Replicas）是不在 ISR 里的分区集合。可通过 min.insync.replicas 配置 ISR 最小数量，不足时 acks=all 会发送失败。
</details>

**Q13.** Kafka 的刷盘参数有两种策略：**\_\_\_\_**（log.flush.interval.messages）和 **\_\_\_\_**（log.flush.interval.ms）。

<details>
<summary>答案</summary>
<b>定量刷，定时刷</b>

Kafka 的刷盘策略有两种：定量刷（log.flush.interval.messages）控制消息到多少条就强制刷盘，定时刷（log.flush.interval.ms）控制间隔多少毫秒就刷盘。如果两个参数都设置，任一条件满足都会刷盘。还有 log.flush.scheduler.interval.ms 参数控制检测间隔。Kafka 建议依赖副本而非调整刷盘参数。
</details>

## Section D：简答题（30分）

**Q14.** 请详细说明从生产者发送到消费者完成消费的整个过程中，哪些环节可能导致消息丢失？以及每个环节的解决方案。

<details>
<summary>答案</summary>
<b>消息丢失的各个环节：</b>

<b>1. 生产者发送环节：</b>

<b>可能丢失场景：</b>
- acks=0：发送后不管，broker 可能没收到或处理失败
- 批量发送：批次大时，客户端可能连请求都没发出就崩溃

<b>解决方案：</b>
- 本地消息表：业务操作中记录待发消息（单事务），发送成功后删除或标记
- 异步补发机制：扫描未发送成功的消息（如三分钟前），补发
- 控制重试间隔和次数：避免无限制重试
- 转化为本地事务 + 补偿机制

<b>2. 主从同步环节：</b>

<b>可能丢失场景：</b>
- acks=1：主分区写入后崩溃，从分区缺少消息
- unclean 选举：ISR 为空时选择第一个从分区作为主分区，可能缺数据

<b>解决方案：</b>
- 设置 acks=all：确保主分区和 ISR 成员都同步
- 配置 min.insync.replicas：控制 ISR 最小数量
- 禁用 unclean 选举：避免 ISR 为空时选举缺少数据的分区

<b>3. 刷盘环节：</b>

<b>可能丢失场景：</b>
- acks=1 或 acks=all 时，消息在 page cache 中未刷盘就崩溃

<b>解决方案：</b>
- 调整 log.flush.interval.messages：定量刷盘
- 调整 log.flush.interval.ms：定时刷盘
- 调整 log.flush.scheduler.interval.ms：检测间隔
- Kafka 建议依赖副本而非频繁刷盘（性能考虑）

<b>4. 消费者提交环节：</b>

<b>可能丢失场景：</b>
- 异步消费：消费者线程提交后，工作线程未处理就崩溃
- 消息已提交但未消费

<b>解决方案：</b>
- 批量消费 + 批量提交：拉取一批消息，全部处理完再提交
- 确保消费逻辑幂等：重复消费不影响结果
- 处理部分失败：重试或丢回消息队列

<b>总结：</b>

从生产者、消息队列、消费者三个角度全面防护：
- 生产者：本地消息表 + 异步补发
- 消息队列：acks=all + 禁用 unclean 选举 + 刷盘参数
- 消费者：批量提交 + 幂等处理

虽然 acks=all + 禁用 unclean 选举后概率很低，但唯一风险是所有副本未刷盘就崩溃，需人工补发。
</details>

**Q15.** 请解释如何在 Kafka 上实现消息回查机制（事务消息），包括整体流程、回查实现方式、数据存储和有序消息的处理。

<details>
<summary>答案</summary>
<b>整体流程：</b>

1. 应用代码发送准备消息到 topic=look_back_msg，包含：
   - 业务 topic、消息体、业务类型、业务 ID
   - 准备状态、回查接口配置

2. 回查中间件消费 look_back_msg，将消息内容存储到数据库

3. 应用代码执行业务操作，完成后发送提交/回滚消息到 look_back_msg

4. 回查中间件查询消息内容，转发到业务 topic

5. 如果未收到提交消息，中间件扫描未提交消息，回查业务方

<b>回查实现方式：</b>

<b>HTTP 回查：</b>
- 业务方提供回查 URL
- 中间件发送请求：包含业务类型、业务 ID
- 业务方返回：是否提交或回滚

示例请求：
```
POST https://abc.com:8080/order/lookback
Body: {"biz_type": "order", "biz_id": "oid-123"}
```

<b>RPC 回查：</b>
- 中间件定义接口，业务方实现
- 业务方提供服务名
- 中间件利用 RPC 泛化调用功能发起调用

示例接口：
```
type MsgLookBack interface {
    LookBack(bizType string, bizID int) Status
}
```

<b>可扩展设计：</b>
支持 HTTP 和 RPC，体现系统设计能力。

<b>数据存储：</b>

参考延迟队列方案，支持高并发：

1. **分区表**：按时间分区，历史分区可归档
2. **交替表**：两个表按天交替读写，TRUNCATE 旧表
3. **分库分表**：按业务 topic 分库分表

示例：使用分区表，后续可扩展为分库分表（按业务 topic）。

<b>有序消息处理：</b>

<b>问题：</b>
回查机制要求准备消息先于提交消息，但可能先收到提交消息。

<b>解决方案：</b>
发送时按照业务 ID 计算哈希值，对分区数量取余得到目标分区，确保同一业务的消息发送到同一分区，保持顺序。

<b>关键点总结：</b>

1. 回查实现：HTTP/RPC 两种方式，可扩展设计
2. 数据存储：分区表、交替表、分库分表保证高性能
3. 有序消息：按业务 ID 哈希选择分区

<b>应用价值：</b>

在 Kafka 不支持回查的情况下自行实现，体现设计和实现复杂系统的能力。可结合延迟消息方案，做成开源框架。
</details>
