## 第一部分:選擇題 (每題 5 分,共 30 分)

**Q1.** undo log 的主要作用是什麼?

A) 記錄事务提交的修改,用於崩溃恢復
B) 記錄事务執行過程中被修改的數據,用於回滾
C) 記錄所有SQL語句,用於主從同步
D) 記錄索引修改,用於性能優化

<details>
<summary>答案</summary>
<b>B) 記錄事务執行過程中被修改的數據,用於回滾</b>

undo log 是指回滾日志,記錄著事务執行過程中被修改的數據。當事务回滾的時候,InnoDB 會根據 undo log 里的數據撤销事务的更改,把数据库恢復到原來的狀態。它就像"后悔药"。
</details>

---

**Q2.** redo log 采用的寫入方式是什麼,這種方式的性能優勢在哪?

A) 隨機寫,性能一般
B) 隨序寫,性能比隨機寫快一個數量級
C) 並行寫,性能極好
D) 分散式寫,性能較差

<details>
<summary>答案</summary>
<b>B) 隨序寫,性能比隨機寫快一個數量級</b>

redo log 是順序寫的(WAL write-ahead-log),不管要修改什麼數據,redo log 在磁盘上都是緊挨著的。順序寫的性能比隨機寫要好很多,即便在 SSD 上,順序寫也能比隨機寫速度快上一個數量級。這是中間件設計里的常用技巧。
</details>

---

**Q3.** innodb_flush_log_at_trx_commit 参数的默認值是?

A) 0
B) 1
C) 2
D) 3

<details>
<summary>答案</summary>
<b>B) 1</b>

innodb_flush_log_at_trx_commit 的默認值是 1,這是最安全的選項,表示每次提交的時候都刷新到磁盘上。0 表示每秒刷新到磁盘,2 表示每次提交的時候刷新到 page cache,依賴操作系统後續刷新到磁盘。只有設為 1 才能保證不丟數據。
</details>

---

**Q4.** binlog 和 redo log 的兩階段提交協議中,判断事务是否成功的標準是什麼?

A) redo log 是否 Prepare 成功
B) redo log 是否 Commit 成功
C) binlog 是否寫入成功
D) undo log 是否記錄成功

<details>
<summary>答案</summary>
<b>C) binlog 是否寫入成功</b>

如果 binlog 已經寫成功了,那麼即便 redo log 提交失敗,MySQL 也会認為事务已經提交了。如果 binlog 沒寫成功,那麼 MySQL 就認為提交失敗了。比較簡單的記憶方式就是看 binlog 寫成功了沒有。這是因為在兩階段提交里,binlog 提交成功意味著事务可以認為提交成功。
</details>

---

**Q5.** 在事务執行過程中,如果數据库在 redo log 刷新到磁盘後但 buffer pool 還未刷新時崩溃,重啟後會如何處理?

A) 用 undo log 回滾事务
B) 用 redo log 重放修改
C) 丢弃所有修改
D) 需要人工介入修復

<details>
<summary>答案</summary>
<b>B) 用 redo log 重放修改</b>

如果在 redo log 已經刷新到磁盘,然後數据库宕機了,buffer pool 丟失了修改,那麼在 MySQL 重啟之後就会回放這個 redo log,從而糾正數据库里的數據。極簡記法:如果 redo log 刷新到了磁盘,就是重放 redo log;在刷新之前都是回滾。
</details>

---

**Q6.** sync_binlog 参数的默認值是什麼?

A) 0
B) 1
C) 10
D) 100

<details>
<summary>答案</summary>
<b>A) 0</b>

sync_binlog 的默認值是 0,表示由操作系统決定,寫入 page cache 就認為成功了。0 是默認值,這時候數据库的性能最好。設為 1 表示每次事务提交都把 binlog 刷新到磁盘,N 表示每 N 次提交刷新到磁盘。
</details>

## 第二部分:是非題 (每題 4 分,共 12 分)

**Q7.** undo log 和 MVCC 的版本鏈密切相關,版本鏈就存儲在 undo log 中。 _(True/False)_

<details>
<summary>答案</summary>
<b>True</b>

正確。版本鏈存儲在 undo log 中。InnoDB 通過 roll_ptr 把每一行的歷史版本串聯在一起,這些串聯起來的歷史版本被放到 undolog裡面。undo log 不僅用於回滾,還支持 MVCC 的多版本讀取。
</details>

---

**Q8.** redo log 直接一步到位寫到磁盘,不經過任何中間緩衝。 _(True/False)_

<details>
<summary>答案</summary>
<b>False</b>

錯誤。redo log 本身也是先寫進 redo log buffer,後面再刷新到操作系统的 page cache,或者一步到位刷新到磁盘。這個刷新時機由 innodb_flush_log_at_trx_commit 参数控制(0/1/2),並非直接一步到位寫到磁盘。
</details>

---

**Q9.** 事务的 ACID 特性中的一致性,和分布式环境下的一致性语义是同一個概念。 _(True/False)_

<details>
<summary>答案</summary>
<b>False</b>

錯誤。事务 ACID 中的一致性指事务執行的結果必須滿足數據約束條件,不會出現矛盾的結果。而分布式环境下的一致性語義強調的是不同數據源之間數據一致。這兩個"一致性"含義不同,要注意區分。
</details>

## 第三部分:填空題 (每題 6 分,共 18 分)

**Q10.** 事务的 ACID 特性指的是<b>\_\_\_\_</b>、<b>\_\_\_\_</b>、<b>\_\_\_\_</b>和<b>\_\_\_\_</b>。

<details>
<summary>答案</summary>
<b>原子性(Atomicity), 一致性(Consistency), 隔离性(Isolation), 持久性(Durability)</b>

ACID 是事务的基本特性:原子性(不可分割,要么都成功要么都失敗)、一致性(滿足數據約束)、隔离性(隔離其他事务干擾)、持久性(結果永久保存,即使故障也不丟失)。
</details>

---

**Q11.** binlog 主要有兩個用途:<b>\_\_\_\_</b>和<b>\_\_\_\_</b>。

<details>
<summary>答案</summary>
<b>數据库故障時恢復數據, 主從同步</b>

binlog 記錄了 MySQL 中數据库的增删改操作,主要有兩個用途:一是數据库出現故障時恢復數據,二是用於主從同步,即便是 Canal 等中間件本質上也是把自己偽裝成一個從節點。
</details>

---

**Q12.** InnoDB 引擎先更新<b>\_\_\_\_</b>中的數據,再寫<b>\_\_\_\_</b>,事务提交後才刷新到磁盘。

<details>
<summary>答案</summary>
<b>buffer pool, redo log</b>

InnoDB 引擎讀寫不是直接操作磁盘的,而是讀寫內存里的 buffer pool。先把 buffer pool 里面的數據更新了,再寫一份 redo log。等到事务結束之後,就把 buffer pool 的數據刷新到磁盘里面。
</details>

## 第四部分:簡答題 (共 40 分)

**Q13.** (20 分) 詳細描述 UPDATE 语句的完整事务執行過程,包括 undo log、redo log、buffer pool 的作用和寫入顺序。並說明在崩溃恢復時如何處理。

<details>
<summary>答案</summary>
<b>參考答案:</b>

**事务執行過程(以 UPDATE tab SET a = 5 WHERE id = 1 为例,原值 a=3):**

1. **事务開始,查找目標行**
   - 查找到目標行
   - 加上鎖
   - 將數據讀入 buffer pool

2. **寫 undo log**
   - 記錄原值 a=3 和主键 id=1
   - 用於回滾時恢復原數據

3. **更新 buffer pool**
   - 在內存上更新值 a=5
   - buffer pool 中的數據已修改

4. **寫 redo log**
   - 記錄修改操作 a從3變為5
   - 先寫入 redo log buffer

5. **提交事务**
   - 根據 innodb_flush_log_at_trx_commit 决定是否刷新 redo log
   - 默認值1:每次提交刷新到磁盘

6. **刷新 buffer pool 到磁盘**
   - 將修改後的數據持久化
   - 可能延迟刷新(异步)

**崩溃恢復處理:**

**情況1: redo log 未刷新到磁盘**
- 用 undo log 回滾
- 撤销所有修改

**情況2: redo log 已刷新到磁盘**
- 重放 redo log
- 恢复 buffer pool 和磁盘數據
- 確保事务持久性

**關鍵記法:**
- redo log 刷新前:回滾
- redo log 刷新後:重放

**關鍵點:**
- 理解完整執行流程
- 掌握 undo log 和 redo log 的作用
- 了解崩溃恢復機制
</details>

**Q14.** (20 分) 解釋中間件的寫入語義概念,包括單機環境下的三種寫入層次和分布式環境下的五種寫入語義,並說明如何根據業務需求調整刷盤参数。

<details>
<summary>答案</summary>
<b>參考答案:</b>

**單機寫入語義(三種層次):**

1. **寫到緩衝區就成功**
   - 中間件寫到自身的日志中或緩衝區
   - 就認為寫入成功
   - 例:redo log buffer

2. **寫到 page cache 就成功**
   - 中間件發起系統调用
   - 寫到操作系统的 page cache
   - 就認為寫入成功
   - 例:innodb_flush_log_at_trx_commit=2

3. **寫到磁盘才成功**
   - 中間件強制發起刷盤
   - 數據被持久化到磁盘上
   - 才認為寫入成功
   - 例:innodb_flush_log_at_trx_commit=1

**刷盤策略(兩種):**
- **定時**:每秒刷到磁盘
- **定量**:按提交次数刷盤(如每N次)

**分布式寫入語義(五種):**

1. **主节点成功就成功**
   - 只要求主节点寫入成功

2. **至少一個從节点成功**
   - 主节点+至少1個從节点成功

3. **大多数從节点成功**
   - 主节点+多數從节点成功

4. **特定数量從节点成功**
   - 主节点+N個從节点成功(可配置)

5. **全部從节点成功**
   - 主节点+所有從节点成功

**調整刷盤参数策略:**

**數據安全優先:**
- sync_binlog = 1
- innodb_flush_log_at_trx_commit = 1(默認)
- 每次提交都刷盤,最安全
- 性能較差

**性能優先(容忍數據丟失):**
- innodb_flush_log_at_trx_commit = 0 或 2
- sync_binlog = 100 或更大
- 定時或定量刷盤
- 性能更好,可能丟數據

**業務分離策略:**
- 兩類業務分開數据库
- 高一致性業務用安全参数
- 高性能業務用性能参数

**實際例子:**
- Kafka 的 acks 機制
- Redis 的 AOF 刷盤时机

**關鍵點:**
- 理解單機和分布式寫入語義
- 掌握参数調整策略
- 能根據業務需求選擇合適配置
</details>
