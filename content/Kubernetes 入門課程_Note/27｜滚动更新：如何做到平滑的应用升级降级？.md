# 滾動更新：平滑的應用升級降級策略

## 📝 課程概述

本課程深入探討 Kubernetes 的應用更新机制——滾動更新（Rolling Update）。課程詳細說明 Kubernetes 如何定義应用版本、實現无感知的服务升级，以及透過 kubectl rollout 命令管理更新历史、暂停更新、版本回退等运维操作，讓复杂的版本管理工作变得自动化且可控。

## 核心觀念與實作解析

### Kubernetes 如何定義应用版本

#### 版本的概念重構

我們常會簡單地認為「版本」就是应用程序的「版本号」或容器镜像的「标签」，但在 Kubernetes 里，这个概念更加全面：

**在 Kubernetes 里，应用的「版本」是整个 Pod 模板（template）**。

Pod 是由 YAML 描述文件确定的，更准确地说，是 Deployment 等对象里的字段 `template`。哪怕 template 里只变动了一个字段，也会形成一个新的版本。

#### 版本号的生成机制

由于 template 内容太多，Kubernetes 使用**摘要算法**计算 template 的 Hash 值作为「版本号」。

Pod 名字里的那串随机数就是 Pod 模板的 Hash 值，例如：
- `ngx-dep-6796fc6f9k` - Hash值 `6796...` 表示当前版本
- 如果将镜像改成 `nginx:stable-alpine`，Hash 值变成 `7c6c...`，表示版本更新了

### 滾動更新的實現原理

#### 滾動更新的定義

**滾動更新（Rolling Update）** 是 Kubernetes 的默认更新策略，它不是把旧 Pod 全部销毁再一次性创建新 Pod，而是：

- **逐个创建新 Pod**
- **同时逐个销毁旧 Pod**
- 保证系统里始终有足够数量的 Pod 运行
- 没有「空窗期」中断服务

新 Pod 数量增加的过程像「滚雪球」，从零开始越滚越大。

#### 实战演示滾動更新

修改 Nginx Deployment 对象，明确指定版本号：

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: ngx-dep

spec:
  minReadySeconds: 15    # 筮认 Pod 就绪的等待时间
  replicas: 4
  ...
  containers:
  - image: nginx:1.21-alpine
  ...
```

`minReadySeconds` 字段不属于 Pod 模板，不影响 Pod 版本，但能让 Kubernetes 在更新过程中等待一点时间，确认 Pod 没问题才继续创建。

将镜像升级到 `nginx:1.22-alpine`，执行更新：

```bash
kubectl apply -f ngx-v2.yml
kubectl rollout status deployment ngx-dep
```

#### 滾動更新的过程详解

使用 `kubectl describe deploy ngx-dep` 观察变化：

**阶段 1**：
- V1 Pod（ngx-dep-54b865d75）数量：4
- V2 Pod：0

**阶段 2**：
- 创建 1个 V2 Pod（ngx-dep-d575d5776）
- V1 Pod 数量：3

**阶段 3**：
- V2 Pod 数量：2
- V1 Pod 数量：1

**阶段 4**：
- V2 Pod 数量：4
- V1 Pod 数量：0

整个更新过程结束。

**滾動更新本质上是两个同步进行的「应用伸缩」操作**：
- 老版本缩容到 0
- 新版本扩容到指定值
- 是一个「此消彼长」的过程

### 管理应用更新的命令

#### kubectl rollout 命令家族

**1. kubectl rollout status** - 查看更新状态

```bash
kubectl rollout status deployment ngx-dep
```

实时显示更新进度。

**2. kubectl rollout pause** - 暂停更新

在更新过程中可以随时暂停：

```bash
kubectl rollout pause deployment ngx-dep
```

用于检查、修改 Pod 或测试验证。

**3. kubectl rollout resume** - 继续更新

```bash
kubectl rollout resume deployment ngx-dep
```

确认没问题后继续更新。

**注意**：pause 和 resume 只支持 Deployment，不能用在 DaemonSet、StatefulSet 上（最新的 1.24 支持了 StatefulSet 的滾動更新）。

#### 版本历史管理

**1. kubectl rollout history** - 查看更新历史

```bash
kubectl rollout history deploy ngx-dep
```

输出版本列表，显示每次更新的历史记录。

**2. kubectl rollout history --revision** - 查看特定版本详情

```bash
kubectl rollout history deploy --revision=2
```

显示每个版本的详细信息，包括标签、镜像名、环境变量、存储卷等。

**3. kubectl rollout undo** - 版本回退

```bash
kubectl rollout undo deploy ngx-dep          # 回退到上一版本
kubectl rollout undo deploy ngx-dep --to-revision=1    # 回退到任意历史版本
```

`kubectl rollout undo` 执行的是滾動更新，只不过使用旧版本 Pod 模板：
- 把新版本 Pod 数量收缩到 0
- 把老版本 Pod 扩展到指定值

版本降级过程与版本升级过程完全一样，只是版本号变化方向相反。

### 添加更新描述（annotations）

#### annotations 字段的作用

`annotations` 字段用于给 API 对象添加附加信息：
- 形式上和 `labels`一样，都是 Key-Value
- 给 Kubernetes 内部的各种对象使用，像是「扩展属性」
- 主要面对 Kubernetes 外部的用户，用来筛选、过滤对象

比喻：
- **annotations**：包装盒里的产品说明书
- **labels**：包装盒外的标签贴纸

#### 使用 annotations 添加版本说明

使用特定字段 `kubernetes.io/change-cause`：

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: ngx-dep
  annotations:
    kubernetes.io/change-cause: v1, ngx=1.21
...

apiVersion: apps/v1
kind: Deployment
metadata:
  name: ngx-dep
  annotations:
    kubernetes.io/change-cause: update to v2, ngx=1.22
...

apiVersion: apps/v1
kind: Deployment
metadata:
  name: ngx-dep
  annotations:
    kubernetes.io/change-cause: update to v3, change name
...
```

创建并更新后，使用 `kubectl rollout history` 查看：

```
REVISION  CHANGE-CAUSE
1         v1, ngx=1.21
2         update to v2, ngx=1.22
3         update to v3, change name
```

每个版本的主要变动情况列得非常清楚，和 Git 版本管理的感觉很像。

### 滾動更新的精细控制

Deployment 的 `spec.strategy.rollingUpdate` 里还有其他字段：

- **maxSurge**：最多新增 Pod 数
- **maxUnavailable**：最多不可用 Pod 数

一般用默认值就足够了。

## 💡 重點摘要

- **应用版本定义**：版本是整个 Pod 模板，使用摘要算法计算 Hash 值作为版本号
- **滾動更新机制**：逐个创建新 Pod、逐个销毁旧 Pod，保证服务始终可用，无空窗期
- **rollout 命令**：status（查看状态）、pause（暂停）、resume（继续）、history（历史）、undo（回退）
- **版本历史管理**：Kubernetes 记录更新历史，支持回退到任意历史版本
- **annotations**：通过 `kubernetes.io/change-cause` 添加版本说明，便于运维管理
